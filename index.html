Как всё начиналось: обобщённое программирование до дженериков

Исходник Markdown ↗

Код главы: example_test.go · historical_test.go.

Историческая точка отсчёта — публичный Go 2009 года и стабильная модель Go 1, выпущенного 28 марта 2012 года. Параметров типов ещё нет, но обобщённые программы уже есть.

Сначала восстановим условия задачи

Представим автора библиотеки начала 2010-х. Нужно один раз написать поиск, сортировку и обход коллекции, а затем применять их к числам, дробям, денежным суммам и пользовательским структурам. Синтаксиса func Find[T ...] нет. Нельзя начинать объяснение с того, что этот автор «забыл добавить T»: такой возможности у него не было.

У него есть конкретные типы, методы, интерфейсы, функции как значения, замыкания, срезы и работа с runtime-типами через reflection. Он может отделить поведение от данных и передать алгоритму необходимые операции. Вопрос не в том, возможно ли обобщение, а в том, какую часть знания о типах можно сохранить на границе библиотечной функции.

Go стал публичным 10 ноября 2009 года. Go 1 закрепил стабильную основу языка и стандартных библиотек в марте 2012 года. В учебнике мы используем Go 1 как опорную модель и не приписываем все его детали каждой дорелизной сборке. Например, предопределённый тип error относится к изменениям Go 1. Источники: исторический контекст Why Generics?, объявление Go 1, изменения Go 1.

Что уже было обобщённым

Встроенный срез позволял хранить конкретные значения разных выбранных типов: []int, []string, []Fraction. Библиотека не обязана была превращать их в общий объектный контейнер. len, append и copy применялись по специальным правилам языка.

Но автор обычной функции не мог объявить аналогичный параметр «срез произвольного E» и связать этот E с типом возвращаемого значения. Между выразительностью встроенных операций и выразительностью пользовательских сигнатур оставался разрыв.

Для работы с поведением уже хватало маленького интерфейса:

Go Исходник ↗
type Stringer interface {
    String() string
}

func Describe(value Stringer) string {
    return value.String()
}

Все наши шесть типов имеют метод String() string. Поэтому одна Describe работает с дробью, деньгами и версией без параметров типов и без ручного исследования типа. У операции один и тот же результат — string, независимо от реализации.

Задача «вызови общее поведение» решена. Более трудная задача — «прими значение произвольного типа и верни результат того же или связанного типа». Например, Add у денег возвращает Money, а Add у дроби — Fraction. Именно здесь далее появится затруднение.

Исторический образец: sort.Interface

В исходниках тега Go 1 пакет sort уже определяет интерфейс коллекции с тремя методами:

Go Исходник ↗
type Interface interface {
    Len() int
    Less(i, j int) bool
    Swap(i, j int)
}

Сортировка не получает значение неизвестного типа. Она узнаёт длину, сравнивает позиции и переставляет их. Конкретный тип элемента остаётся у реализации этих операций. Это центральный приём раннего Go: скрыть элемент за действиями, достаточными алгоритму. Исторический источник: sort.go из Go 1.

Такой подход не требует наследования от базового класса коллекций. Новый определённый тип с нужными методами удовлетворяет интерфейсу. Программа может расширить набор поддерживаемых коллекций, не переписывая сортировку.

Чего нельзя рисовать в исторической схеме

Неверно утверждать, что интерфейсы появились после reflection, или что reflection был следующим релизом после интерфейсов. Они сосуществовали в раннем Go. Также генерация исходников была возможна до появления команды go generate.

В первых главах мы исследуем несколько доступных тогда решений одного ограничения. Лишь затем перейдём к новым возможностям языка и библиотек. Статья The Laws of Reflection опубликована в 2011 году — это хороший ориентир, показывающий, что reflection не был поздним ответом на отсутствие generics.

Наши типы: одинаковые операции ещё не дают общего алгоритма

Исходник Markdown ↗

Код главы: example_test.go · types_test.go.

Возьмём настоящие типы проекта и отделим математические и предметные операции от алгоритмов обхода.

Теперь выберем данные для библиотеки. Нам нужны не абстрактные E и T, а дроби, деньги и числа с понятным поведением. Сравним их методы и отделим одинаковые названия от одинаковых сигнатур.

Полные объявления и методы находятся в отдельных пакетах: fraction, money, boxint, intvalue, vector2, version.

Мы специально добились большого пересечения методов: у Fraction, BoxInt и IntValue совпадают одиннадцать имён и форм сигнатур, у Money — девять из этих одиннадцати. Но это сходство на уровне схемы с заменой собственного типа, а не идентичность конкретных сигнатур Go. Таблица методов фиксирует точный контракт.

Дробь: сравнить представление или значение?

Go Исходник ↗
half := fraction.Fraction{Numerator: 1, Denominator: 2}
other := fraction.Fraction{Numerator: 2, Denominator: 4}

sameFields := half == other // false
sameValue := half.Equal(other) // true

Если общий Find будет использовать равенство полей, он решит другую задачу. Алгоритму нужно передать выбранное условие или операцию предметного типа, а не угадывать смысл сравнения.

Денежные суммы ещё строже: 100 USD и 100 EUR нельзя просто сложить или упорядочить как целые 100. Money.Add и Money.Compare возвращают ошибку при разных валютах. Поэтому сигнатура нашего алгоритма должна уметь передавать ошибку наружу.

Одна форма метода, разные сигнатуры

Схема
Fraction.Add(Fraction) → (Fraction, error)
BoxInt.Add(BoxInt)     → (BoxInt, error)
Money.Add(Money)       → (Money, error)

Нельзя заменить аргумент и результат интерфейсом и ожидать, что эти методы автоматически его реализуют:

Go Исходник ↗
// Такое объявление допустимо, но наши типы его НЕ реализуют.
type Adder interface {
    Add(interface{}) (interface{}, error)
}

Go требует совпадения сигнатур методов. Возможность отдельно присвоить Money в interface{} не меняет тип метода Money.Add. И пустой интерфейс не обозначает «тот же тип, что у получателя».

Для String всё иначе: String() string действительно является одной и той же сигнатурой у всех шести типов. Поэтому маленький интерфейс Stringer работает непосредственно, без адаптации каждого результата.

Find, All и Map здесь — названия учебных задач, а не заявления о наличии одноимённых функций в Go 1. В нашем нынешнем пакете Find возвращает индекс или -1, All на пустом входе — true, Any — false; все три дополнительно возвращают error.

Где заканчивается общее

У Vector2 нет Compare: можно сортировать по длине или координатам, но критерий должен выбрать вызывающий. У Version нет Add: арифметически складывать номера версий не имеет предметного смысла. Не следует добавлять такие методы только ради единого большого интерфейса.

Чем меньше операций просит алгоритм, тем больше подходящих типов. Find не обязан требовать Add; Sum не обязан требовать Compare. Это принцип проектирования интерфейсов, доступный задолго до дженериков.

Первая реализация: конкретный тип и повторяющийся цикл

Исходник Markdown ↗

Код главы: concrete.go · example_test.go.

Начнём с программы, которую можно написать без какой-либо универсальной библиотеки, и увидим место повторения.

Начнём с рабочего поиска по дробям. Затем поменяем только условие, а после — тип элементов. Так станет видно, какая часть программы повторяется и что именно стоит обобщать.

Find только для дробей

Следующая функция реализована в lessons/concrete. Это первый учебный шаг перед общим пакетом algorithms. Здесь и далее фрагменты опускают package и импорты; полные версии адаптеров будут взяты из тестируемого кода проекта.

Go Исходник ↗
func FindFraction(values []fraction.Fraction, target fraction.Fraction) (int, error) {
    if err := target.Validate(); err != nil {
        return -1, err
    }
    for i, value := range values {
        if err := value.Validate(); err != nil {
            return -1, err
        }
        if value.Equal(target) {
            return i, nil
        }
    }
    return -1, nil
}

Компилятор знает тип элемента и target. Поиск использует математическое равенство. У него есть ранняя остановка и отдельный признак отсутствия результата. Из невалидной дроби не получается молча «не совпало», поскольку мы сознательно выбрали проверку входа перед сравнением.

Если нужен Find для BoxInt, типы изменятся, а цикл почти нет. Если нужен поиск положительной дроби, придётся менять и условие. Эти две причины повторения нужно разделить.

Функция высшего порядка убирает одну причину

Go Исходник ↗
func FindFractionFunc(values []fraction.Fraction,
    test func(fraction.Fraction) (bool, error)) (int, error) {
    for i, value := range values {
        matched, err := test(value)
        if err != nil {
            return -1, err
        }
        if matched {
            return i, nil
        }
    }
    return -1, nil
}

Теперь можно искать равную, положительную или нулевую дробь, передавая разные test. Цикл уже переиспользуется между предметными условиями. Функции как значения и замыкания были средствами раннего Go; callback не является следствием появления generics.

Но []Money по-прежнему не подходит. Мы обобщили поведение, оставив фиксированным тип данных.

То же ограничение у суммы

Go Исходник ↗
func SumMoney(values []money.Money, initial money.Money) (money.Money, error) {
    total := initial
    for _, value := range values {
        next, err := total.Add(value)
        if err != nil {
            return total, err // в этом варианте возвращаем уже накопленный префикс
        }
        total = next
    }
    return total, nil
}

Для дробей появится SumFraction с таким же порядком действий: получить значение, сложить, проверить ошибку, заменить аккумулятор. Копирование этой логики для новых типов увеличивает число мест, в которых можно нарушить контракт.

Обратите внимание: ошибка Add не означает автоматического отката уже накопленной суммы. Здесь возврат частичного результата — явное решение API. Другой вариант мог бы возвращать только нулевой результат при ошибке, но это уже другой договор с вызывающим.

Map показывает повторение по двум типам

Для преобразования дробей в строки потребовалась бы функция с сигнатурой:

Схема
MapFractionText([]Fraction, func(Fraction) (string, error)) → ([]string, error)

А для строк из Money — другая. Для получения целых из BoxInt — третья. Повторяется не только тип входа, но и связь между входом, callback и выходом.

Изменение требованияДостаточно другого callback?
Найти равную дробь вместо положительнойДа, в FindFractionFunc
Найти деньги вместо дробиНет, сигнатура принимает только Fraction
По-другому отформатировать дробь в stringДа, в конкретном MapFractionText
Преобразовать дробь в другой выходной типНет, потребуется другая сигнатура Map

Почему не стоит осуждать этот первый вариант

Для одной короткой задачи конкретный цикл может быть лучшим выбором: легко читать, типы известны, нет адаптеров. Проблема появляется у автора многократно используемой библиотеки. Ему нужно не убрать две строки любой ценой, а сохранять один проверенный алгоритм при росте набора типов.

Следующая мысль не требует новых возможностей языка: если Find возвращает индекс, может быть, самому алгоритму вообще не нужен тип элемента?

Индексы и замыкания: элемент остаётся у вызывающего

Исходник Markdown ↗

Код главы: find.go · example_test.go · map_test.go.

Ранний Go позволял исключить неизвестный тип из сигнатуры, передав алгоритму операцию над индексом.

Find возвращает индекс. Значит, он может вообще не получать элемент: достаточно спросить, подходит ли позиция. Проверим эту идею сначала на поиске, затем на записи результата Map.

Линейный поиск только по позициям

Go Исходник ↗
func FindIndex(n int, test func(int) (bool, error)) (int, error) {
    for i := 0; i < n; i++ {
        matched, err := test(i)
        if err != nil {
            return -1, err
        }
        if matched {
            return i, nil
        }
    }
    return -1, nil
}

Этот вариант теперь можно запустить отдельно: реализация FindIndex, примеры для дробей и денег, объяснение альтернативы. Импорт — gotypes/algorithms/closures, вызов — closures.FindIndex. В основном пакете algorithms длина и проверка объединены в интерфейсном объекте.

Go Исходник ↗
half := fraction.Fraction{Numerator: 1, Denominator: 2}
index, err := FindIndex(len(values), func(i int) (bool, error) {
    if err := values[i].Validate(); err != nil {
        return false, err
    }
    return values[i].Equal(half), nil
})

Тип values — []Fraction, известный замыканию. FindIndex получает только int, bool и error. Для денег меняется замыкание, а библиотечный цикл сохраняется. Нет упаковки элементов в interface{} и нет runtime-исследования их типов.

Это уже типобезопасное обобщение поведения и данных, но информация о данных находится за границей алгоритма. Сигнатура не сообщает, что n является длиной именно той коллекции, которую индексирует test.

Настоящий образец: sort.Search

Стандартный sort.Search тоже принимает размер и функцию от индекса. Он выполняет бинарный поиск границы, где монотонный предикат меняется с false на true. Результат отсутствия границы — n, а не -1.

Go Исходник ↗
// import "sort"
values := []int{2, 5, 9, 12}
index := sort.Search(len(values), func(i int) bool {
    return values[i] >= 8
}) // 2

Привязка к данным находится в замыкании, сам Search не знает тип элементов. Этот API иллюстрирует, почему далеко не каждой полезной обобщённой функции необходим параметр E. Правила поиска: sort.Search.

Наш FindIndex нельзя заменить на бинарный Search для произвольных дробей: условие «равен 1/2» не обязано быть монотонным. Важнее сходства сигнатур — предусловия конкретного алгоритма.

Map через замыкание записи

Go Исходник ↗
func MapIndex(n int, apply func(int) error) error {
    for i := 0; i < n; i++ {
        if err := apply(i); err != nil {
            return err
        }
    }
    return nil
}
Go Исходник ↗
var texts []string
if values != nil {
    texts = make([]string, len(values))
}
err := MapIndex(len(values), func(i int) error {
    if err := values[i].Validate(); err != nil {
        return err
    }
    texts[i] = values[i].String()
    return nil
})

Создание результата и преобразование остаются конкретно типизированными. Но MapIndex организует только цикл: он не может сам выбрать тип и создать []string, потому что не получает сведений о связи входа и выхода.

Если длина texts не соответствует n, ошибка проявится в callback. Если ошибка преобразования произошла посередине, заполненный префикс сохраняется. Это не последствия интерфейсов или reflection — они возникли уже на уровне договора индексного API.

Почему следующим шагом станет объект операций

Мы передаём несколько согласованных частей: размер, исходные данные, предикат или функцию записи. Их можно связать в один адаптер с методами. Тогда алгоритм сможет попросить минимальный набор операций, а вызывающий — реализовать их конкретным типом.

Обе формы были доступны в одной исторической модели языка. Переход от замыкания к интерфейсу в учебнике — изменение организации программы, а не очередной релиз Go.

Значение через интерфейс: что обещает параметр

Исходник Markdown ↗

Код главы: interfaces.go · example_test.go.

Разберём прямую передачу Fraction: сначала Stringer, затем interface{} и проверку нужного поведения.

Замыкание уже позволило передать поведение. Теперь посмотрим на второй инструмент раннего Go — интерфейс. Начнём с одной дроби и метода String, чтобы пока не смешивать значение и коллекцию.

Можно ли передать саму Fraction через интерфейс

Да. Дробь можно передать через любой обычный интерфейс, требованиям которого она удовлетворяет. Адаптер не является обязательной обёрткой для всех значений Go. Сначала нужно спросить: какие именно действия потребитель хочет выполнять?

В следующих фрагментах используются пакеты fmt, gotypes/fraction и gotypes/money. Это отдельные учебные варианты API, а не новые функции пакета algorithms. Заведомо некомпилируемые строки явно отмечены.

Go Исходник ↗
type Stringer interface {
    String() string
}

func PrintValue(value Stringer) {
    fmt.Println(value.String())
}
Go Исходник ↗
f := fraction.Fraction{Numerator: 1, Denominator: 2}
m := money.Money{Amount: 250, Currency: "USD"}
PrintValue(f) // 1/2
PrintValue(m) // 250 USD (minor units)

Оба типа уже имеют String() string. Поэтому они подходят напрямую. Функция печати не нуждается ни в fractionQuery, ни в проверке конкретного типа. Она обобщена по поведению «предоставить строковое представление».

Что сохраняется внутри интерфейса, а что доступно снаружи

Go Исходник ↗
f := fraction.Fraction{Numerator: 1, Denominator: 2}
var value Stringer = f
text := value.String() // Разрешено контрактом Stringer.
// value.Numerator     // Не компилируется: поле не доступно через Stringer.
// value.Add(f)        // Не компилируется: Stringer не объявляет Add.

Статический тип value — Stringer. Конкретный тип хранимого значения — fraction.Fraction. Дробь не теряет свои поля и методы, но потребитель через Stringer может использовать только операции этого интерфейса. Присваивание структуры по значению сохраняет копию её значения; оно не превращает исходную переменную f в интерфейсную переменную.

Если потребителю действительно необходима именно дробь, можно проверить конкретный тип:

Go Исходник ↗
f, ok := value.(fraction.Fraction)
if ok {
    fmt.Println(f.Numerator, f.Denominator)
}

Это type assertion, а не преобразование произвольного объекта в дробь. Для хранимого Money ok будет false. Для хранимого *fraction.Fraction проверка на fraction.Fraction тоже даст false: указатель и значение — разные конкретные типы. Форма без ok паникует при несовпадении.

Если общий алгоритм постоянно делает такие проверки для Fraction, Money и BoxInt, знание предметных типов переместилось внутрь него. Добавление нового типа потребует дописать соответствующую ветку. Иногда это нужный закрытый набор случаев, но это уже другой способ обобщения.

Почему пустой интерфейс не решает вопрос операций

Go Исходник ↗
var value interface{} = fraction.Fraction{Numerator: 1, Denominator: 2}
// value.String() // Не компилируется: interface{} не объявляет методов.

Пустой интерфейс принимает дробь, деньги и другие значения. Но его контракт не обещает ни String, ни Add. После приёма значения придётся проверять конкретный тип или наличие нужного поведенческого интерфейса.

Например, проверка value.(Stringer) открывает доступ к String, но ничего не говорит о сложении. Возможность принять любое значение и возможность выполнить нужную операцию — разные требования к API.

Одна задача: пустой интерфейс или интерфейс с нужным методом

Пусть функция должна получить строковое представление значения именно через его метод String. Сравним две сигнатуры на одной задаче. Stringer с методом String() string уже объявлен выше.

Go Исходник ↗
func DescribeUnknown(value interface{}) (string, error) {
    stringer, ok := value.(Stringer)
    if !ok {
        return "", fmt.Errorf("тип %T не предоставляет String() string", value)
    }
    return stringer.String(), nil
}

func DescribeStringer(value Stringer) string {
    return value.String()
}

Первая функция принимает любое значение. Но внутри ей требуется конкретное поведение, которого пустой интерфейс не обещает. Поэтому она проверяет соответствие Stringer во время выполнения и обрабатывает отказ.

Вторая функция сообщает это требование сразу в сигнатуре. Для аргумента конкретного типа компилятор проверяет наличие String до запуска программы. Внутри можно сразу вызвать метод; отдельная ветка «метода нет» не нужна.

Go Исходник ↗
f := fraction.Fraction{Numerator: 1, Denominator: 2}

text, err := DescribeUnknown(f) // Работает; соответствие проверится внутри.
fmt.Println(text, err)         // 1/2 <nil>

text = DescribeStringer(f)     // Работает; Fraction уже удовлетворяет Stringer.
fmt.Println(text)              // 1/2

Теперь передадим обычное целое число:

Go Исходник ↗
text, err := DescribeUnknown(42) // Компилируется, но вернёт ошибку выполнения.
// DescribeStringer(42)          // Не компилируется: у int нет String() string.

Это не запрет форматировать int вообще. Здесь выбран конкретный контракт «вызвать String». Функции fmt умеют форматировать числа по собственным правилам; их более широкий API решает другую задачу.

Что именно проверяет assertion на интерфейс

В DescribeUnknown используется value.(Stringer), а не value.(fraction.Fraction). Это важная разница:

ПроверкаЧто спрашиваемКакие значения подходят
value.(fraction.Fraction)Хранится ли здесь именно значение Fraction?Этот конкретный тип
value.(Stringer)Предоставляет ли хранимый тип нужный метод?Fraction, Money и другие реализации Stringer

Поэтому проверка на поведенческий интерфейс не требует перечислять все предметные типы. Но при приёме interface{} сама проверка всё равно происходит во время выполнения. Её нельзя убрать только потому, что сегодняшние вызовы передают дроби.

Есть и обратная ситуация: конкретное значение подходит, но статический тип переменной слишком широк:

Go Исходник ↗
var unknown interface{} = fraction.Fraction{Numerator: 1, Denominator: 2}
// DescribeStringer(unknown) // Не компилируется: interface{} не обещает String.

stringer, ok := unknown.(Stringer)
if ok {
    fmt.Println(DescribeStringer(stringer))
}

Как только значение оказалось за границей interface{}, вызывающий должен восстановить нужный контракт проверкой. Компилятор оценивает тип выражения unknown, а не выводит из его текущего содержимого разрешение на вызов.

Оба варианта используют интерфейсные значения

Пустой интерфейс и Stringer могут хранить одну и ту же конкретную Fraction. Различается набор обещанных операций: у interface{} он пуст, у Stringer есть String. В обоих случаях за интерфейсом остаётся конкретное значение; вызов метода направляется к его реализации.

Поэтому неверно объяснять различие словами «пустой интерфейс динамический, а интерфейс с методами вообще без динамики». Важная гарантия Stringer — проверка соответствия контракту на границе передачи, а не запрет выбирать конкретную реализацию во время выполнения. Здесь также нельзя без измерений обещать отсутствие выделений памяти или конкретное ускорение.

Что получит наш алгоритм от правильного контракта

Если бы Find принимал interface{}, пришлось бы сначала выяснять, как получить длину и проверить позицию. Можно проверять известные типы срезов либо делать assertion на Predicate. В последнем случае функция фактически требует Predicate, но скрывает это требование от своей сигнатуры.

Наш вариант Find(data Predicate) объявляет Len и Match сразу. fractionQuery удовлетворяет контракту и передаётся напрямую. Если вызывающий хранит его в переменной interface{}, перед Find понадобится проверка на Predicate — по той же причине, что в примере с unknown.

Замена Predicate на interface{} не делает []Fraction пригодным для поиска автоматически. Принять срез получится, но операции поиска всё равно нужно откуда-то получить. Пустой интерфейс расширяет набор допустимых входов, а не добавляет этим входам методы.

Когда пустой интерфейс оправдан

Пустой интерфейс полезен, когда API действительно принимает произвольные значения и не требует от каждого одного обязательного метода. Например, нужно передать значение дальше без исследования либо поддержать несколько видов входа с разными правилами обработки. Тогда динамические проверки являются частью явного договора.

Если же алгоритму всегда нужны одни и те же операции, интерфейс с этими методами точнее описывает задачу. Он позволяет отсеять неподходящие конкретные аргументы до выполнения и уменьшает число проверок внутри алгоритма.

Наличие методов не доказывает их смысл: Stringer не гарантирует нужный формат, Predicate — правильность предиката, а типизированный nil по-прежнему может попасть в интерфейс. Но требование «метод существует с такой сигнатурой» уже выражено и проверяемо.

В современном Go any является псевдонимом interface{}, поэтому замена названия не добавляет методов или статических гарантий. В исторических примерах мы оставляем написание interface{}.

Ограничения интерфейсов: свой тип, срезы и указатели

Исходник Markdown ↗

Stringer объединяет одинаковое поведение. Теперь проверим, может ли обычный интерфейс сохранить связь между типом аргумента и типом результата.

Мы научились вызывать общий String у дроби и денег. Следующий вопрос сложнее: можно ли таким же образом сложить значения и сохранить их собственный тип? Именно здесь видны границы обычного интерфейса.

Почему одинаковое имя Add не даёт общего метода

Наши методы имеют конкретные сигнатуры:

Схема
Fraction.Add(Fraction) → (Fraction, error)
Money.Add(Money)       → (Money, error)

Соблазнительно заменить конкретные типы одним интерфейсом:

Go Исходник ↗
type Addable interface {
    Add(Addable) (Addable, error)
}

// Не компилируется: у Fraction другая сигнатура Add.
// var _ Addable = fraction.Fraction{}

Интерфейс Addable требует метод, который принимает Addable и возвращает Addable. Fraction.Add принимает только Fraction и возвращает Fraction. Go не вставляет автоматические обёртки для параметров и результатов методов. Совпасть должны сами сигнатуры, а не только имя и число аргументов. Это правило также разобрано в FAQ о сигнатурах методов.

Здесь есть существенная разница обещаний. Если бы и дроби, и деньги удовлетворяли Addable, контракт разрешал бы передать деньги в Add дроби: параметр объявлен как Addable. Он не означает «значение того же конкретного типа, что и получатель».

Даже интерфейс с методом Add(Fraction) (Addable, error) не подошёл бы к исходному методу: его результат Fraction не совпадает с объявленным результатом Addable. То, что отдельное значение можно присвоить интерфейсу, не меняет тип всей функции.

Интерфейс для сложения конкретных дробей возможен

Go Исходник ↗
type FractionAdder interface {
    Add(fraction.Fraction) (fraction.Fraction, error)
}

func AddFraction(left FractionAdder, right fraction.Fraction) (fraction.Fraction, error) {
    return left.Add(right)
}

var _ FractionAdder = fraction.Fraction{}

Такой код корректен и обходится без адаптера. Но связь с Fraction явно осталась в параметре и результате. Этот контракт допускает разные реализации операции над дробью; он не превращается в общий Sum для дробей, денег и целых.

Термин «обобщение» здесь требует уточнения: можно обобщить реализацию поведения, сохранив фиксированные типы аргументов, а можно захотеть обобщить и сами эти типы. Обычные интерфейсы прекрасно решают первую задачу, но не выражают произвольную связь «аргумент и результат имеют тот же конкретный тип».

Можно ли переделать Add под interface{}

Технически можно спроектировать метод Add(interface{}) (interface{}, error), извлекать внутри Fraction через assertion и возвращать ошибку для неподходящего типа. Но существующий Add пришлось бы изменить или поместить такую операцию в обёртку: перегрузить два метода с именем Add у одного базового типа нельзя.

Тогда вызов с Money станет допустим на этапе компиляции, а проверку совместимости возьмёт на себя реализация. Результат тоже будет иметь статический тип interface{}; чтобы получить Fraction, вызывающий должен проверять его конкретный тип. Это осознанный обмен статических гарантий на динамическую обработку, а не бесплатное устранение адаптера.

В нашем moneySum сложение остаётся Money.Add(Money). Общий алгоритм вызывает Add(index), а адаптер берёт конкретные деньги из своего среза. Проверка совместимости валют остаётся предметной проверкой даже при таком статически согласованном типе.

Почему []Fraction нельзя передать как []Stringer

Go Исходник ↗
func PrintAll(values []Stringer) {
    for _, value := range values {
        fmt.Println(value.String())
    }
}
Go Исходник ↗
fractions := []fraction.Fraction{
    {Numerator: 1, Denominator: 2},
}
// PrintAll(fractions) // Не компилируется: []Fraction не является []Stringer.

Соответствие интерфейсу у элемента не распространяется автоматически на контейнер. Типы []fraction.Fraction и []Stringer различаются. Go не выполняет скрытый цикл присваиваний элементов; нужен отдельный срез. См. FAQ о срезах интерфейсов.

Go Исходник ↗
var printable []Stringer
if fractions != nil {
    printable = make([]Stringer, len(fractions))
}
for i, value := range fractions {
    printable[i] = value
}
PrintAll(printable)

Теперь каждый элемент printable — интерфейсное значение. Оно может хранить и Fraction, и Money. Присваивание printable[0] = money.Money{Currency: "USD"} было бы допустимо и заменило бы элемент нового среза, не элемент исходного fractions.

Это также помогает увидеть, почему нельзя просто обращаться к одному срезу как к другому: []Stringer разрешает записывать значения разных подходящих типов, а []Fraction разрешает хранить только дроби. В нашем примере структуры копируются по значениям. Если упаковать указатели, сами указатели будут скопированы, но объекты за ними могут остаться общими.

Замыкание и коллекционный адаптер позволяют обходить исходный []Fraction без такого поэлементного упаковывания.

Почему одна Fraction всё равно не подходит нашему Find

Наш Find просит Len и Match(index). Это контракт коллекции вместе с условием, а не контракт отдельной дроби. Наличие у Fraction методов String, Equal и Add не удовлетворяет этим другим требованиям.

Можно было бы придумать объект поиска из одного элемента с Len, возвращающим 1. Но смысл проверки всё равно пришлось бы где-то задать. Такой объект фактически стал бы адаптером одиночного значения; он не решил бы задачу обхода произвольного среза.

У самого []Fraction также нет методов Len и Match. А если они нужны именно выбранному интерфейсному API, их предоставляет fractionQuery. Для API FindIndex достаточно длины и замыкания — отдельные методы вообще не требуются.

Значение и указатель: ещё одна граница соответствия

Методы нашего Fraction объявлены с получателем по значению. Поэтому и Fraction, и *Fraction удовлетворяют Stringer. У moneySum метод Add(index) объявлен с получателем-указателем, поскольку он изменяет Total. Интерфейсу Summable удовлетворяет *moneySum, а значение moneySum — нет.

Вызов sum.Add(0) для адресуемой переменной sum может выглядеть рабочим: Go допускает неявное взятие адреса при таком вызове метода. Но присваивание sum интерфейсу не добавляет недостающие методы. В algorithms.Sum нужно передать &sum. Правила: наборы методов в спецификации.

Отдельно от соответствия типов стоит пригодность значения. Нулевой указатель может удовлетворять интерфейсу, но вызов метода через него может паниковать. Интерфейс, содержащий типизированный nil-указатель, сам не равен nil. Поэтому проверка интерфейса на nil не доказывает, что его конкретное значение пригодно для вызова.

Главная идея раннего Go: интерфейс описывает операции коллекции

Исходник Markdown ↗

Код главы: example_test.go · historical_test.go.

Элемент не становится «универсальным объектом». Алгоритм просто перестаёт получать его напрямую.

Теперь соединим предыдущие идеи. Замыкание показывало, как работать по индексам; интерфейс — как запросить набор методов. Построим интерфейс операций коллекции и свяжем его с данными адаптером.

Сначала разделим три понятия

Представьте, что мы пишем Find для библиотеки. Дроби принадлежат вызывающему коду. Библиотеке нужно обходить их, проверять условие и останавливаться на первом совпадении. Как договориться о взаимодействии?

ПонятиеВ нашем примереЕго роль
Интерфейсalgorithms.PredicateОбъявляет, какие операции нужны Find
АдаптерfractionQueryРеализует эти операции над конкретными дробями
Алгоритмalgorithms.FindИспользует операции, чтобы организовать поиск

Интерфейс — описание требований. Адаптер — конкретный код, который выполняет эти требования с помощью имеющихся данных. Слово «адаптер» обозначает роль типа в программе. Особого ключевого слова adapter в Go нет.

Интерфейс сам не хранит наш срез, не содержит тела поиска и не добавляет методы существующим значениям. Когда мы передаём адаптер как интерфейсный аргумент, алгоритм получает доступ к операциям этого конкретного адаптера.

Выведем интерфейс из тела поиска

Чтобы написать цикл, нужны две вещи: число элементов и проверка элемента по позиции. Отсюда возникает контракт:

Go Исходник ↗
type Predicate interface {
    Len() int
    Match(i int) (bool, error)
}

Здесь нет метода Get, возвращающего элемент. Find возвращает индекс и поэтому способен обойтись без получения самой дроби. Вопрос «какой тип имеет элемент?» заменён вопросом «подходит ли элемент на этой позиции?».

Так мы не просто прячем длинное имя типа: мы выбираем границу ответственности. Алгоритм отвечает за обход и раннюю остановку. Код, реализующий Match, отвечает за смысл проверки.

Поэтому интерфейс объявлен рядом с потребителем — в algorithms. Автор Find формулирует минимальные требования. Пакету fraction не нужно импортировать algorithms и заранее знать о существовании поиска.

Почему сам срез не подходит

У []fraction.Fraction можно узнать длину встроенной функцией len. Но у него нет метода Len() int. Для интерфейса это разные вещи. Также у среза нет Match: один и тот же набор дробей можно проверять на равенство половине, положительность или другое условие.

Такой вызов не компилируется:

Go Исходник ↗
// values имеет тип []fraction.Fraction.
// Ошибка: у этого типа нет методов Len и Match.
algorithms.Find(values)

Метод Equal у отдельной Fraction не исправляет ситуацию. Он сравнивает два значения. Find же просит длину коллекции и проверку по индексу. Это операции другого уровня.

Нужен тип, который свяжет имеющийся срез с требуемыми методами. В следующей главе им станет fractionQuery: он хранит срез и функцию проверки, а методы Len и Match обращаются к ним.

Почему Go не требует implements

Соответствие интерфейсу определяется набором методов и их сигнатурами. Если у fractionQuery есть нужные Len и Match, значение можно передать в Find. Объявлять наследование или регистрировать адаптер не требуется.

Go Исходник ↗
var _ algorithms.Predicate = fractionQuery{}

Такая строка может находиться в пакете, где определён fractionQuery. Она заставляет компилятор проверить соответствие. При этом методы не вызываются: nil в поле Test не мешает проверке типа, хотя вызов Match с таким полем был бы ошибкой выполнения.

Имена параметров методов значения не имеют. А типы имеют: Match(int) bool не удовлетворяет требованию Match(int) (bool, error).

Это даёт полезное разделение зависимостей:

Схема
Код потребителя
  хранит []Fraction и условие
  определяет fractionQuery
  импортирует fraction и algorithms
            │
            └── передаёт fractionQuery в Find

algorithms знает только Predicate.
fraction знает только правила работы с дробью.

Адаптер находится там, где встретились конкретные данные и конкретная задача. Делать его частью предметного типа не обязательно.

Чему учит исторический sort.Interface

В Go 1 сортировке достаточно трёх операций: длины, сравнения двух позиций и их перестановки. Пусть данные представлены определённым срезовым типом:

Go Исходник ↗
type boxesByValue []boxint.BoxInt

func (s boxesByValue) Len() int { return len(s) }
func (s boxesByValue) Less(i, j int) bool {
    return s[i].Value < s[j].Value
}
func (s boxesByValue) Swap(i, j int) {
    s[i], s[j] = s[j], s[i]
}

// import "sort"
// sort.Sort(boxesByValue(values))

Вызов работает потому, что boxesByValue имеет нужные методы. Не потому, что каждый BoxInt реализует sort.Interface: у отдельного числа нет длины коллекции и перестановки двух её позиций.

Это разделение двух уровней — ключ к раннему обобщению. Значение умеет сравниваться с таким же значением. Адаптер коллекции переводит запрос алгоритма «сравни позиции i и j» в обращение к этим значениям.

В историческом API используются Less и Swap; изучать этот подход можно по исходнику sort из Go 1. Наша библиотека сохраняет идею, но расширяет сравнение возвратом ошибки.

Реальные интерфейсы нашего пакета

Go Исходник ↗
type Ordered interface {
    Len() int
    Compare(i, j int) (int, error)
}

type Sortable interface {
    Ordered
    Swap(i, j int)
}

Для Min/Max нужна только Ordered. Для Sort требуется также Swap. Алгоритм поиска не должен требовать возможности переставлять элементы, если сам её не использует.

Встраивание Ordered в Sortable объединяет требования к методам. Это не наследование реализации и не добавление полей в структуру.

Как методы BoxInt становятся операциями адаптера

Go Исходник ↗
type boxes []boxint.BoxInt

func (s boxes) Len() int { return len(s) }
func (s boxes) Compare(i, j int) (int, error) {
    return s[i].Compare(s[j])
}
func (s boxes) Swap(i, j int) { s[i], s[j] = s[j], s[i] }

var _ algorithms.Sortable = boxes(nil)

boxes.Compare принимает индексы. Внутри он вызывает BoxInt.Compare, который принимает BoxInt. Сигнатуры намеренно различаются: адаптер соединяет интерфейс обхода с конкретной операцией значения.

Строка var _ ... проверяет реализацию интерфейса при компиляции. Она не вызывает алгоритм и не делает данные автоматически отсортированными. boxes(nil) — допустимый пустой срез; его Len возвращает 0.

Сам алгоритм не импортирует boxint. Чтобы добавить дроби, достаточно другого срезового адаптера с теми же Len/Compare/Swap, вызывающего Fraction.Compare. Код сортировки останется прежним.

Почему совпадение Add у значений не решало эту задачу

Предположим, у Money и Fraction одинаково названы Add, Compare и String. Всё равно Compare у первого принимает Money, у второго — Fraction. Это не одна конкретная сигнатура.

А у двух коллекционных адаптеров Compare(int, int) (int, error) действительно совпадает. Неизвестный тип элемента выведен за границу алгоритма. Мы выиграли общий цикл, заплатив необходимостью писать адаптеры для разных коллекций.

Именно эту цену — небольшое, но повторяемое описание одинаковых операций над разными типами — позднее обсуждали как один из мотивов параметров типов. См. Why Generics?.

Find, All и Any: один цикл для разных предметных условий

Исходник Markdown ↗

Код главы: algorithms.go · example_test.go · algorithms_test.go.

Прочитаем реальную реализацию algorithms по шагам: где находятся данные, предикат и знание типа.

Протокол коллекции уже выбран. Теперь прочитаем законченный поиск: сначала цикл, затем адаптер, затем вызов и трассу. All и Any используют тот же договор, но по-разному останавливаются.

Минимальный протокол

Go Исходник ↗
type Predicate interface {
    Len() int
    Match(i int) (bool, error)
}

Predicate здесь означает коллекцию вместе с условием проверки. Название описывает её роль для алгоритма; это не функция, которая принимает неизвестный элемент. Мы сознательно объединили длину и условие в одном значении адаптера.

Исходник: algorithms.go. Внешний контракт Find возвращает первый индекс, а не копию найденного объекта. Это позволяет не возвращать значение неизвестного типа.

Алгоритм Find целиком

Go Исходник ↗
func Find(data Predicate) (int, error) {
	n := data.Len()
	for i := 0; i < n; i++ {
		matched, err := data.Match(i)
		if err != nil {
			return -1, err
		}
		if matched {
			return i, nil
		}
	}
	return -1, nil
}

Проследим информацию в теле. Есть n и i типа int, matched типа bool и err типа error. Ни Fraction, ни Money, ни BoxInt там нет. Но найденный индекс можно использовать в исходном типизированном срезе вызывающего.

Сначала проверяется ошибка, затем matched. Нельзя трактовать пару (true, err) как успешное совпадение: операция уже сообщила, что результат недостоверен.

Адаптер знает Fraction

Go Исходник ↗
type fractionQuery struct {
    Values []fraction.Fraction
    Test   func(fraction.Fraction) (bool, error)
}

func (q fractionQuery) Len() int { return len(q.Values) }
func (q fractionQuery) Match(i int) (bool, error) {
    return q.Test(q.Values[i])
}

Test получает конкретную Fraction и может вызывать её методы. Предикат не обязан быть одинаковым у всех запросов: поле-функция позволяет менять условие без нового типа адаптера.

Прочитаем fractionQuery буквально

В структуре два поля. Values хранит срез конкретных дробей. Test хранит функцию, которая принимает одну дробь и возвращает ответ вместе с возможной ошибкой. Тела функции в объявлении структуры нет: вызывающий передаст её при создании запроса.

Метод Len переводит запрос алгоритма «дай количество элементов» в обычный len(q.Values).

Метод Match состоит из трёх действий. Его можно переписать более многословно, не меняя смысла:

Go Исходник ↗
func (q fractionQuery) Match(i int) (bool, error) {
    value := q.Values[i]           // Получаем конкретную Fraction.
    matched, err := q.Test(value)  // Вызываем сохранённую функцию.
    return matched, err           // Возвращаем ответ алгоритму.
}

Это альтернативная запись того же метода; добавлять обе версии в один пакет нельзя.

Обратите внимание: Match не содержит цикла и не выбирает следующий индекс. Адаптер обслуживает один запрос. Цикл остаётся внутри Find.

Как читать полный сценарий

В ExampleFind ниже сначала создаётся срез, затем функция isHalf, затем query с именованными полями. Только после этого вызывается Find. Читайте эти четыре шага отдельно: так видно, что условие относится к дроби, а цикл работает с индексами.

Что происходит при передаче в интерфейс

Параметр data внутри Find имеет статический тип Predicate. В приведённом вызове передано значение конкретного типа fractionQuery. Упрощённо интерфейсное значение можно понимать как сочетание конкретного типа и значения этого типа.

Схема
Find: data имеет статический тип Predicate
  конкретное значение: fractionQuery
    Values → срез дробей
    Test   → функция isHalf

data.Match(1)
  → метод fractionQuery.Match с получателем query
  → query.Values[1], то есть дробь 2/4
  → query.Test(эта дробь)
  → isHalf(эта дробь)
  → true, nil

Вызов метода интерфейса направляется к реализации конкретного значения. Find не пишет type switch и не выясняет, дроби перед ним или деньги. Его тело может использовать только операции, доступные через объявленный тип параметра: обратиться к data.Values или data.Test нельзя, потому что этих полей нет в контракте Predicate.

При передаче query по значению копируется значение структуры, включая описание среза. Элементы среза при этом не клонируются: исходный values и поле Values ссылаются на один базовый массив. Это не создание []interface{} и не упаковка каждой дроби отдельно. Нужна ли для интерфейсного значения аллокация в куче, зависит от компилятора и контекста использования; сама схема этого не обещает.

Зачем структура, если есть замыкание

Для этого же поиска можно использовать FindIndex из предыдущей главы:

index, err := FindIndex(len(values), func(i int) (bool, error) {
    return isHalf(values[i])

Замыкание делает ту же работу, что Match: связывает индекс с конкретным значением. Для простого Find отдельный адаптер не обязателен. Он нужен именно потому, что наш выбранный API принимает Predicate.

Адаптер собирает операции в один объект, который можно передать в Find, All и Any. Это полезно для повторного использования одного запроса и особенно для протоколов с несколькими операциями, как Len, Compare и Swap. Но компилятор всё равно не доказывает, что методы обращаются к одному и тому же срезу: это ответственность реализации.

В простом локальном поиске замыкание часто понятнее. Не нужно создавать структуру ради самого слова «интерфейс». Сначала выбирают, какие данные и операции должны пересекать границу библиотеки, затем — удобную форму API.

Полный исполняемый вариант без структуры-адаптера вынесен отдельно: код и объяснение, два примера вызова.

Что адаптер не делает за нас

fractionQuery не проверяет границы индекса, не исправляет дроби и не создаёт функцию Test автоматически. Если Test равен nil, вызов Match паникует. Если индекс выходит за пределы Values, индексирование паникует. Наш Find вычисляет индексы по Len; адаптер и callback должны сохранять согласованность коллекции во время обхода.

Методы здесь используют получатель по значению, поскольку им не нужно заменять поля query. Поэтому интерфейсу удовлетворяют и fractionQuery, и *fractionQuery. Для moneySum в следующей главе потребуется изменять поле Total, и там получатель будет указателем.

Проверяемый пример из example_test.go:

Go Исходник ↗
func ExampleFind() {
	// 1. Данные и условие поиска.
	values := []fraction.Fraction{
		{Numerator: 1, Denominator: 3},
		{Numerator: 2, Denominator: 4},
		{Numerator: 3, Denominator: 4},
	}
	half := fraction.Fraction{Numerator: 1, Denominator: 2}
	isHalf := func(value fraction.Fraction) (bool, error) {
		if err := value.Validate(); err != nil {
			return false, err
		}
		return value.Equal(half), nil
	}

	// 2. Адаптер связывает срез и условие с методами Len и Match.
	query := fractionQuery{Values: values, Test: isHalf}

	// 3. Алгоритм видит только интерфейс адаптера.
	index, err := algorithms.Find(query)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	if index == -1 {
		fmt.Println("Совпадений нет")
		return
	}

	// 4. Найденное значение берём из исходного типизированного среза.
	fmt.Println("Индекс:", index)
	fmt.Println("Дробь:", values[index])

	// Индекс: 1
	// Дробь: 1/2
}

Ожидаемый индекс — 1, потому что элемент 2/4 математически равен 1/2. Поиск ничего не знает о сокращении дробей: это знание остаётся в Fraction.Equal.

Здесь target заведомо корректен по литералу, а каждый посещённый элемент проходит Validate. Если target приходит извне, его тоже нужно проверить перед поиском: сама Equal для невалидных значений возвращает false, а не error.

Трасса одного вызова

Схема
Find(query)
  → query.Len() = 3
  → query.Match(0)
      → Test(Fraction{1, 3})
      → Equal(1/2) = false
  → query.Match(1)
      → Test(Fraction{2, 4})
      → Equal(1/2) = true
  → return 1, nil

Match(2) уже не вызывается.

Эта трасса показывает два независимых решения: алгоритм управляет остановкой; предикат выбирает смысл совпадения.

All использует тот же интерфейс

Go Исходник ↗
func All(data Predicate) (bool, error) {
	n := data.Len()
	for i := 0; i < n; i++ {
		matched, err := data.Match(i)
		if err != nil {
			return false, err
		}
		if !matched {
			return false, nil
		}
	}
	return true, nil
}

Для пустой коллекции цикл не выполняется, результат true. Это договор «нет элемента, опровергающего условие». При первом false работа прекращается; callback после этого не вызываются.

Go Исходник ↗
func ExampleAll() {
	values := []fraction.Fraction{
		{Numerator: 1, Denominator: 3},
		{Numerator: 2, Denominator: 4},
	}
	zero := fraction.Fraction{Denominator: 1}
	isPositive := func(value fraction.Fraction) (bool, error) {
		comparison, err := value.Compare(zero)
		return comparison > 0, err
	}
	query := fractionQuery{Values: values, Test: isPositive}

	positive, err := algorithms.All(query)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	fmt.Println("Все положительные:", positive)
	// Output: Все положительные: true
}

Мы использовали Compare с корректной дробью 0/1. Сам All не требует, чтобы у элементов был Compare: вместо него Test мог бы проверять формат строки, доступность ресурса или другое условие.

Any выражается через Find

Go Исходник ↗
func Any(data Predicate) (bool, error) {
	index, err := Find(data)
	return index >= 0, err
}

Тут переиспользуется уже не только протокол коллекции, но и готовый алгоритм. Пустой вход даёт false, первое совпадение завершает работу. При ошибке Find возвращает -1, поэтому Any возвращает false вместе с той же ошибкой.

Добавляем другой тип без изменения algorithms

Для Money можно написать moneyQuery с Values []money.Money и Test func(money.Money) (bool, error). Методы Len и Match будут почти такими же. После этого тот же Find найдёт сумму нужной валюты, а All проверит, что все суммы неотрицательны.

Компилятор проверит конкретный callback внутри moneyQuery. Цена подхода — повторение небольшого адаптера. Мы не избавились от всех различий типов; мы локализовали их вне библиотечного обхода.

Map и Sum: где в раннем Go хранился типизированный результат

Исходник Markdown ↗

Код главы: example_test.go · algorithms_test.go.

Поиск смог вернуть int. Преобразование и сумма должны сохранить конкретное значение — поэтому адаптер становится важнее.

Поиск возвращал индекс, поэтому тип результата не был проблемой. Map должен получить строки, а Sum — новую денежную сумму. Разберём, кто создаёт и хранит эти результаты, если общий алгоритм не знает их типов.

Map не может угадать []R

Наша публичная сигнатура Map(data Mapping) error не обещает вернуть произвольный срез. Она просит объект, который умеет преобразовать элемент и записать результат:

Go Исходник ↗
type Mapping interface {
    Len() int
    Apply(i int) error
}
Go Исходник ↗
func Map(data Mapping) error {
	n := data.Len()
	for i := 0; i < n; i++ {
		if err := data.Apply(i); err != nil {
			return err
		}
	}
	return nil
}

Тип результата не исчез из программы. Он просто отсутствует в сигнатуре общего алгоритма и хранится у вызывающего. Вот конкретный адаптер для Fraction → string:

Go Исходник ↗
type fractionText struct {
    Source    []fraction.Fraction
    Target    []string
    Transform func(fraction.Fraction) (string, error)
}

func (m fractionText) Len() int { return len(m.Source) }
func (m fractionText) Apply(i int) error {
    text, err := m.Transform(m.Source[i])
    if err != nil {
        return err
    }
    m.Target[i] = text
    return nil
}

Связь Fraction → string явно типизирована внутри адаптера. Неправильный callback func(Money) (string, error) не подходит полю Transform. Но для связи Money → string потребуется новый адаптер.

Полный вызов и расположение результата

Go Исходник ↗
func ExampleMap() {
	values := []fraction.Fraction{
		{Numerator: 2, Denominator: 4},
		{Numerator: 6, Denominator: 3},
	}
	texts := make([]string, len(values))
	toText := func(value fraction.Fraction) (string, error) {
		if err := value.Validate(); err != nil {
			return "", err
		}
		return value.String(), nil
	}
	job := fractionText{Source: values, Target: texts, Transform: toText}

	err := algorithms.Map(job)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	// Результат записан в texts через адаптер.
	fmt.Println("Строки:", texts)
	// Output: Строки: [1/2 2]
}

Этот код берётся из исполняемого примера. texts создан до Map, остаётся []string после Map и не требует assertion. При nil-источнике сохраняем nil-результат; этот выбор сделал вызывающий, а не общий цикл.

Почему Apply имеет получателя по значению и всё же меняет texts? Адаптер содержит заголовок среза. Копия заголовка продолжает ссылаться на тот же backing array; присваивание Target[i] меняет общий элемент. Но переназначение самого поля Target внутри такой копии не изменило бы заголовок texts у вызывающего. Это принципиальное различие при проектировании адаптеров.

Наша реализация сначала вычисляет строку, проверяет ошибку и лишь потом записывает её. При ошибке на втором элементе первая строка остаётся записанной, второй и последующие слоты не меняются. Алгоритм не умеет откатить произвольные действия Apply.

Sum: неизвестен не только элемент, но и ноль

У BoxInt корректный ноль — нулевая структура. У Fraction нулевая структура невалидна: нужен знаменатель 1. У Money нулю нужна валюта. Поэтому общий Sum не может просто создать «нулевое значение какого-то типа» и считать вопрос решённым.

Go Исходник ↗
type Summable interface {
    Len() int
    Add(i int) error
}
Go Исходник ↗
func Sum(data Summable) error {
	n := data.Len()
	for i := 0; i < n; i++ {
		if err := data.Add(i); err != nil {
			return err
		}
	}
	return nil
}

Начальное значение и текущее состояние суммы находятся в адаптере:

Go Исходник ↗
type moneySum struct {
    Values []money.Money
    Total  money.Money
}

func (s *moneySum) Len() int { return len(s.Values) }
func (s *moneySum) Add(i int) error {
    next, err := s.Total.Add(s.Values[i])
    if err != nil {
        return err
    }
    s.Total = next
    return nil
}

Здесь два разных Add. Метод адаптера принимает индекс; метод Money принимает Money. Адаптер переводит один протокол в другой и обновляет аккумулятор только после успешной операции.

Почему получатель — указатель

Total является значением структуры. Если метод адаптера получал бы копию moneySum и присваивал её полю Total, вызывающий не увидел бы нового аккумулятора. Поэтому изменяющий состояние метод определён у *moneySum, и в Sum передают &sum.

Go Исходник ↗
var _ algorithms.Summable = (*moneySum)(nil)
// moneySum{} не реализует Summable: нужные методы имеют pointer receiver.

Это не поздняя сложность дженериков: method sets и видимость изменения состояния нужно понимать уже для раннего интерфейсного решения.

Полный денежный пример

Go Исходник ↗
func ExampleSum() {
	values := []money.Money{
		{Amount: 100, Currency: "USD"},
		{Amount: 250, Currency: "USD"},
	}
	initial := money.Money{Currency: "USD"} // Нулевая сумма с заданной валютой.
	sum := moneySum{Values: values, Total: initial}

	// Указатель позволяет адаптеру изменять своё поле Total.
	err := algorithms.Sum(&sum)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	fmt.Println("Сумма:", sum.Total)
	// Output: Сумма: 350 USD (minor units)
}

Если заменить вторую сумму на EUR, вызов вернёт ошибку несовместимой валюты. Total уже содержит первый успешно обработанный элемент; следующие элементы не посещаются. Если вход пуст, Total остаётся исходным. При повторном независимом вызове Sum адаптер нужно инициализировать заново — иначе он продолжит складывать с текущим Total.

Для дробей реализация fractionSum аналогична, но аккумулятор Fraction начинается с 0/1. Один и тот же Sum проверен с обоими типами в algorithms_test.go.

Что выиграли и чего не смогли выразить

Общие Map и Sum не знают конкретных типов и не используют reflection. Результаты сохраняют конкретный тип. Но связь входа и результата, их создание и часть служебного кода приходится повторять в адаптерах.

Это и есть содержательная граница ранней модели. Она позволяла обобщать алгоритм через операции, но не позволяла объявить один Map с произвольными связанными типами входа и выхода. Следующие механизмы будем оценивать по тому, как они перемещают именно эту границу.

Min, Max, Sort и границы обещаний ранней библиотеки

Исходник Markdown ↗

Код главы: algorithms.go · algorithms_test.go.

Закончим первую библиотеку и проверим её договор: интерфейс делает алгоритм общим, но не делает ошибки и предметные ограничения невозможными.

Для поиска хватало проверки одной позиции. Минимум и сортировка требуют сравнения двух позиций, а сортировка — ещё и перестановки. Расширим договор ровно этими операциями и проверим его границы.

Экстремум без возвращения неизвестного значения

Go Исходник ↗
func Min(data Ordered) (int, error) {
	n := data.Len()
	if n == 0 {
		return -1, nil
	}
	best := 0
	for i := 1; i < n; i++ {
		comparison, err := data.Compare(i, best)
		if err != nil {
			return -1, err
		}
		if comparison < 0 {
			best = i
		}
	}
	return best, nil
}

У Min тот же удачный выход, что у Find: индекс. Тип значения остаётся у вызывающего, который обращается к исходному срезу. При равенстве лучший индекс не меняется — возвращается первое минимальное значение.

Max устроен симметрично: кандидат заменяет лучший индекс, если Compare дал положительный результат. Обе функции возвращают -1 для пустой коллекции и при ошибке сравнения; наличие ошибки отличает эти случаи.

Go Исходник ↗
func ExampleMin() {
	values := []boxint.BoxInt{{Value: 3}, {Value: 1}, {Value: 2}, {Value: 1}}
	collection := boxes(values)

	index, err := algorithms.Min(collection)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	if index == -1 {
		fmt.Println("Коллекция пуста")
		return
	}
	fmt.Println("Индекс:", index)
	fmt.Println("Минимум", values[index])
	// Output:
	// Индекс: 1
	// Минимум 1
}

Это учебный пример с известным непустым входом. В общем коде нужно проверить err и index >= 0 до доступа values[index]. Индекс -1 нельзя безусловно использовать для обращения к срезу.

От Ordered к Sortable

Для поиска экстремума достаточно сравнений. Для сортировки добавляется Swap. Реальная реализация нашего пакета намеренно короткая: стабильные вставки.

Go Исходник ↗
func Sort(data Sortable) error {
	n := data.Len()
	for i := 1; i < n; i++ {
		for j := i; j > 0; j-- {
			comparison, err := data.Compare(j, j-1)
			if err != nil {
				return err
			}
			if comparison >= 0 {
				break
			}
			data.Swap(j, j-1)
		}
	}
	return nil
}

Для входа 3, 1, 2 последовательность действий такова:

Схема
i = 1: Compare(1, 0) < 0 → Swap(1, 0) → 1, 3, 2
i = 2: Compare(2, 1) < 0 → Swap(2, 1) → 1, 2, 3
       Compare(1, 0) > 0 → остановить внутренний цикл

Равные элементы не переставляются, поскольку при Compare >= 0 внутренний цикл прекращается. Так сохраняется их относительный порядок. Худшая сложность — O(n²), дополнительная память — O(1).

Это не утверждение, что стандартная сортировка раннего Go целиком была таким циклом. Из раннего Go мы взяли способ связать алгоритм с коллекцией через интерфейс. Собственный алгоритм вставок выбран для чтения и объяснения. Стандартный API также отличался: Less не возвращал error, а наш Compare возвращает.

Пустые коллекции и нулевые значения

All пустой коллекции возвращает true, Any — false. Map пустой коллекции ничего не записывает. Sum не создаёт и не проверяет новое начальное значение — оставляет существующий аккумулятор. Sort не сравнивает пустую и одноэлементную коллекции. Min для единственного элемента возвращает индекс 0, не вызывая Compare.

Поэтому невалидная единственная Fraction может пройти через Min без ошибки, если адаптер не выполнил предварительную проверку. Общий контракт Ordered обещает сравнение, а не валидацию каждого элемента. Это ограничение нужно понимать, а не прятать за словом «типобезопасный».

В тестах algorithms проверяется порядок посещённых индексов, короткое замыкание, передача ошибки, первый экстремум при равных значениях, стабильность сортировки и сохранение частичного результата. Примеры проверяют конкретный вывод для Fraction, Money и BoxInt.

Итог первой эпохи: обобщение уже работает

Один algorithms обслуживает разные предметные типы. Ни один цикл не знает поля дроби или валюты. Конкретные значения и результаты сохраняют типы внутри адаптеров. Автоматического наследования методов или операторов не понадобилось.

Но добавление нового типа требует новых адаптеров. Сложные отношения вроде []E + func(E) R → []R описываются косвенно, через конкретные структуры с полями. Именно это оставшееся повторение и отсутствие общей связанной сигнатуры создают мотивацию изучать interface{}, reflection, генерацию и позже параметры типов.

interface{}: один контейнер, потерянные статические связи

Исходник Markdown ↗

Код главы: algorithms.go · example_test.go · algorithms_test.go.

Принять значение любого типа и сохранить связь между произвольными типами — разные требования.

До сих пор элементы оставались у вызывающего. Теперь попробуем передать их внутрь общей функции как интерфейсные значения. Это альтернативное решение той же задачи в раннем Go, а не новый релиз языка.

Убираем адаптеры с методами

В ранней библиотеке из первой части конкретные типы сохранились внутри fractionQuery, fractionText и moneySum. Теперь исследуем альтернативу: вынести элементы в общий интерфейсный контейнер. Это решение тоже было доступно до дженериков, а не появилось после очередного обновления языка.

Для следующих сравнений возьмём User: у него есть Name, Age и Active. Поиск проверяет совершеннолетие, All — активность, Map получает имена. Полные вызовы находятся в examples/example_test.go. Их callback не возвращают error; это упрощённая модель для демонстрации статических типов. Перенося такой подход на наши Fraction и Money, нельзя убрать ошибки Validate/Add: понадобится callback с error и передача ошибки наружу, как в algorithms. Простая замена на interface{} не решает этот вопрос.

Если все элементы заранее упаковать в interface{}, получится одна сигнатура для разных данных. В этой главе используем историческое написание; с Go 1.18 any является алиасом того же типа.

Go Исходник ↗
func FindAny(src []interface{}, pred func(interface{}) bool) int {
	for i, item := range src {
		if pred(item) {
			return i
		}
	}
	return -1
}
Go Исходник ↗
func AllAny(src []interface{}, pred func(interface{}) bool) bool {
	for _, item := range src {
		if !pred(item) {
			return false
		}
	}
	return true
}
Go Исходник ↗
func MapAny(src []interface{}, transform func(interface{}) interface{}) []interface{} {
	if src == nil {
		return nil
	}
	out := make([]interface{}, len(src))
	for i, item := range src {
		out[i] = transform(item)
	}
	return out
}

Алгоритмы действительно общие. Но MapAny на этапе компиляции возвращает только []interface{}. То, что внутри оказались исключительно строки, не меняет этот статический тип.

Цена на границе вызова

Go Исходник ↗
var boxed []interface{}
if users != nil {
    boxed = make([]interface{}, len(users))
}
for i, user := range users {
    boxed[i] = user
}

index := FindAny(boxed, func(x interface{}) bool {
    return x.(User).Age >= 18
})
all := AllAny(boxed, func(x interface{}) bool {
    return x.(User).Active
})
raw := MapAny(boxed, func(x interface{}) interface{} {
    return x.(User).Name
})

var names []string
if raw != nil {
    names = make([]string, len(raw))
}
for i, item := range raw {
    names[i] = item.(string)
}

Нельзя просто передать []User как []interface{}. И нельзя присвоить func(User) string переменной типа func(interface{}) interface{}. В первом случае нужен новый срез с поэлементным присваиванием, во втором — функция-обёртка.

Отсутствие ковариантности у срезов важно и семантически: если бы общий изменяемый []User можно было использовать как []interface{}, через него можно было бы попытаться записать строку в хранилище пользователей. Для преобразования срезов Go требует явного цикла. Источник: Go FAQ.

Что увидит компилятор

В FindAny нет декларации «callback ожидает тот же конкретный тип, который лежит в исходном срезе». Он получает interface{} и возвращает bool — это весь статический контракт. Поэтому такой вызов компилируется:

Go Исходник ↗
FindAny([]interface{}{User{Name: "Аня"}}, func(x interface{}) bool {
    return len(x.(string)) > 0 // panic при обработке User
})

Можно заменить assertion на value, ok := x.(User). Но затем нужно решить, что делать при несовпадении: пропустить элемент, вернуть ошибку, завершить поиск? Мы вынуждены добавлять в контракт ситуации, которых у конкретной типизированной функции не было.

Ещё опаснее проверка через ==: сравнение двух интерфейсных значений может вызвать panic, если их динамические значения несравнимы. interface{} не означает «любой оператор допустим».

Данные не теряют runtime-тип

Упаковка User в интерфейс не стирает сведения о нём из runtime. Иначе assertion был бы невозможен. Потеря происходит в статическом контракте: компилятор вызывающего кода больше не выводит []string из MapAny.

Поэтому выражение «type erasure» здесь следует использовать осторожно: это не буквальное отсутствие информации о типе во время исполнения. Для нашего сравнения точнее говорить о потере статической связи между типами аргументов и результата.

Когда это полезная модель

Если данные по смыслу разнородны — например, набор произвольных значений для форматирования — []interface{} отражает задачу. Проблема возникает, когда однородную []User вынуждают пройти через этот формат только ради общего цикла.

В приведённом адаптере появляются дополнительные контейнеры и обходы для упаковки и извлечения. Это конкретное свойство этой реализации. Утверждать, что каждое интерфейсное значение обязательно создаёт отдельную heap-аллокацию, нельзя: размещение зависит от компилятора и контекста.

Переход к reflection

Следующий вопрос: можно ли принять исходный []User и исходный func(User) string без ручной упаковки, а совместимость выяснить внутри библиотеки? Для этого нужно уметь исследовать типы и вызывать функцию во время исполнения.

Reflection: универсальность с проверкой при исполнении

Исходник Markdown ↗

Код главы: reflection.go · example_test.go.

Reflection переносит часть работы с типами внутрь библиотеки, но выполняет её над runtime-описаниями значений.

Пустой интерфейс позволил принять разные значения, но не связал тип callback с типом элемента. Reflection позволяет проверить эту связь во время выполнения. Посмотрим, какие проверки для этого действительно нужны.

Меняем границу API

В первой части algorithms получал явно заданные операции адаптера. Здесь библиотека сама исследует переданное значение и функцию. Это альтернативный путь, доступный уже в раннем Go; он не означает, что интерфейсы перестали использоваться. Для сравнения ниже оставлены реализации из модуля examples над User.

Проверка формы через reflect не заменяет предметную валидацию: корректный тип Fraction может содержать нулевой знаменатель, а два Money — разные валюты. Такие ошибки должны проверять сами операции. Наличие нужной сигнатуры callback ещё не делает его безопасным для любого содержимого.

Вместо []interface{} примем весь исходный срез в одном интерфейсном значении. Отдельно примем исходную функцию:

Go Исходник ↗
index, err := FindReflect(users, adult)
all, err := AllReflect(users, active)
raw, err := MapReflect(users, name)
// Каждый err нужно проверить до использования результата.

При упаковке среза целиком мы не создаём срез интерфейсных элементов. Его динамический тип остаётся []User. Но тип src interface{} сам по себе не обещает даже того, что пришёл срез: можно передать число. Обещания должна проверить реализация.

Валидация является частью алгоритма

Наша библиотека допускает только неvariadic-функцию с одним входом и одним выходом. Тип входа должен точно совпадать с типом элемента среза. Для Find и All результат должен быть ровно bool.

Go Исходник ↗
func checkTransform(src, fn interface{}) (reflect.Value, reflect.Value, error) {
	s, f := reflect.ValueOf(src), reflect.ValueOf(fn)
	if !s.IsValid() || s.Kind() != reflect.Slice {
		return s, f, fmt.Errorf("source must be a slice")
	}
	if !f.IsValid() || f.Kind() != reflect.Func || f.IsNil() {
		return s, f, fmt.Errorf("callback must be a non-nil function")
	}
	t := f.Type()
	if t.IsVariadic() || t.NumIn() != 1 || t.NumOut() != 1 || t.In(0) != s.Type().Elem() {
		return s, f, fmt.Errorf("callback must have signature func(%v) R", s.Type().Elem())
	}
	return s, f, nil
}

Этот контракт сознательно уже, чем все возможности reflect.Value.Call: мы не используем присваиваемость к интерфейсному параметру и не делаем автоматических конверсий. Например, для []User функция func(interface{}) string будет отвергнута. Так проще увидеть и проверить отношение типов.

Typed nil-срез является корректным пустым входом. Нетипизированный nil, не-срез, nil-функция, неправильное число аргументов и несовпадение типов возвращают ошибку. Проверка выполняется даже для пустого среза: неверную сигнатуру нельзя маскировать отсутствием элементов. Все проверки находятся в reflection.go.

Find и All

Go Исходник ↗
func FindReflect(src, pred interface{}) (int, error) {
	s, f, err := checkPredicate(src, pred)
	if err != nil {
		return -1, err
	}
	for i := 0; i < s.Len(); i++ {
		if f.Call([]reflect.Value{s.Index(i)})[0].Bool() {
			return i, nil
		}
	}
	return -1, nil
}
Go Исходник ↗
func AllReflect(src, pred interface{}) (bool, error) {
	s, f, err := checkPredicate(src, pred)
	if err != nil {
		return false, err
	}
	for i := 0; i < s.Len(); i++ {
		if !f.Call([]reflect.Value{s.Index(i)})[0].Bool() {
			return false, nil
		}
	}
	return true, nil
}

После проверки каждый элемент передаётся через reflect.Value, результат читается как bool. Ранняя остановка сохранена. Но ошибка func(Order) bool для []User обнаруживается при вызове, а не при компиляции программы.

Map может построить настоящий []R

Go Исходник ↗
func MapReflect(src, transform interface{}) (interface{}, error) {
	s, f, err := checkTransform(src, transform)
	if err != nil {
		return nil, err
	}
	target := reflect.SliceOf(f.Type().Out(0))
	if s.IsNil() {
		return reflect.Zero(target).Interface(), nil
	}
	out := reflect.MakeSlice(target, s.Len(), s.Len())
	for i := 0; i < s.Len(); i++ {
		out.Index(i).Set(f.Call([]reflect.Value{s.Index(i)})[0])
	}
	return out.Interface(), nil
}

Из типа возвращаемого значения callback библиотека строит тип []R, создаёт срез и заполняет его. Для func(User) string динамический тип результата действительно будет []string, а не []interface{}.

Go Исходник ↗
raw, err := MapReflect(users, name)
if err != nil {
    // Обработать несовместимый вызов.
    return
}
names, ok := raw.([]string)
if !ok {
    // Нарушено ожидание вызывающего кода о типе результата.
    return
}

Статический тип raw по-прежнему interface{}. Связь между callback и результатом существует в реализации, но не выражена сигнатурой Go. На границе вызывающего кода снова нужна проверка.

Если исходный срез nil, возвращается интерфейс, содержащий nil-срез целевого типа. Поэтому raw == nil в успешном таком вызове ложно, а raw.([]string) == nil истинно. Прежняя справочная глава о typed nil объясняет механизм, а здесь видно его влияние на дизайн API.

Граница между ошибкой API и panic пользователя

Валидация гарантирует допустимую форму вызова. Она не гарантирует, что name не паникует, не делит на ноль и не обращается к закрытому ресурсу. В нашей реализации panic callback распространяется наружу, как в остальных вариантах. Автоматически восстанавливать его и выдавать как «ошибку типа» было бы изменением контракта.

Цена реализации включает проверки метаданных, упаковку аргументов вызова и reflect.Call на каждом обработанном элементе. Количественный вывод требует измерения. Нельзя переносить результат такого поэлементного reflection-алгоритма на любой код, который использует reflect один раз при настройке. API и ограничения: reflect, модель интерфейсного значения: The Laws of Reflection.

Где reflection сохраняет свою роль

Когда типы приходят из данных во время исполнения — например, при обходе полей произвольной структуры и чтении тегов — compile-time-параметр E не заменяет исследование структуры. Для однородного Map с известными в исходном коде типами мы платим за динамику, которая не была требованием задачи.

Генерация кода: специализация до компиляции

Исходник Markdown ↗

Можно сохранить конкретные сигнатуры, если повторяющийся код будет писать программа.

Мы попробовали проверять неизвестные типы во время выполнения. Другой путь — ещё до компиляции получить несколько обычных функций из одного шаблона. Разделим время написания алгоритма, генерации и исполнения.

Переносим обобщение в инструмент

После первой части можно сформулировать конкретную цель генерации: не писать вручную похожие адаптеры для Fraction и Money либо сразу выпустить несколько конкретных алгоритмов. Это другой способ организовать повторяющийся исходник, а не новый runtime-механизм. Генерация существовала до команды go generate; историческую дату команды отделяем от возраста самого подхода.

Работающий генератор ниже относится к сохранённому модулю examples: он выпускает специализации User → string и int → string. Он не генерирует нынешние Fraction/Money-адаптеры. Для них сначала пришлось бы определить шаблон с обработкой ошибок, а затем явно добавить нужные специализации.

У конкретного FindUser был удобный типобезопасный API, но повторяющееся тело. Генератор хранит тело один раз в шаблоне, подставляет типы и выпускает обычный Go-код. Компилятор видит уже специализированные функции.

Схема

Историческая роль go generate

Команда go generate появилась в Go 1.4. Она стандартизировала запуск генераторов по директивам, но не изобрела генерацию и не включила её автоматически в go build. Автор пакета запускает её явно; сгенерированные файлы обычно поставляются вместе с библиотекой. Источник: Generating code.

Поэтому неверно рисовать историю как «до Go 1.4 генерации не существовало». Менялась интеграция с инструментами, а сам приём был доступен ранее.

Почему параметры типов всё равно понадобились

Генератор решает повторение исходника, но заставляет поддерживать отдельный язык шаблона, список специализаций и стадию сборки. Потребитель библиотеки не может просто вызвать единственную Map с новым типом и получить проверенный результат без подготовки нового кода.

Следующее требование: сделать типовую параметризацию частью обычной декларации Go. Тогда библиотека сможет публиковать одну проверяемую функцию, а потребитель — выбирать типы при вызове.

Go 1.18: связи типов становятся частью сигнатуры

Исходник Markdown ↗

Код главы: generic.go · example_test.go · example_test.go.

Параметры типов позволяют опубликовать один алгоритм с согласованными типами входа, callback и результата.

Теперь доходим до изменения самого языка: Go 1.18. Параметры типов позволяют записать связь входа и результата в сигнатуре. Сначала сравним простой Find/Map, затем вернём ошибки и начальное значение нашей суммы.

Find и All: тип известен, но произволен

Первая часть закончилась работающей библиотекой algorithms: общего обхода удалось добиться через адаптеры, а типы результатов остались у вызывающего. Параметры типов позволяют выразить некоторые из этих связей прямо в сигнатуре. Сначала рассмотрим сохранённые упрощённые функции из examples над User; затем вернёмся к контрактам ошибок Fraction и Money.

Go Исходник ↗
func Find[E any](src []E, pred func(E) bool) int {
	for i, item := range src {
		if pred(item) {
			return i
		}
	}
	return -1
}
Go Исходник ↗
func All[E any](src []E, pred func(E) bool) bool {
	for _, item := range src {
		if !pred(item) {
			return false
		}
	}
	return true
}

E — не интерфейсная коробка вокруг каждого элемента. При конкретном вызове он обозначает выбранный тип. Тело алгоритма проверяется с учётом ограничения: при any оно может передавать E в func(E) bool, но не может произвольно складывать значения или читать у них поле Age.

Go Исходник ↗
index := Find(users, adult)
all := All(users, active)
textIndex := Find([]string{"go", "generic"}, func(s string) bool {
    return len(s) > 2
})

Один исходник работает для User, string и новых пользовательских типов. Цикл и условия остановки проверяются в одном месте; предметные предикаты остаются обычными типизированными функциями.

Map: недостающее отношение E → R

Go Исходник ↗
func Map[E, R any](src []E, transform func(E) R) []R {
	if src == nil {
		return nil
	}
	out := make([]R, len(src))
	for i, item := range src {
		out[i] = transform(item)
	}
	return out
}
Go Исходник ↗
names := Map(users, name) // []string
ages := Map(users, func(u User) int { return u.Age }) // []int

// Map(users, func(s string) int { return len(s) })
// Ошибка компиляции: []User и параметр string не согласованы.

Компилятор связывает E с элементом первого аргумента и входом callback; R — с выходом callback и элементом результата. Теперь то, что reflection проверял при исполнении, выражено на границе функции.

Для []User и func(User) string никакие преобразования User → interface{} и interface{} → string не требуются. Вывод аргументов типов сокращает запись, но не меняет смысл: можно написать Map[User, string](users, name) явно.

any в ограничении и any как тип значения

Сравните:

Схема
MapAny([]interface{}, func(interface{}) interface{}) []interface{}
Map[E, R any]([]E, func(E) R) []R

В первой сигнатуре один и тот же интерфейсный тип принимает значения разных динамических типов. Во второй any ограничивает допустимые аргументы типов, а E и R сохраняют конкретные выбранные типы в сигнатуре.

Вызов Map[any, any] возможен и будет работать с интерфейсными элементами. Дженерики не запрещают динамику; они позволяют не вводить её туда, где нужна типизированная однородная коллекция.

Дженерики не заменили интерфейсы

Продолжение нашей ранней библиотеки с сохранением ошибок

Для Sum теперь можно потребовать метод сложения с тем же типом. Следующий код реализован в lessons/generic и продолжает API с сохранением ошибок:

Go Исходник ↗
type Addable[T any] interface {
    Add(T) (T, error)
}

func SumValues[T Addable[T]](values []T, initial T) (T, error) {
    total := initial
    for _, value := range values {
        next, err := total.Add(value)
        if err != nil {
            return total, err
        }
        total = next
    }
    return total, nil
}

Теперь связь с собственным типом присутствует в интерфейсе Addable[T]. Money.Add и Fraction.Add подходят для разных инстанциаций без коллекционного адаптера с Add(index). Но initial по-прежнему задаёт вызывающий: для Money нужна валюта, для Fraction — корректный 0/1. Параметры типов не доказывают, что нулевое значение структуры является нейтральным элементом сложения.

Для Map можно вернуть конкретный []R и одновременно сохранить возврат ошибок:

Go Исходник ↗
func MapValues[E, R any](values []E, transform func(E) (R, error)) ([]R, error) {
    if values == nil {
        return nil, nil
    }
    out := make([]R, len(values))
    for i, value := range values {
        result, err := transform(value)
        if err != nil {
            return out, err
        }
        out[i] = result
    }
    return out, nil
}

Здесь выбран полный буфер результата: при ошибке заполненный префикс сохраняется, оставшийся суффикс содержит нулевые R. Это явное решение API. В раннем Mapping вызывающий сам выбирал хранилище; новый вариант берёт выделение памяти на себя. Нельзя объяснять переход к generics только уменьшением числа строк и незаметно менять договор о результате.

Что остаётся у интерфейсов

Find с предикатом не нуждается в методах у E: операцию предоставляет callback. Если задача по смыслу требует Read, интерфейс io.Reader остаётся хорошим контрактом. Если нужно одновременно сохранить конкретный тип и потребовать метод, эти два механизма можно сочетать — следующая глава именно об этом.

Ограничения: выражаем ровно те операции, которые нужны

Исходник Markdown ↗

Код главы: generic.go · example_test.go.

Хороший generic-алгоритм требует минимальных возможностей и сохраняет нужные отношения между типами.

Параметр типа сохраняет выбранный тип, но не разрешает автоматически любые операции. Для каждого алгоритма сформулируем минимальное требование: равенство, порядок, метод или сохранение типа среза.

Предикат и встроенное равенство — разные API

В Find сравнение целиком принадлежит pred, поэтому E any достаточно. Но поиск конкретного значения через == потребует другого ограничения:

Go Исходник ↗
func Contains[E comparable](src []E, target E) bool {
	return Find(src, func(item E) bool { return item == target }) >= 0
}

Это не усиленная версия Find на все случаи. Срез [][]int нельзя передать в Contains, поскольку []int несравним. Его можно передать в Find с функцией сравнения срезов. Ограничение должно следовать из операций тела, а не из названия алгоритма.

С Go 1.20 интерфейсный тип any может удовлетворять comparable. Поэтому Contains[any] разрешён, но сравнение интерфейсных значений с несравнимыми динамическими типами может вызвать panic. comparable не является обещанием безопасно сравнить произвольное runtime-содержимое интерфейса. Источник: Go 1.20.

Сортировка: порядок или функция сравнения

Для < потребуется множество упорядоченных типов, например cmp.Ordered. Для структуры User общего встроенного порядка нет; библиотека принимает func(User, User) int.

Go Исходник ↗
// imports: "cmp", "slices"
slices.Sort([]int{3, 1, 2})
slices.SortFunc(users, func(a, b User) int {
    return cmp.Compare(a.Age, b.Age)
})

Предикат «совершеннолетний» не является компаратором: он не сравнивает два значения. Компилятор проверяет форму callback, но не способен доказать согласованность порядка. Даже type-safe API требует семантического договора о сравнении.

Зачем писать S ~[]E, если есть []E

Простой Map[E, R] уже принимает значение определённого срезового типа с подходящим элементом. Но возвращает ровно []R. Отдельный параметр S нужен, когда API должен сохранять сам тип контейнера.

Go Исходник ↗
func Clone[S ~[]E, E any](src S) S {
	if src == nil {
		return nil
	}
	out := make(S, len(src))
	copy(out, src)
	return out
}
Go Исходник ↗
type Users []User
func (s Users) Count() int { return len(s) }

var users Users
copied := Clone(users)
_ = copied.Count() // возвращён Users, не просто []User

~[]E означает типы, underlying type которых — []E. В Clone тип результата S совпадает с типом входа. Это полезнее, чем механически добавлять S в любую функцию, принимающую срез.

Для Map при переходе User → string сохранить Users нельзя: это другой тип элемента. Можно принимать отдельный параметр целевого контейнера, но Go не всегда сможет вывести его из обычных аргументов. У API появляется дополнительная сложность, которую нужно оправдать реальным требованием. Разбор такой сигнатуры: Deconstructing Type Parameters.

Интерфейс как ограничение

Go Исходник ↗
type Named interface {
    Name() string
}

func Names[E Named](src []E) []string {
    return Map(src, func(item E) string { return item.Name() })
}

Это одновременно параметрический алгоритм и требование поведения. []ConcreteNamed не нужно сначала преобразовывать в []Named. Ограничение позволяет вызывать метод внутри generic-тела, сохраняя связь с конкретным E.

В сквозной модели User уже есть поле Name; метод с тем же именем добавить нельзя. Для этого примера нужна другая модель или адаптер. Поле структуры и метод интерфейса — разные вещи.

Есть и ограничение с отношением к самому типу:

Go Исходник ↗
type Equaler[E any] interface {
    Equal(E) bool
}

func ContainsEqual[E Equaler[E]](src []E, target E) bool {
    return Find(src, func(item E) bool { return item.Equal(target) }) >= 0
}

Здесь описано не просто наличие метода с любым параметром, а способность сравниваться с тем же E. Такая запись допустима начиная с Go 1.18: объявление Equaler ссылается на собственный параметр E, а не рекурсивно ограничивает само себя в списке параметров.

Type sets не являются runtime-контейнерами вариантов

Ограничение interface{ ~int | ~string } разрешает инстанциации с подходящими типами. Оно не создаёт обычный интерфейсный контейнер «int или string», который можно положить в поле и переключать во время исполнения. Для динамического набора вариантов нужен другой дизайн данных.

Аналогично два независимых параметра E any и R any не разрешают просто написать R(x): допустимость конверсии должна следовать из ограничений. В Map операция предоставлена функцией func(E) R, поэтому библиотека не придумывает конверсию самостоятельно.

sort.Slice(users, func(i, j int) bool {
    return users[i].Age < users[j].Age
})

// Go 1.21+: типизированные элементы в callback.
slices.SortFunc(users, func(a, b User) int {
    return cmp.Compare(a.Age, b.Age)
})

// Для типов со встроенным порядком callback вообще не нужен.
slices.Sort([]int{3, 1, 2})

У sort.Slice нет требований реализовать методы адаптера. Но первый параметр не гарантирует срез на этапе компиляции, а замыкание способно случайно сравнивать элементы другой коллекции. slices.SortFunc связывает тип элемента и параметры сравнения статически.

sort.Slice использует runtime-механизмы для доступа к переданному срезу и перестановок. Это не означает, что он вызывает reflect.Call для каждого сравнения: callback здесь обычная функция от индексов. Поэтому его нельзя оценивать по скорости учебного MapReflect с поэлементными динамическими вызовами. Источники: sort.Slice, Go 1.8.

Итераторы: обобщаем уже не тип элемента, а источник

Исходник Markdown ↗

Код главы: iterator.go · example_test.go · algorithms_test.go.

После решения проблемы E → R остаётся другая: алгоритм всё ещё привязан к срезу.

До сих пор входом был срез. Теперь захотим получать значения постепенно, например из другого обхода. Итератор меняет способ доставки элементов; параметры типов сохраняют их тип.

Дженерики не сделали []E произвольной коллекцией

Map[E, R] обобщён по типам, но его вход — срез. Для дерева, списка или вычисляемой последовательности придётся сначала собрать []E либо предоставить другой протокол обхода. Сборка может быть дорогой, а бесконечный источник вообще нельзя предварительно материализовать.

С Go 1.23 стандартный тип iter.Seq[E] описывает функцию, которая передаёт значения потребителю через yield. Возврат false сообщает источнику, что обход нужно остановить. iter.Seq2[K, V] передаёт пары. Это push-протокол: источник вызывает потребителя. Источник: iter.

Go Исходник ↗
// Концептуальная форма iter.Seq[E]:
// type Seq[E any] func(yield func(E) bool)

// import "slices"
for user := range slices.Values(users) {
    // user имеет тип User
    _ = user
}

Обычный for range скрывает обмен сигналом остановки. Если потребитель делает break, корректный источник должен прекратить выдавать значения. Go 1.23 стандартизировал типы и синтаксис; функции с callback как идея существовали раньше.

Ленивый Map

Go Исходник ↗
func MapSeq[E, R any](src iter.Seq[E], transform func(E) R) iter.Seq[R] {
	return func(yield func(R) bool) {
		for item := range src {
			if !yield(transform(item)) {
				return
			}
		}
	}
}

Вызов MapSeq создаёт функцию обхода. Он ещё не вызывает transform и не создаёт срез результатов. Работа начинается, когда кто-то потребляет возвращённую последовательность.

Go Исходник ↗
// import "slices"
names := MapSeq(slices.Values(users), name)
for value := range names {
    // Обработать только первое имя.
    _ = value
    break
}

Обработан только первый элемент. Проверка if !yield(...) { return } принципиальна: игнорирование false нарушает протокол и может привести к panic при range-over-func. Это не необязательная оптимизация.

Find и All над последовательностью

Go Исходник ↗
func FindSeq[E any](src iter.Seq[E], pred func(E) bool) (E, bool) {
	for item := range src {
		if pred(item) {
			return item, true
		}
	}
	var zero E
	return zero, false
}
Go Исходник ↗
func AllSeq[E any](src iter.Seq[E], pred func(E) bool) bool {
	for item := range src {
		if !pred(item) {
			return false
		}
	}
	return true
}

Теперь Find возвращает (E, bool). Прежний индекс int больше не является универсальным результатом: дерево или канал может не иметь понятия индексируемого элемента. Можно вернуть порядковый номер обхода, но это будет другая семантика, которую нужно назвать явно.

Нулевая величина E не служит признаком отсутствия: нулевой пользователь тоже может быть найден. Поэтому bool отделяет результат от отсутствия совпадения.

Композиция без промежуточного среза

Go Исходник ↗
// import "slices"
lengths := MapSeq(
    MapSeq(slices.Values(users), name),
    func(s string) int { return len(s) },
)
allLong := AllSeq(lengths, func(n int) bool { return n >= 4 })

Не создаются промежуточные []string и []int. Но функции и замыкания всё ещё имеют стоимость; код не обещает отсутствие любых аллокаций. При первом коротком имени All прекращает потребление, и остановка распространяется через обе стадии.

Это меняет наблюдаемое поведение при побочных эффектах. Eager-выражение All(Map(users, fn), pred) сначала вызывает fn для всех элементов. Ленивое выражение может вызвать fn только для префикса. Такие программы эквивалентны по bool для подходящих чистых функций, но не обязательно по логам, записи в БД или моменту panic.

Материализация — отдельное решение

Go Исходник ↗
// import "slices"
names := slices.Collect(MapSeq(slices.Values(users), name))

Collect возвращает nil для пустой последовательности. Итератор сам по себе не различает nil-срез и ненулевой пустой срез: оба не выдают элементов. Поэтому eager-контракт нашей Map о nil нельзя механически перенести на pipeline через Seq. Это пример потери информации при абстрагировании источника, а не ошибка типизации.

Не каждый Seq допускает повторный обход. Одни источники повторяемы, другие одноразовые; это нужно документировать. Для pull-модели есть iter.Pull, возвращающий next и stop; при раннем завершении потребитель должен вызвать stop. Протокол завершения и жизненный цикл — часть интерфейса алгоритмов. Источники: Range Over Function Types, slices.Collect.

Предикат All отвергает третий элемент. Сколько раз вызывается fn в eager Map на 100 элементах и в ленивом MapSeq? Что изменится, если fn паникует на десятом элементе?

Выбор определяется тем, какую информацию и какие операции должен сохранять контракт.

Мы прошли путь от конкретного цикла до типизированной ленивой последовательности. Сравним решения по требованиям задачи и договору об ошибках, а не по количеству строк или возрасту синтаксиса.

Следующая часть реализует этот план: одна задача на дробях во всех подходах, затем законы, Filter/Reduce, замеры и практикум.

Один сценарий, разные границы API

Историческая отправная точка теперь находится в первых десяти главах и работающем пакете algorithms. Там Fraction, Money и BoxInt уже обслуживаются общими циклами без параметров типов. Поэтому вывод курса — не «дженерики впервые сделали алгоритмы общими», а «дженерики позволили прямо записать часть отношений типов, прежде скрытых в адаптерах».

При сравнении с примерами над User из examples учитывайте разные договоры: algorithms передаёт ошибки операций, хранит Map-результат и Sum-аккумулятор в адаптере и не откатывает выполненные шаги. Упрощённый callback без error нельзя считать эквивалентной заменой проверяемому сложению денег.

Основная линия развития — всё более прямое выражение нужного отношения на границе библиотеки. Это не означает, что последний пункт лучше для любого вызова. Для io.Reader нужен общий набор методов; для обхода полей неизвестной структуры нужны runtime-метаданные; для обычного []User → []string естественен generic Map.

Что означает «переиспользовали алгоритм»

Можно переиспользовать только цикл (MapInto), цикл и протокол операций (RunMap), шаблон исходника (генерация), динамическую реализацию (reflection) или типизированное отношение (Map[E, R]). Эти варианты устраняют разные виды повторения.

Считать только строки тела недостаточно. Учитывайте код вызова, адаптеры, проверки ошибок, промежуточные контейнеры и необходимость обновлять специализации. Короткий универсальный цикл может обойтись дорогим и хрупким API вокруг него.

Стоимость: что измерять отдельно

Для конечных срезов Find и All имеют худшее время O(n) и O(1) дополнительной памяти самого обхода. Map выполняет n преобразований и хранит n результатов. Стоимость callback в эти оценки нужно включать отдельно. У всех вариантов может быть одна асимптотика и совершенно разная постоянная стоимость.

Нельзя вынести упаковку []interface{} из benchmark и затем объявить полученное время стоимостью полного API. Нельзя сравнить ленивый Map, который никто не потребил, с eager Map, который реально обработал все элементы. Нельзя обосновывать выбор только лозунгом «reflection медленный»: разделяйте настройку и поэлементную работу.

Результаты реальных запусков вынесены в главу об измерениях. Достоверный результат должен указывать Go toolchain, архитектуру, размер входа, работу callback, ns/op, B/op, allocs/op и повторяемость измерений.

Минимальная библиотека после разбора

Для срезов достаточно начать с Find[E any], All[E any], Map[E, R any]. Поиск по значению может быть отдельным Contains[E comparable]. Для произвольных источников добавьте Seq-варианты с документированным завершением и семантикой повторного обхода.

Не добавляйте поддержку ошибок, параллелизма, контекста и отмены одним универсальным флагом. Например, MapErr с func(E) (R, error) должен определить: остановку на первой ошибке, возврат частичного результата, порядок и выполнение оставшихся callback. Эти решения не следуют из параметров типов.

Также не стоит дублировать стандартную библиотеку ради собственного названия: реальный поиск по предикату для среза уже есть как slices.IndexFunc. Учебные реализации здесь нужны, чтобы сравнить выразительность подходов.

Практика, которая проверяет понимание

  1. Добавьте Order и повторите Find/All/Map всеми подходами. Запишите, какие файлы и адаптеры понадобились, где выявились несовместимые callback.
  2. Напишите Filter[E any] с сохранением порядка. Зафиксируйте поведение nil, пустого среза и отсутствия совпадений. Сравните срез результата с представлением через Seq.
  3. Напишите Reduce[E, A any] с начальным аккумулятором и func(A, E) A. Объясните, почему тип аккумулятора может отличаться от E и зачем нужен начальный результат для пустого входа.
  4. Создайте два Map: User → string и User → []string. Покажите, что Map сохраняет вложенность, а FlatMap потребовал бы другого алгоритма.
  5. Добавьте ошибку callback на третьем элементе и спроектируйте MapErr. Проверьте, были ли обработаны четвёртый и пятый элементы.
  6. Реализуйте FindSeq над деревом. Объясните, почему возвращается значение с bool, а не индекс среза.
  7. Проверьте закон композиции Map с чистыми функциями. Затем найдите контрпример при побочных эффектах или изменяемых объектах.

Для Filter важна не только сигнатура: если результат ссылается на исходный backing array, мутации будут наблюдаемы иначе, чем при новой аллокации. Для Reduce важен порядок: без ассоциативности нельзя произвольно распараллелить свёртку. Для ленивой композиции важен момент вычислений. Именно на таких вопросах проектирование алгоритмов становится содержательным.

Зачем нужен ещё один сквозной пример

В основном курсе мы использовали дроби и деньги для предметных ошибок, а User — для простого сравнения сигнатур. Здесь убираем это переключение: каждый подход решает одну задачу над Fraction. Теперь видно, какой код относится к алгоритму, а какой нужен для передачи данных через выбранный API.

Данные — три дроби: 1/3, 2/4 и −1/6. Нужно найти первую половину, сложить все значения и выбрать положительные. Исходный срез не меняется.

ОперацияОжидаемый результат
Find с условием Equal(1/2)Индекс 1: дробь 2/4 математически равна 1/2
Sum с начальным 0/12/3
Filter с условием Compare(0/1) > 0Две исходные дроби: 1/3 и 2/4

String печатает вторую выбранную дробь как 1/2. Filter не нормализует её поля: он сохраняет исходное значение 2/4, а сокращение относится к строковому представлению.

Договор, который не меняется между реализациями

Find обходит слева направо, возвращает первый индекс или −1 и останавливается при первой ошибке. Sum выполняет левую свёртку с явно переданным начальным значением. При ошибке возвращается последняя успешная сумма. Ошибка имеет приоритет над одновременно возвращённым true или новым значением.

Входные значения и длина не изменяются во время обхода. Callback может вести внешний счётчик вызовов, но не должен менять исходный срез. Это существенное условие: interface{}-вариант предварительно копирует значения при упаковке, а другие варианты могут читать исходное хранилище непосредственно.

Общий договор рассчитан на подходящие ненулевые callback. Невалидная дробь обнаруживается только при её посещении. Проверка совместимости динамических аргументов reflection выполняется до обхода, даже для пустого среза; это дополнительная проверка его собственного API.

Сначала прочитайте вызов

В Approaches есть единый стенд с полями Find, Filter и Reduce. Он нужен тестам и примерам, чтобы запускать варианты одинаковым способом. Этот удобный интерфейс стенда не подменяет сигнатуры сравниваемых ядер.

Например, вариант с замыканием передаёт в FindIndex длину и функцию, обращающуюся к s[i]. Вариант с интерфейсом создаёт Search{Values: s, Test: p}. Вариант с пустым интерфейсом сначала вызывает Box(s), затем AnyFind, причём каждая проверка извлекает Fraction. Генерация и generics обходятся без этого преобразования контейнера.

Sum в стенде определён через Reduce с операцией Add. Поэтому порядок, обработка ошибки и частичная сумма наследуются от соответствующей реализации Reduce, а не от отдельного общего арифметического цикла.

Реализация 1. Конкретные функции для Fraction

Алгоритм получает сам срез. В цикле value уже имеет тип Fraction, а total — тип Fraction. Ни интерфейсного контейнера, ни адаптера, ни параметров типов здесь нет.

func ConcreteFind(src []fraction.Fraction, test func(fraction.Fraction) (bool, error)) (int, error) {

		matched, err := test(value)

		}
		total = next
	}
	return total, nil

Реализация 3. Интерфейсы и адаптеры

Ядра ниже находятся в пакете algorithms. Они запрашивают только длину и операции по индексам. Find не знает Fraction; Sum не знает тип аккумулятора.

Go Исходник ↗
type Predicate interface {
	Len() int
	Match(i int) (bool, error)
}

func Find(data Predicate) (int, error) {
	n := data.Len()
	for i := 0; i < n; i++ {
		matched, err := data.Match(i)
		if err != nil {
			return -1, err
		}
		if matched {
			return i, nil
		}
	}
	return -1, nil
}

type Summable interface {
	Len() int
	Add(i int) error
}

func Sum(data Summable) error {
	n := data.Len()
	for i := 0; i < n; i++ {
		if err := data.Add(i); err != nil {
			return err
		}
	}
	return nil
}

А это конкретные адаптеры из journey. Search хранит срез и условие. Fold хранит срез, сумму и шаг сложения. Их методы переводят индекс в действие над Fraction.

Go Исходник ↗
type Search struct {
	Values []fraction.Fraction
	Test   func(fraction.Fraction) (bool, error)
}

func (s Search) Len() int                  { return len(s.Values) }
func (s Search) Match(i int) (bool, error) { return s.Test(s.Values[i]) }

type Fold struct {
	Values []fraction.Fraction
	Total  fraction.Fraction
	Step   func(fraction.Fraction, fraction.Fraction) (fraction.Fraction, error)
}

func (f *Fold) Len() int { return len(f.Values) }
func (f *Fold) Add(i int) error {
	next, err := f.Step(f.Total, f.Values[i])
	if err != nil {
		return err
	}
	f.Total = next
	return nil
}

Полная подготовка и извлечение данных показаны ниже. Box создаёт интерфейсный срез. unbox проверяет именно Fraction. AnyPredicate и anyStep связывают интерфейсные аргументы с нашими предметными функциями. Здесь нельзя просто вызвать Add у interface{}.

Go Исходник ↗
func Box(src []fraction.Fraction) []interface{} {
	if src == nil {
		return nil
	}
	out := make([]interface{}, len(src))
	for i, v := range src {
		out[i] = v
	}
	return out
}

func unbox(value interface{}) (fraction.Fraction, error) {
	f, ok := value.(fraction.Fraction)
	if !ok {
		return fraction.Fraction{}, fmt.Errorf("expected Fraction, got %T", value)
	}
	return f, nil
}

func AnyPredicate(test Predicate) func(interface{}) (bool, error) {
	return func(value interface{}) (bool, error) {
		f, err := unbox(value)
		if err != nil {
			return false, err
		}
		return test(f)
	}
}

func anyStep(step Step) func(interface{}, interface{}) (interface{}, error) {
	return func(a, b interface{}) (interface{}, error) {
		left, err := unbox(a)
		if err != nil {
			return nil, err
		}
		right, err := unbox(b)
		if err != nil {
			return nil, err
		}
		return step(left, right)
	}
}

Теперь прямой вызов содержит упаковку, оба алгоритма и извлечение суммы:

Реализация 5. Reflection

Вызов снова принимает произвольные значения, но теперь библиотека исследует срез и сигнатуры функций. Проверки выполняются до цикла, включая пустой вход. Полный код проверок приведён здесь, а не спрятан за необъяснённым helper.

Go Исходник ↗
var errorType = reflect.TypeOf((*error)(nil)).Elem()

func checkPredicate(src, test interface{}) (reflect.Value, reflect.Value, error) {
	s, f := reflect.ValueOf(src), reflect.ValueOf(test)
	if !s.IsValid() || s.Kind() != reflect.Slice {
		return s, f, fmt.Errorf("source must be a slice")
	}
	if !f.IsValid() || f.Kind() != reflect.Func || f.IsNil() {
		return s, f, fmt.Errorf("predicate must be a non-nil function")
	}
	t := f.Type()
	if t.IsVariadic() || t.NumIn() != 1 || t.NumOut() != 2 || t.In(0) != s.Type().Elem() || t.Out(0) != reflect.TypeOf(false) || t.Out(1) != errorType {
		return s, f, fmt.Errorf("predicate must have signature func(E) (bool, error)")
	}
	return s, f, nil
}

func reflectedError(v reflect.Value) error {
	if v.IsNil() {
		return nil
	}
	return v.Interface().(error)
}

После проверки Find вызывает предикат через reflect.Value.Call и читает bool и error.

Go Исходник ↗
func ReflectFind(src, test interface{}) (int, error) {
	s, f, err := checkPredicate(src, test)
	if err != nil {
		return -1, err
	}
	for i := 0; i < s.Len(); i++ {
		r := f.Call([]reflect.Value{s.Index(i)})
		if err := reflectedError(r[1]); err != nil {
			return -1, err
		}
		if r[0].Bool() {
			return i, nil
		}
	}
	return -1, nil
}

Reduce отдельно проверяет связь типов аккумулятора, элемента и результата шага. Затем каждый следующий аккумулятор становится reflect.Value результата успешного вызова.

Go Исходник ↗
func ReflectReduce(src, initial, step interface{}) (interface{}, error) {
	s, a, f := reflect.ValueOf(src), reflect.ValueOf(initial), reflect.ValueOf(step)
	if !s.IsValid() || s.Kind() != reflect.Slice || !a.IsValid() {
		return initial, fmt.Errorf("source must be a slice and initial must have a concrete type")
	}
	if !f.IsValid() || f.Kind() != reflect.Func || f.IsNil() {
		return initial, fmt.Errorf("step must be a non-nil function")
	}
	t := f.Type()
	if t.IsVariadic() || t.NumIn() != 2 || t.NumOut() != 2 || t.In(0) != a.Type() || t.In(1) != s.Type().Elem() || t.Out(0) != a.Type() || t.Out(1) != errorType {
		return initial, fmt.Errorf("step must have signature func(A,E) (A,error)")
	}
	for i := 0; i < s.Len(); i++ {
		r := f.Call([]reflect.Value{a, s.Index(i)})
		if err := reflectedError(r[1]); err != nil {
			return a.Interface(), err
		}
		a = r[0]
	}
	return a.Interface(), nil
}

Прямой вызов не упаковывает элементы по одному, но получает сумму как interface{}. Для извлечения используется полностью показанная выше unbox.

Здесь не нужны ни коллекционный адаптер, ни упаковка, ни assertion результата. При этом error и порядок накопления остались частью явно написанного алгоритма. Исходник.

Реализация 8. Типизированный итератор

Ядро получает источник iter.Seq, а не срез. Find считает позиции в порядке получения значений. Reduce обрабатывает значения по мере поступления. Выход из range прекращает корректно реализованный источник.

Go Исходник ↗
func IteratorFind[E any](src iter.Seq[E], test func(E) (bool, error)) (int, error) {
	index := 0
	for value := range src {
		matched, err := test(value)
		if err != nil {
			return -1, err
		}
		if matched {
			return index, nil
		}
		index++
	}
	return -1, nil
}

func IteratorReduce[E, A any](src iter.Seq[E], initial A, step func(A, E) (A, error)) (A, error) {
	total := initial
	for value := range src {
		next, err := step(total, value)
		if err != nil {
			return total, err
		}
		total = next
	}
	return total, nil
}

В этом сценарии источником служит slices.Values. Каждый алгоритм получает собственный обход тех же дробей:

Go Исходник ↗
func Example_directIterator() {
	values := exampleFractions()

Законы операций: что не выражает сигнатура

Исходник Markdown ↗
Метод может подходить интерфейсу и всё равно не выполнять правила, на которые рассчитывает алгоритм.

Код главы: примеры и контрпример переполнения · проверки законов.

Начнём с равенства

Для корректных дробей Equal сравнивает математические значения: 1/2 и 2/4 равны. Оператор == сравнивает поля, поэтому результат другой. Выбор операции — часть постановки задачи, а не подробность синтаксиса интерфейса.

У равенства обычно ожидают три свойства: значение равно себе; перестановка аргументов не меняет ответ; из a=b и b=c следует a=c. Они называются рефлексивностью, симметричностью и транзитивностью.

Но наш Fraction{} не является корректной дробью, и Equal для него возвращает false даже при сравнении с самим собой. Поэтому закон формулируется на множестве допустимых значений. Нельзя убрать это условие и обвинять реализацию в нарушении обещания, которого она не давала.

Порядок нужен алгоритму, а не только компилятору

Compare возвращает знак результата. Для корректных дробей ожидаем согласованность: если a меньше b, то b больше a; если a ≤ b и b ≤ c, то a ≤ c. Нулевой результат Compare должен совпадать с математическим равенством.

Сортировка не может проверить эти свойства по одной сигнатуре Compare(int,int). Например, сравнение только числителей объявит 1/2 меньшим, чем 2/4, хотя дроби равны. Оно может задавать порядок представлений, но не требуемый нам порядок математических значений.

Для Money порядок в нашей модели определён внутри одной валюты. Ошибка сравнения USD и EUR не означает, что одно из них меньше другого. Для Vector2 сначала нужно выбрать критерий: длина, X или лексикографический порядок. Универсального предметного порядка интерфейс не изобретает.

Нейтральный элемент задаётся явно

Для сложения дробей это корректный 0/1. Для денег — нулевая сумма с выбранной валютой. Нулевое значение структуры не обязано быть нейтральным: у Fraction оно невалидно, у Money не задана валюта.

Именно поэтому Sum и Reduce принимают initial. Для пустого входа возвращается он же, без вызова Add и без скрытой валидации. Это правило алгоритма, а не вывод из имени Sum.

Ассоциативность и перестановка — разные свойства

Ассоциативность разрешает менять скобки: (a+b)+c = a+(b+c). Коммутативность разрешает менять местами аргументы: a+b = b+a. Для перестановки элементов произвольной суммы нужны соответствующие законы; одного похожего имени Add недостаточно.

Математическое сложение рациональных чисел обладает обоими свойствами. Наш тип, однако, хранит конечные int64 и возвращает ошибку, когда канонический результат не представим. Операция над программными значениями может завершиться ошибкой раньше, чем математическое выражение будет вычислено целиком.

Go Исходник ↗
func Example() {
	half := fraction.Fraction{Numerator: 1, Denominator: 2}
	other := fraction.Fraction{Numerator: 2, Denominator: 4}
	fmt.Println("Поля и значение:", half == other, half.Equal(other))
	invalid := fraction.Fraction{}
	fmt.Println("Невалидная дробь равна себе:", invalid.Equal(invalid))
	zero := fraction.Fraction{Denominator: 1}
	sum, err := half.Add(zero)
	fmt.Println("Нейтральный элемент:", sum.Equal(half), err)
	a := fraction.Fraction{Numerator: math.MaxInt64, Denominator: 1}
	b := fraction.Fraction{Numerator: 1, Denominator: 1}
	c := fraction.Fraction{Numerator: -1, Denominator: 1}
	_, leftErr := a.Add(b)
	bc, err := b.Add(c)
	if err != nil {
		fmt.Println(err)
		return
	}
	right, err := a.Add(bc)
	fmt.Println("(a+b)+c: первый шаг переполнен:", leftErr != nil)
	fmt.Println("a+(b+c):", right, err)
	// Output:
	// Поля и значение: false true
	// Невалидная дробь равна себе: false
	// Нейтральный элемент: true <nil>
	// (a+b)+c: первый шаг переполнен: true
	// a+(b+c): 9223372036854775807 <nil>
}

При a=MaxInt64, b=1, c=−1 первая группировка переполняется на a+b. Во второй сначала получается b+c=0, затем a+0 допустимо. Поэтому менять группировку проверяемой суммы без дополнительных условий нельзя. Это особенно важно для параллельного Reduce: изменение порядка может изменить наличие и место ошибки.

Что проверяют наши тесты

В fuzz-тесте дроби ограничены числителями по модулю 999 и положительными знаменателями до 97. Для суммы трёх таких дробей промежуточные канонические результаты укладываются в int64. На этой области проверяются равенство, порядок, коммутативность, ассоциативность и нейтральный элемент.

Переполнение проверяется отдельно конкретным контрпримером. Ограничение области — часть теста и объяснения; тест не заявляет ассоциативность успешного исполнения для всех int64.

Filter и Reduce: один договор для разных API

Исходник Markdown ↗
Спроектируем результат, пустой вход и ошибку до выбора способа обобщения.

Код главы: восемь вариантов · generic-ядра · тесты договора.

Filter выбирает, а не преобразует

Map строит новое значение для каждого входного элемента. Filter сохраняет сами подходящие элементы в прежнем порядке. Дробь 2/4 остаётся 2/4; алгоритм не вызывает New и не сокращает поля.

Наш договор таков: nil-вход даёт nil-результат; любой ненулевой вход даёт ненулевой срез, даже если ничего не выбрано. Результат имеет отдельное хранилище элементов. При ошибке возвращаются ранее выбранные элементы, текущий и последующие не добавляются. Вместимость среза не входит в договор.

Go Исходник ↗
func GenericFilter[E any](src []E, test func(E) (bool, error)) ([]E, error) {
	if src == nil {
		return nil, nil
	}
	out := make([]E, 0, len(src))
	for _, value := range src {
		matched, err := test(value)
		if err != nil {
			return out, err
		}
		if matched {
			out = append(out, value)
		}
	}
	return out, nil
}

При копировании Fraction копируются её числовые поля. Для произвольного E это неглубокая копия: если элемент содержит указатель или срез, объекты за ними могут остаться общими. Обещание отдельного результирующего среза не означает глубокое копирование графа данных.

Почему true вместе с error не добавляет элемент

Предикат может вернуть (true, err). В нашем API это ошибка, а не совпадение. Ветвь обработки ошибки идёт первой, поэтому Filter сохраняет только уже принятый префикс результата. Частичный результат — не обязательно префикс входа: среди посещённых элементов могли быть отброшенные.

Пример с ошибкой на втором элементе возвращает [1/2] и показывает ровно два вызова callback во всех восьми подходах. Третий элемент не посещается.

Reduce меняет аккумулятор

В отличие от Filter, результат Reduce не обязан быть коллекцией. E — тип элемента, A — тип аккумулятора. Функция шага получает текущий A и очередной E, затем предлагает новое значение A.

Go Исходник ↗
func GenericReduce[E, A any](src []E, initial A, step func(A, E) (A, error)) (A, error) {
	total := initial
	for _, value := range src {
		next, err := step(total, value)
		if err != nil {
			return total, err
		}
		total = next
	}
	return total, nil
}

Алгоритм фиксирует новое значение только после успешного шага. При ошибке возвращает последнее успешное. Для nil и пустого входа сохраняет initial; callback не вызывается. Свёртка идёт слева направо и не переставляет элементы.

Это не транзакция. Если A содержит изменяемый объект и step успел изменить его перед ошибкой, возврат прежнего значения переменной не отменит изменения объекта. Наши сравнения используют Fraction со значимыми числовыми полями; для указательного аккумулятора нужен отдельный договор о мутациях или копировании.

Аккумулятор может иметь другой тип

Go Исходник ↗
func ExampleGenericReduce() {
	values := []fraction.Fraction{{Numerator: 1, Denominator: 2}, {Numerator: 1, Denominator: 3}}
	text, err := journey.GenericReduce(values, "", func(total string, value fraction.Fraction) (string, error) {
		if err := value.Validate(); err != nil {
			return "", err
		}
		return strings.TrimPrefix(total+", "+value.String(), ", "), nil
	})
	fmt.Println(text, err)
	// Output: 1/2, 1/3 <nil>
}

Здесь E — Fraction, A — string. Следовательно, Reduce не является просто другим названием суммы. Sum — частный случай Reduce, где типы совпадают, а шагом служит Add.

В конкретном варианте этой главы A фиксирован как Fraction. Для строковой свёртки пришлось бы выпустить ещё одну специализацию или определить другой адаптер. GenericReduce и ReflectReduce способны выразить другую пару типов, но проверяют её в разное время.

Как сохраняется договор у разных подходов

У замыкания результирующий срез и аккумулятор находятся в окружающем коде. У Selection и Fold — в полях адаптера. У interface{} нужны упаковка и извлечение. Reflection создаёт срез нужного динамического типа и проверяет сигнатуру шага. Сгенерированный и generic-код хранят типизированные локальные значения.

IteratorFilter выдаёт пары (E,error). Первая ошибка выдаётся один раз и завершает обход; значение E при ошибке не используется. Прекращение потребления тоже останавливает источник. Сам итератор не различает nil-срез и пустой срез, поэтому общий стенд сохраняет это различие при создании итогового хранилища, зная исходный срез.

AnyFind с заранее подготовленным входом: медиана 144.2 ns/op, диапазон 143.3–144.8, 0 B/op, 0 allocs/op.

Как читать эти числа

В дешёвом поиске упаковка 64 дробей в интерфейсный срез заметна. Когда boxed-срез подготовлен заранее, AnyFind выполняет гораздо меньше работы: упаковка уже оплачена вне таймера. Поэтому 144.2 ns/op подготовленного ядра нельзя сопоставлять с полной стоимостью другого API и называть выигрышем потребителя.

В FindMath и Sum значительную часть работы выполняют методы Fraction, использующие math/big. Различия способов вызова оказываются на фоне более дорогой предметной операции. Это видно при сопоставлении дешёвого и математического предикатов; это не доказательство одинаковой стоимости любых callback.

У конкретного FindCheap разброс составил 158.9–280.4 ns/op. Уже поэтому мелкие различия между concrete, generation, generic и closure не следует превращать в рейтинг. Три коротких запуска — учебный снимок, не статистическое доказательство превосходства.

Интерфейсный вариант в этом стенде выделяет память под конкретный адаптер. Это наблюдение для данного кода и компилятора, а не правило «любой интерфейс всегда аллоцирует». Аналогично результат reflection включает проверку сигнатуры и вызовы reflect.Value.Call; другие reflection-API могут иметь иной способ подготовки.

Что включено в цену удобства

Стенд Approach использует поля-функции, чтобы одинаково вызывать варианты. Эта диспетчеризация есть в полном измерении. Мы измеряем конкретный путь потребителя из сквозного сценария, а не изолированную машинную инструкцию вызова интерфейсного метода.

Итераторный Filter полностью потребляется и собирается в срез. Иначе сравнение с eager Filter было бы некорректным. Для задачи «получить только первый подходящий элемент» нужен другой benchmark с ранним завершением, а не перенос этих цифр.

Как повторить исследование

  1. Сначала запустите тесты общего договора: сравниваемые реализации должны выдавать одинаковые результаты.
  2. Повторите измерения на своей машине с теми же параметрами и сохраните полный вывод.
  3. Затем отдельно измените размер входа, положение совпадения или стоимость callback.
  4. Для производственного решения увеличьте длительность и число повторов, оцените разброс и условия запуска.

Задание 4. Проверьте композицию Map

Для чистых функций ожидается одинаковый результат двух проходов Map(g, Map(f, values)) и одного прохода с g(f(value)). Сохранится ли порядок наблюдаемых эффектов, если обе функции записывают события в журнал?

Go Исходник ↗
func Example_mapComposition() {
	var events []string
	f := func(n int) int { events = append(events, fmt.Sprintf("f%d", n)); return n + 1 }
	g := func(n int) int { events = append(events, fmt.Sprintf("g%d", n)); return n * 2 }
	first := generic.Map(generic.Map([]int{1, 2}, f), g)
	fmt.Println(first, events)
	events = nil
	second := generic.Map([]int{1, 2}, func(n int) int { return g(f(n)) })
	fmt.Println(second, events)
	// Output:
	// [4 6] [f1 f2 g2 g3]
	// [4 6] [f1 g2 f2 g3]
}

Числовые результаты совпали, журналы — нет. При двух проходах сначала выполняются все f, затем все g; при объединении они чередуются. Поэтому оптимизация композиции требует условий о побочных эффектах, а не только совпадения сигнатур.

Задание 6. Разделите закон и область его действия

Исходник Markdown ↗

Константы и присваивание

Исходник Markdown ↗

Код главы: example_test.go.

Число 42 в исходнике и переменная типа int со значением 42 подчиняются разным правилам. Сначала сравним их присваивание, затем посмотрим на определённые типы и nil.

Нетипизированная константа

var b float64 = answer
var c complex128 = answer

inferred := 42 // int: тип по умолчанию
const typed int = 42
// var d int64 = typed // typed уже имеет тип int

// _ = uint8(300) // ошибка компиляции: константа не помещается

Разница между константой и переменной объясняет, почему uint8(300) запрещено, а преобразование переменной со значением 300 даёт 44. Это не автоматическое расширение любых чисел. См. Constants.

Совместимость при присваивании

Go Исходник ↗
type Numbers []int
var named Numbers = []int{1, 2}
var plain []int = named // одинаковые underlying types, один тип неименованный

type OtherNumbers []int
// var other OtherNumbers = named // оба типа определённые
other := OtherNumbers(named)       // явная конверсия допустима

Термины: type ID int создаёт определённый тип; его underlying type — int. Именованность, идентичность типов и возможность присваивания — разные понятия. Алиас сам по себе нового типа не создаёт.

Есть отдельные правила для интерфейсов, каналов, nil и параметров типов. Эти правила действуют также при передаче аргументов и возврате результатов. Нормативный список: Assignability.

Строки, байты, руны и числа

Исходник Markdown ↗

Код главы: example_test.go.

Цель главы: Выбирать между байтами, рунами и текстовым представлением числа.

Строка может быть текстом числа или последовательностью UTF-8. В первом случае нужен парсер, во втором — выбор между байтами и рунами. Примеры ниже показывают разные результаты этих операций.

Go Исходник ↗
text := "Привет"
bytes := []byte(text) // UTF-8 байты
runes := []rune(text) // кодовые точки Unicode
fromBytes := string(bytes)
fromRunes := string(runes)

letter := string(rune(65)) // "A", не "65"
replacement := string(rune(-1)) // "�": недопустимая кодовая точка

type Label string
label := Label(text)
original := string(label)

byte — алиас uint8, rune — алиас int32. Одна руна не обязательно равна одному видимому символу. []byte сохраняет байты, а []rune декодирует UTF-8; некорректные последовательности при декодировании заменяются на U+FFFD.

Обычные конверсии между строкой и срезом обеспечивают независимость наблюдаемых изменений: изменение полученного []byte не меняет исходную строку. Из этого не следует обязательная heap-аллокация: компилятор может оптимизировать её. См. Effective Go: strings и конверсии строк.

if err != nil {
    // Обработать ошибку формата или диапазона.
}
decimal := strconv.Itoa(42)
hex := strconv.FormatInt(255, 16) // "ff"
parsed, parseErr := strconv.ParseInt("ff", 16, 64)
flag, boolErr := strconv.ParseBool("true")
number, floatErr := strconv.ParseFloat("3.14", 64)

int("42") запрещено, string(42) даёт кодовую точку, а strconv.Itoa(42) — десятичную запись. Для форматирования с шаблоном есть fmt.Sprintf, для чтения формата — fmt.Sscanf. Проверка синтаксиса и диапазона относится к разбору данных, а не к конверсии языка. Справочник: strconv.

Определённые типы, структуры, функции и контейнеры

Исходник Markdown ↗

Код главы: defined.go · example_test.go · example_test.go.

Цель главы: Понимать совместимость составных и определённых типов.

Конверсия нового типа не означает преобразование всех его элементов и не переносит методы. Начнём с ID, затем проверим структуры и контейнеры, обращая внимание на общую память.

Новый тип не наследует методы

Go Исходник ↗
// import "fmt"
type UserID int64
func (id UserID) String() string { return fmt.Sprintf("user:%d", id) }

type OrderID UserID

func exampleIDs() {
    user := UserID(42)
    order := OrderID(user)
    _ = user.String()
    // _ = order.String() // у OrderID нет этого метода
    _ = order
}

Конверсия позволяет перейти между такими типами, но не проверяет предметный смысл. Для запрета отрицательного ID нужен конструктор с валидацией.

Структуры; послабление Go 1.8 для тегов

Go Исходник ↗
type APIUser struct {
    ID int64 `json:"id"`
}
type DBUser struct {
    ID int64 `db:"user_id"`
}

func convertUser(api APIUser) DBUser {
    return DBUser(api) // Go 1.8+: различия тегов не мешают
}

Это не автоматический маппинг по названиям. Порядок полей и их типы имеют значение. Например, ID int и ID int64 потребуют явного построения результата. Копирование структуры неглубокое: поля-срезы и указатели могут продолжить ссылаться на общие данные. См. Go 1.8.

Указатели, функции, массивы, срезы и map

Go Исходник ↗
type A int
type B int

type F func(int) int
type G func(int) int

type Vector [2]int
type SliceA []int
type SliceB []int
type MapA map[string]int
type MapB map[string]int

func exampleComposite() {
    a := A(1)
    b := (*B)(&a) // допустимая конверсия неименованных указателей
    *b = 7       // изменяет a: это та же память

    f := F(func(n int) int { return n + 1 })
    g := G(f)
    vector := Vector([2]int{1, 2})

    s := SliceA{1, 2}
    t := SliceB(s) // тот же backing array
    t[0] = 9

    m := MapA{"x": 1}
    convertedMap := MapB(m) // та же map
    convertedMap["x"] = 2

    _, _, _ = g, vector, b
}

Одинаковое представление памяти само по себе не разрешает конверсию. Например, *int64 → *float64 требует иных механизмов. Для обычных указателей существенны условия идентичности underlying types базовых типов; для функций — сигнатуры. См. Conversions.

Нет поэлементной конверсии контейнеров:

Go Исходник ↗
src := []int{1, 2, 3}
// dst := []int64(src) // запрещено
dst := make([]int64, len(src))
for i, n := range src {
    dst[i] = int64(n)
}

// Не работают также []string → []any и map[string]int → map[string]int64.

Направление канала

Go Исходник ↗
ch := make(chan int)
var recv <-chan int = ch
var send chan<- int = ch
explicit := (<-chan int)(ch)
// both := (chan int)(recv) // восстановить оба направления нельзя

Это ограничивает доступ через значение, а не создаёт новый канал. Для двух определённых типов каналов может потребоваться промежуточный неименованный тип. Правила приведены в Assignability.

Интерфейсы: исходная модель полиморфизма

Исходник Markdown ↗

Код главы: typeinterfaces.go · example_test.go.

Цель главы: Работать с динамическим типом интерфейсного значения.

Здесь собраны точные правила, на которых основаны главы об адаптерах. Следите за двумя типами: объявленным типом переменной и конкретным типом значения внутри интерфейса.

Упаковка конкретного значения

Go Исходник ↗
var x any = int(42) // any доступен с Go 1.18
var old interface{} = int(42) // историческая запись того же типа

Интерфейс хранит динамический тип и значение. Присваивание int в any не превращает его в «универсальное число». Пара тип + значение — семантическая модель, не обещание конкретной раскладки runtime. См. The Laws of Reflection.

Type assertion: x.(T)

Go Исходник ↗
var x any = int(42)
n := x.(int)              // 42
wide, ok := x.(int64)      // 0, false
// panicValue := x.(int64) // panic

if n, ok := x.(int); ok {
    converted := int64(n)  // assertion, затем числовая конверсия
    _ = converted
}

Для конкретного T требуется совпадение динамического типа, а не просто возможность конверсии. Для интерфейсного T проверяется реализация интерфейса. Исходный операнд должен иметь интерфейсный тип; к обычной переменной int assertion применить нельзя. См. Effective Go: interface conversions.

Интерфейс → интерфейс

Go Исходник ↗
// import "io"
func inspect(rw io.ReadWriter) {
    var reader io.Reader = rw // все нужные методы гарантированы статически
    writer, ok := reader.(io.Writer) // проверка динамического значения
    _, _ = writer, ok
}

Type switch

Go Исходник ↗
// import "fmt"
func describe(x any) string {
    switch v := x.(type) {
    case nil:
        return "nil interface"
    case int:
        return fmt.Sprintf("int: %d", v)
    case string:
        return "string: " + v
    case float32, float64:
        return fmt.Sprintf("float: %v", v) // здесь v имеет тип any
    default:
        return fmt.Sprintf("other: %T", v)
    }
}

Это проверка вариантов во время исполнения. Нетипизированного x.(type) вне type switch не существует. См. Type switches.

Методы, указатели и typed nil

Go Исходник ↗
type Worker interface { Work() }
type Job struct{}
func (*Job) Work() {}

var _ Worker = (*Job)(nil) // проверка реализации на этапе компиляции
// var _ Worker = Job{}   // у Job нет метода с pointer receiver

func nilExample() bool {
    var p *Job = nil
    var w Worker = p
    return w == nil // false: динамический тип *Job присутствует
}

Автоматическое взятие адреса при вызове метода у адресуемой переменной не добавляет pointer-методы в method set типа значения. Интерфейс равен nil, когда отсутствуют и динамический тип, и значение. Это также объясняет ошибку возврата typed nil как error. См. Go FAQ: nil error и method sets.

Reflection: когда тип приходит во время исполнения

Исходник Markdown ↗

Код главы: reflection.go · example_test.go.

Цель главы: Проверять возможность динамической конверсии.

Когда целевой тип приходит во время выполнения, обычная запись T(x) не подходит. Проверим динамическую конверсию и отдельно выясним, почему совместимости типов иногда недостаточно.

Go Исходник ↗
// import "reflect"
func convertDynamic(x any, target reflect.Type) (any, bool) {
    value := reflect.ValueOf(x)
    if target == nil || !value.IsValid() || !value.CanConvert(target) {
        return nil, false
    }
    return value.Convert(target).Interface(), true
}

// out, ok := convertDynamic(int32(42), reflect.TypeOf(int64(0)))
// out имеет статический тип any и динамический тип int64.

reflect.Type.ConvertibleTo проверяет совместимость типов. Value.CanConvert учитывает также конкретное значение: например, длину среза перед конверсией в массив. Convert без проверки может вызвать panic.

AssignableTo относится к присваиванию, Implements — к реализации интерфейса. Эти проверки не взаимозаменяемы. reflect.Value.Int() читает целочисленное значение как int64, но не меняет исходный тип. Запись через Set/SetInt дополнительно зависит от доступности значения для изменения.

С Go 1.22 reflect.TypeFor[T]() возвращает тип аргумента, включая интерфейсный тип; reflect.TypeOf(x) возвращает динамический тип значения. Источники: reflect, Go 1.22.

Срез → указатель на массив: Go 1.17

Исходник Markdown ↗

Код главы: example_test.go · failures_test.go.

Этот переход даёт доступ к началу среза как к массиву через указатель. Главный эксперимент — изменить элемент и увидеть изменение исходного среза.

Go Исходник ↗
s := []int{10, 20, 30}
p := (*[2]int)(s)
p[0] = 99 // s[0] тоже стал 99

// _ = (*[4]int)(s) // panic: len(s) < 4

Проверяется len, а не cap. Конверсия не копирует элементы. Для nil-среза конверсия в *[0]T даёт nil-указатель; для пустого, но ненулевого среза — ненулевой указатель на массив нулевой длины. Это первый введённый в Go случай конверсии, способной вызвать runtime panic. Источник: Go 1.17.

Обратное представление массива как среза создаётся через slicing: a[:] или p[:]. Сам массив при a[:] должен быть адресуемым. Это операция slicing, а не T(x).

Дженерики: Go 1.18

Исходник Markdown ↗

Код главы: conversions.go · example_test.go · failures_test.go.

Цель главы: Обобщать конверсии с проверяемыми ограничениями.

Этот раздел дополняет основной курс правилами конверсий. Проверим, какие ограничения разрешают To(x), чем assertion отличается от него и почему comparable не устраняет все паники.

Что они добавили

До дженериков обобщённый алгоритм обычно выражали через интерфейсы с методами, interface{} с assertions, reflection, генерацию кода или отдельные реализации для типов. Дженерики позволили проверять операции над параметрами типов при компиляции и сохранять конкретные типы аргументов и результатов. См. An Introduction To Generics.

Ограниченная конверсия

Go Исходник ↗
type Real interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64 |
    ~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr |
    ~float32 | ~float64
}

func Convert[To Real, From Real](x From) To {
    return To(x)
}

// result := Convert[int64](int32(42))
// To задан явно; From выводится из аргумента.

~int64 допускает типы с underlying type int64, например type UserID int64. Без ~ член int64 описывает сам этот тип. | объединяет множества типов. Здесь конверсия разрешена для всех сочетаний исходного и целевого типов, но потери точности и переполнение остаются возможными.

Интерфейс с type terms, например interface{ ~int | ~string }, применяется как ограничение, а не как тип обычной переменной. any означает отсутствие ограничений, а не разрешение любой операции. Источник: Go 1.18.

Почему универсальный cast не получается

Go Исходник ↗
// Не компилируется: any не гарантирует допустимость конверсии.
// func Cast[To, From any](x From) To { return To(x) }

func Assert[T any](x any) (T, bool) {
    value, ok := x.(T)
    return value, ok
}

func IsString[T any](x T) bool {
    _, ok := any(x).(string)
    return ok
}

Assert[int64](int(42)) вернёт 0, false. Assert обобщает проверку типа, не числовую конверсию. Прямой x.(string) для x T запрещён: сначала нужно интерфейсное значение. Так же для type switch используют switch any(x).(type). См. Type assertions.

Поэлементный маппинг

Go Исходник ↗
func Map[S ~[]E, E, R any](src S, convert func(E) R) []R {
    if src == nil {
        return nil
    }
    dst := make([]R, len(src))
    for i, item := range src {
        dst[i] = convert(item)
    }
    return dst
}

// result := Map([]int{1, 2}, func(n int) int64 { return int64(n) })

Алгоритм создаёт новый срез, а смысл конверсии задаёт вызывающий код. При возможных ошибках нужен отдельный контракт с (R, error) и правилом обработки частичного результата. Дженерики сами такой контракт не выбирают.

comparable: уточнение Go 1.20

С Go 1.20 any может удовлетворять ограничению comparable. Это не обещает, что сравнение любых динамических значений безопасно:

Go Исходник ↗
func Equal[T comparable](a, b T) bool { return a == b }

// Equal[any](42, 42)           // true, Go 1.20+
// Equal[any]([]int{1}, []int{1}) // panic: срезы несравнимы

Это изменение правил удовлетворения ограничения, а не новый способ конверсии. Источник: Go 1.20.

Generic aliases: Go 1.24

Go Исходник ↗
type Set[T comparable] = map[T]bool // Go 1.24+

func aliasSetExample() {

Самоссылки в ограничениях: Go 1.26

    Add(A) A
}

Ограничение может ссылаться на объявляемый generic-тип. Это расширяет описание допустимых типов, но не даёт дополнительной runtime-конверсии. Источник: Go 1.26.

Методы с собственными параметрами типов: Go 1.27

// n := (Converter{}).ToInt64(int32(42)) // Go 1.27+

Исходник Markdown ↗

Код главы: example_test.go.

Цель главы: Отличать числовую конверсию от интерпретации памяти.

Обычная конверсия меняет числовое значение по правилам языка. Здесь мы смотрим на те же биты как на другой тип. Это отдельная операция с отдельными требованиями к памяти.

Go Исходник ↗
// import "unsafe"
bits := uint32(0x3f800000)
number := *(*float32)(unsafe.Pointer(&bits)) // 1 на соответствующем представлении

Это чтение битов через другой тип, не числовое преобразование float32(bits). Для такого примера лучше готовая функция math.Float32frombits.

unsafe.Pointer допускает переходы к/от типизированных указателей и uintptr при документированных ограничениях. uintptr — целое число, не GC-ссылка: нельзя хранить в нём адрес и считать объект защищённым от сборки мусора. Арифметика адресов и обратные преобразования допустимы только в перечисленных документацией шаблонах.

errors.As: извлечение ошибки из дерева

Go Исходник ↗
// imports: "errors", "io/fs"
func pathFromError(err error) (string, bool) {
    var target *fs.PathError
    if errors.As(err, &target) {
        return target.Path, true
    }
    return "", false
}

err.(*fs.PathError) проверяет только непосредственный динамический тип. errors.As проходит по обёрнутым ошибкам и учитывает пользовательский метод As. Это механизм поиска, а не T(x). Он появился в Go 1.13; пример использует пакет io/fs из Go 1.16. Источник: errors.

JSON и другие форматы

json.Unmarshal декодирует данные по правилам JSON. Для традиционного API encoding/json число при декодировании в any обычно становится float64; Decoder.UseNumber позволяет получить json.Number. Преобразование через JSON может терять сведения о типах и точность чисел, поэтому это отдельный контракт сериализации. Источник: encoding/json.

Адаптер функции к интерфейсу

Go Исходник ↗
// import "net/http"
func serve(w http.ResponseWriter, r *http.Request) {}

var handler http.Handler = http.HandlerFunc(serve)

Здесь сначала функция конвертируется в определённый функциональный тип http.HandlerFunc, у которого есть метод ServeHTTP, затем присваивается интерфейсу. Это сочетание двух обычных механизмов. Источник: Effective Go: interfaces.

Ручной маппинг, генерация, cgo

Для структур с разными полями пишут ToDomain, ToDTO, конструктор или генерируют такой код. Генерация не вводит новых правил типизации. На границе с C действуют также размеры C-типов, правила владения и передачи указателей; функции вроде C.GoString выполняют специальное преобразование данных. Это отдельная тема межъязыкового взаимодействия, не универсальный cast. См. cgo.
