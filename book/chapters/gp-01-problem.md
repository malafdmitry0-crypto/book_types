# 2. Наши типы: одинаковые операции ещё не дают общего алгоритма

Код главы: [example_test.go](../../lessons/generic/example_test.go) · [types_test.go](../../types_test.go).


> Возьмём настоящие типы проекта и отделим математические и предметные операции от алгоритмов обхода.

Теперь выберем данные для библиотеки. Нам нужны не абстрактные E и T, а дроби, деньги и числа с понятным поведением. Сравним их методы и отделим одинаковые названия от одинаковых сигнатур.

## Шесть типов с разными возможностями

| Тип | Что представляет | Какие операции естественны |
|---|---|---|
| Fraction | Обыкновенную дробь | Математическое равенство, порядок, арифметика |
| Money | Количество минимальных единиц и валюту | Сумма и разность одной валюты, порядок внутри валюты |
| BoxInt | int64 в структуре | Проверяемая целочисленная арифметика через методы |
| IntValue | Определённый тип на основе int64 | Числовые операторы и проверяемые методы |
| Vector2 | Две координаты | Равенство, сумма, масштабирование, скалярное произведение |
| Version | Три числовых компонента версии | Порядок и переход к следующему компоненту |

Полные объявления и методы находятся в отдельных пакетах: [fraction](../../fraction/fraction.go), [money](../../money/money.go), [boxint](../../boxint/boxint.go), [intvalue](../../intvalue/intvalue.go), [vector2](../../vector2/vector2.go), [version](../../version/version.go).

Мы специально добились большого пересечения методов: у Fraction, BoxInt и IntValue совпадают одиннадцать имён и форм сигнатур, у Money — девять из этих одиннадцати. Но это сходство на уровне схемы с заменой собственного типа, а не идентичность конкретных сигнатур Go. [Таблица методов](../../TYPES.md) фиксирует точный контракт.

## Дробь: сравнить представление или значение?

```go
half := fraction.Fraction{Numerator: 1, Denominator: 2}
other := fraction.Fraction{Numerator: 2, Denominator: 4}

sameFields := half == other // false
sameValue := half.Equal(other) // true
```

Если общий Find будет использовать равенство полей, он решит другую задачу. Алгоритму нужно передать выбранное условие или операцию предметного типа, а не угадывать смысл сравнения.

Денежные суммы ещё строже: `100 USD` и `100 EUR` нельзя просто сложить или упорядочить как целые 100. Money.Add и Money.Compare возвращают ошибку при разных валютах. Поэтому сигнатура нашего алгоритма должна уметь передавать ошибку наружу.

## Одна форма метода, разные сигнатуры

```text
Fraction.Add(Fraction) → (Fraction, error)
BoxInt.Add(BoxInt)     → (BoxInt, error)
Money.Add(Money)       → (Money, error)
```

Нельзя заменить аргумент и результат интерфейсом и ожидать, что эти методы автоматически его реализуют:

```go
// Такое объявление допустимо, но наши типы его НЕ реализуют.
type Adder interface {
    Add(interface{}) (interface{}, error)
}
```

Go требует совпадения сигнатур методов. Возможность отдельно присвоить Money в interface{} не меняет тип метода Money.Add. И пустой интерфейс не обозначает «тот же тип, что у получателя».

Для String всё иначе: `String() string` действительно является одной и той же сигнатурой у всех шести типов. Поэтому маленький интерфейс Stringer работает непосредственно, без адаптации каждого результата.

## Какие алгоритмы будем писать

| Задача | Конкретный пример | Что нужно алгоритму |
|---|---|---|
| Find | Найти дробь, равную 1/2 | Условие совпадения |
| All / Any | Все дроби положительны? Есть нулевая? | Предикат и ранняя остановка |
| Map | Превратить `[]Fraction` в `[]string` | Преобразование и место для результата |
| Sum | Сложить `[]Money` | Операция сложения и начальное значение |
| Min / Max | Найти минимальный BoxInt | Согласованный порядок |
| Sort | Упорядочить `[]BoxInt` | Порядок и перестановка элементов |

Find, All и Map здесь — названия учебных задач, а не заявления о наличии одноимённых функций в Go 1. В нашем нынешнем пакете Find возвращает индекс или -1, All на пустом входе — true, Any — false; все три дополнительно возвращают error.

## Где заканчивается общее

У Vector2 нет Compare: можно сортировать по длине или координатам, но критерий должен выбрать вызывающий. У Version нет Add: арифметически складывать номера версий не имеет предметного смысла. Не следует добавлять такие методы только ради единого большого интерфейса.

Чем меньше операций просит алгоритм, тем больше подходящих типов. Find не обязан требовать Add; Sum не обязан требовать Compare. Это принцип проектирования интерфейсов, доступный задолго до дженериков.

## Четыре вопроса для каждого следующего решения

1. Где находится конкретный тип элемента: у алгоритма или у адаптера?
2. Кто связывает вход, операцию и результат?
3. Когда обнаруживается неправильный вызов: при компиляции или при исполнении?
4. Что приходится повторить, чтобы перейти от дробей к деньгам?

## Проверка понимания

Почему 100% совпадения форм методов у Fraction и BoxInt недостаточно для общего интерфейса Adder без параметра типа? Почему тот же аргумент не мешает им одновременно реализовывать Stringer?
