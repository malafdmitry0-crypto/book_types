# 11. interface{}: один контейнер, потерянные статические связи

Код главы: [algorithms.go](../../examples/algorithms.go) · [example_test.go](../../examples/example_test.go) · [algorithms_test.go](../../examples/algorithms_test.go).


> Принять значение любого типа и сохранить связь между произвольными типами — разные требования.

До сих пор элементы оставались у вызывающего. Теперь попробуем передать их внутрь общей функции как интерфейсные значения. Это альтернативное решение той же задачи в раннем Go, а не новый релиз языка.

## Убираем адаптеры с методами

В ранней библиотеке из первой части конкретные типы сохранились внутри fractionQuery, fractionText и moneySum. Теперь исследуем альтернативу: вынести элементы в общий интерфейсный контейнер. Это решение тоже было доступно до дженериков, а не появилось после очередного обновления языка.

Для следующих сравнений возьмём User: у него есть Name, Age и Active. Поиск проверяет совершеннолетие, All — активность, Map получает имена. Полные вызовы находятся в examples/example_test.go. Их callback не возвращают error; это упрощённая модель для демонстрации статических типов. Перенося такой подход на наши Fraction и Money, нельзя убрать ошибки Validate/Add: понадобится callback с error и передача ошибки наружу, как в algorithms. Простая замена на interface{} не решает этот вопрос.

Если все элементы заранее упаковать в `interface{}`, получится одна сигнатура для разных данных. В этой главе используем историческое написание; с Go 1.18 `any` является алиасом того же типа.

```go
func FindAny(src []interface{}, pred func(interface{}) bool) int {
	for i, item := range src {
		if pred(item) {
			return i
		}
	}
	return -1
}
```

```go
func AllAny(src []interface{}, pred func(interface{}) bool) bool {
	for _, item := range src {
		if !pred(item) {
			return false
		}
	}
	return true
}
```

```go
func MapAny(src []interface{}, transform func(interface{}) interface{}) []interface{} {
	if src == nil {
		return nil
	}
	out := make([]interface{}, len(src))
	for i, item := range src {
		out[i] = transform(item)
	}
	return out
}
```

Алгоритмы действительно общие. Но `MapAny` на этапе компиляции возвращает только `[]interface{}`. То, что внутри оказались исключительно строки, не меняет этот статический тип.

## Цена на границе вызова

```go
var boxed []interface{}
if users != nil {
    boxed = make([]interface{}, len(users))
}
for i, user := range users {
    boxed[i] = user
}

index := FindAny(boxed, func(x interface{}) bool {
    return x.(User).Age >= 18
})
all := AllAny(boxed, func(x interface{}) bool {
    return x.(User).Active
})
raw := MapAny(boxed, func(x interface{}) interface{} {
    return x.(User).Name
})

var names []string
if raw != nil {
    names = make([]string, len(raw))
}
for i, item := range raw {
    names[i] = item.(string)
}
```

Нельзя просто передать `[]User` как `[]interface{}`. И нельзя присвоить `func(User) string` переменной типа `func(interface{}) interface{}`. В первом случае нужен новый срез с поэлементным присваиванием, во втором — функция-обёртка.

Отсутствие ковариантности у срезов важно и семантически: если бы общий изменяемый `[]User` можно было использовать как `[]interface{}`, через него можно было бы попытаться записать строку в хранилище пользователей. Для преобразования срезов Go требует явного цикла. Источник: [Go FAQ](https://go.dev/doc/faq#convert_slice_of_interface).

## Что увидит компилятор

В `FindAny` нет декларации «callback ожидает тот же конкретный тип, который лежит в исходном срезе». Он получает `interface{}` и возвращает `bool` — это весь статический контракт. Поэтому такой вызов компилируется:

```go
FindAny([]interface{}{User{Name: "Аня"}}, func(x interface{}) bool {
    return len(x.(string)) > 0 // panic при обработке User
})
```

Можно заменить assertion на `value, ok := x.(User)`. Но затем нужно решить, что делать при несовпадении: пропустить элемент, вернуть ошибку, завершить поиск? Мы вынуждены добавлять в контракт ситуации, которых у конкретной типизированной функции не было.

Ещё опаснее проверка через `==`: сравнение двух интерфейсных значений может вызвать panic, если их динамические значения несравнимы. `interface{}` не означает «любой оператор допустим».

## Данные не теряют runtime-тип

Упаковка `User` в интерфейс не стирает сведения о нём из runtime. Иначе assertion был бы невозможен. Потеря происходит в статическом контракте: компилятор вызывающего кода больше не выводит `[]string` из `MapAny`.

Поэтому выражение «type erasure» здесь следует использовать осторожно: это не буквальное отсутствие информации о типе во время исполнения. Для нашего сравнения точнее говорить о потере статической связи между типами аргументов и результата.

## Когда это полезная модель

Если данные по смыслу разнородны — например, набор произвольных значений для форматирования — `[]interface{}` отражает задачу. Проблема возникает, когда однородную `[]User` вынуждают пройти через этот формат только ради общего цикла.

В приведённом адаптере появляются дополнительные контейнеры и обходы для упаковки и извлечения. Это конкретное свойство этой реализации. Утверждать, что каждое интерфейсное значение обязательно создаёт отдельную heap-аллокацию, нельзя: размещение зависит от компилятора и контекста.

## Переход к reflection

Следующий вопрос: можно ли принять исходный `[]User` и исходный `func(User) string` без ручной упаковки, а совместимость выяснить внутри библиотеки? Для этого нужно уметь исследовать типы и вызывать функцию во время исполнения.

## Проверка понимания

`MapAny` обработал миллион пользователей и вернул миллион строк. Почему `raw.([]string)` даже не является допустимой операцией, а преобразование `[]string(raw)` тоже не работает? Укажите сначала статический тип `raw`.
