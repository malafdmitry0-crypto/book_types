## Задание 1. Найдите неправильное сравнение

Сортировку дробей реализовали сравнением числителей. Подберите две математически равные дроби, для которых эта проверка говорит «меньше». Затем исправьте критерий, сохранив возврат ошибки.

Решение: 1/2 и 2/4. Сравнение 1<2 истинно, но Fraction.Compare возвращает 0. Если задача — порядок математических значений, нужно использовать Compare и передать ошибку наружу. Исполняемый пример — Example_comparatorCounterexample.

## Задание 2. Предскажите частичный Filter

На первом элементе callback возвращает true, на втором — true вместе с ошибкой. В срезе есть третий элемент. Какие элементы попадут в результат и сколько раз вызовется callback?

Решение: только первый элемент и два вызова. Ошибка проверяется до true. Example_partialFilter запускает этот сценарий для всех восьми вариантов. Попробуйте изменить первый ответ на false: результат станет пустым, но число вызовов останется прежним.

## Задание 3. Смените тип аккумулятора

Получите одну строку из среза Fraction через Reduce, разделяя записи запятыми. Не создавайте промежуточный []string. Определите поведение пустого входа и ошибки Validate.

Решение находится в ExampleGenericReduce: начальный аккумулятор — пустая строка, шаг проверяет дробь и добавляет её String. При ошибке алгоритм возвращает строку, накопленную до ошибочного элемента. Типы E и A различаются.

## Задание 4. Проверьте композицию Map

Для чистых функций ожидается одинаковый результат двух проходов Map(g, Map(f, values)) и одного прохода с g(f(value)). Сохранится ли порядок наблюдаемых эффектов, если обе функции записывают события в журнал?

```go
func Example_mapComposition() {
	var events []string
	f := func(n int) int { events = append(events, fmt.Sprintf("f%d", n)); return n + 1 }
	g := func(n int) int { events = append(events, fmt.Sprintf("g%d", n)); return n * 2 }
	first := generic.Map(generic.Map([]int{1, 2}, f), g)
	fmt.Println(first, events)
	events = nil
	second := generic.Map([]int{1, 2}, func(n int) int { return g(f(n)) })
	fmt.Println(second, events)
	// Output:
	// [4 6] [f1 f2 g2 g3]
	// [4 6] [f1 g2 f2 g3]
}
```

Числовые результаты совпали, журналы — нет. При двух проходах сначала выполняются все f, затем все g; при объединении они чередуются. Поэтому оптимизация композиции требует условий о побочных эффектах, а не только совпадения сигнатур.

## Задание 5. Автоматически меняйте вход одной задачи

Создайте fuzz-тест, который строит дроби из байтов и сравнивает восемь подходов. Начните с nil/пустого входа, отсутствия совпадений и отрицательных значений. Проверяйте не только сумму, но и индекс, порядок Filter и nilness.

Решение — FuzzApproachAgreement. Оно сравнивает подходы с конкретной реализацией на входах длиной до 32 и дробях со знаменателем 6. Ограничение длины удерживает стоимость reflection и арифметики в разумных пределах. Общая ошибка всех реализаций могла бы остаться незамеченной, поэтому отдельно существуют тесты известных результатов и законов.

## Задание 6. Разделите закон и область его действия

Напишите проверку ассоциативности сложения, затем подайте MaxInt64, 1 и −1. Можно ли считать несовпадение успешности двух группировок ошибкой Fraction.Add?

Решение — нет: операция возвращает ошибку переполнения промежуточного результата. FuzzFractionLaws проверяет ассоциативность на ограниченной области, где результаты представимы. TestOverflowChangesGrouping отдельно фиксирует различие группировок на границе диапазона.

## Запуск обычных и fuzz-тестов

Обычный go test выполняет сохранённые начальные примеры fuzz-тестов. Режим -fuzz дополнительно генерирует входы и ищет новые пути выполнения. Это проверка свойств на исследованных данных, а не математическое доказательство. Правила и команды: [Go Fuzzing](https://go.dev/doc/security/fuzz/).

```sh
go test ./lessons/journey ./lessons/laws
go test ./lessons/laws -run '^$' -fuzz '^FuzzFractionLaws$' -fuzztime=5s -parallel=2
go test ./lessons/journey -run '^$' -fuzz '^FuzzApproachAgreement$' -fuzztime=5s -parallel=2
```

В этой проверке оба fuzz-запуска завершились успешно. Количество исследованных входов зависит от машины, времени и сохранённого fuzz-кэша; оно не является показателем покрытия всех возможных значений.
