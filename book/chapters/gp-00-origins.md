# 1. Как всё начиналось: обобщённое программирование до дженериков

Код главы: [example_test.go](../../lessons/interfaces/example_test.go) · [historical_test.go](../../lessons/interfaces/historical_test.go).


> Историческая точка отсчёта — публичный Go 2009 года и стабильная модель Go 1, выпущенного 28 марта 2012 года. Параметров типов ещё нет, но обобщённые программы уже есть.

## Сначала восстановим условия задачи

Представим автора библиотеки начала 2010-х. Нужно один раз написать поиск, сортировку и обход коллекции, а затем применять их к числам, дробям, денежным суммам и пользовательским структурам. Синтаксиса `func Find[T ...]` нет. Нельзя начинать объяснение с того, что этот автор «забыл добавить T»: такой возможности у него не было.

У него есть конкретные типы, методы, интерфейсы, функции как значения, замыкания, срезы и работа с runtime-типами через reflection. Он может отделить поведение от данных и передать алгоритму необходимые операции. Вопрос не в том, возможно ли обобщение, а в том, **какую часть знания о типах можно сохранить на границе библиотечной функции**.

Go стал публичным 10 ноября 2009 года. Go 1 закрепил стабильную основу языка и стандартных библиотек в марте 2012 года. В учебнике мы используем Go 1 как опорную модель и не приписываем все его детали каждой дорелизной сборке. Например, предопределённый тип `error` относится к изменениям Go 1. Источники: [исторический контекст Why Generics?](https://go.dev/blog/why-generics), [объявление Go 1](https://go.dev/blog/go1), [изменения Go 1](https://go.dev/doc/go1).

## Что уже было обобщённым

Встроенный срез позволял хранить конкретные значения разных выбранных типов: `[]int`, `[]string`, `[]Fraction`. Библиотека не обязана была превращать их в общий объектный контейнер. `len`, `append` и `copy` применялись по специальным правилам языка.

Но автор обычной функции не мог объявить аналогичный параметр «срез произвольного E» и связать этот E с типом возвращаемого значения. Между выразительностью встроенных операций и выразительностью пользовательских сигнатур оставался разрыв.

Для работы с поведением уже хватало маленького интерфейса:

```go
type Stringer interface {
    String() string
}

func DescribeStringer(value Stringer) string {
    return value.String()
}
```

Все наши шесть типов имеют метод `String() string`. Поэтому одна DescribeStringer работает с дробью, деньгами и версией без параметров типов и без ручного исследования типа. У операции один и тот же результат — string, независимо от реализации.

Задача «вызови общее поведение» решена. Более трудная задача — «прими значение произвольного типа и верни результат того же или связанного типа». Например, Add у денег возвращает Money, а Add у дроби — Fraction. Именно здесь далее появится затруднение.

## Исторический образец: sort.Interface

В исходниках тега Go 1 пакет sort уже определяет интерфейс коллекции с тремя методами:

```go
type Interface interface {
    Len() int
    Less(i, j int) bool
    Swap(i, j int)
}
```

Сортировка не получает значение неизвестного типа. Она узнаёт длину, сравнивает позиции и переставляет их. Конкретный тип элемента остаётся у реализации этих операций. Это центральный приём раннего Go: **скрыть элемент за действиями, достаточными алгоритму**. Исторический источник: [sort.go из Go 1](https://raw.githubusercontent.com/golang/go/go1/src/pkg/sort/sort.go).

Такой подход не требует наследования от базового класса коллекций. Новый определённый тип с нужными методами удовлетворяет интерфейсу. Программа может расширить набор поддерживаемых коллекций, не переписывая сортировку.

## Чего нельзя рисовать в исторической схеме

Неверно утверждать, что интерфейсы появились после reflection, или что reflection был следующим релизом после интерфейсов. Они сосуществовали в раннем Go. Также генерация исходников была возможна до появления команды `go generate`.

В первых главах мы исследуем несколько доступных тогда решений одного ограничения. Лишь затем перейдём к новым возможностям языка и библиотек. Статья [The Laws of Reflection](https://go.dev/blog/laws-of-reflection) опубликована в 2011 году — это хороший ориентир, показывающий, что reflection не был поздним ответом на отсутствие generics.

## Как устроен наш исторический эксперимент

| Уровень | Что берём из проекта |
|---|---|
| Предметные значения | Fraction, Money, BoxInt, IntValue, Vector2, Version |
| Операции значений | Equal, Compare, Add, String и остальные методы |
| Обобщённый обход | Пакет algorithms без параметров типов и reflection |
| Связь двух уровней | Небольшие адаптеры в коде потребителя |
| Проверка результата | Исполняемые примеры и тесты алгоритмов |

Наш пакет не является копией стандартной библиотеки Go 1. Например, Compare может вернуть error, а сортировка для прозрачности написана вставками. Историческим является способ выражать обобщение через интерфейсы операций. Весь проект собирается современным Go: методы некоторых значений используют более новые библиотеки. Не путайте воспроизведение идеи с обещанием запустить весь репозиторий компилятором 2012 года.

## Что нужно понять перед следующей главой

Почему DescribeStringer легко получает одну общую сигнатуру для разных типов, а Add не получается обобщить так же? Сравните конкретные типы аргументов и результатов, не переходя пока к синтаксису дженериков.
