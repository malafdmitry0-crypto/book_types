# 6. Ограничения интерфейсов: свой тип, срезы и указатели

Код главы: [example_test.go](../../lessons/interfaces/example_test.go) · [failures_test.go](../../lessons/failures/failures_test.go).


> Stringer объединяет одинаковое поведение. Теперь проверим, может ли обычный интерфейс сохранить связь между типом аргумента и типом результата.

Мы научились вызывать общий String у дроби и денег. Следующий вопрос сложнее: можно ли таким же образом сложить значения и сохранить их собственный тип? Именно здесь видны границы обычного интерфейса.

## Почему одинаковое имя Add не даёт общего метода

Наши методы имеют конкретные сигнатуры:

```text
Fraction.Add(Fraction) → (Fraction, error)
Money.Add(Money)       → (Money, error)
```

Соблазнительно заменить конкретные типы одним интерфейсом:

```go
type Addable interface {
    Add(Addable) (Addable, error)
}

// Не компилируется: у Fraction другая сигнатура Add.
// var _ Addable = fraction.Fraction{}
```

Интерфейс Addable требует метод, который принимает Addable и возвращает Addable. Fraction.Add принимает только Fraction и возвращает Fraction. Go не вставляет автоматические обёртки для параметров и результатов методов. Совпасть должны сами сигнатуры, а не только имя и число аргументов. Это правило также разобрано в [FAQ о сигнатурах методов](https://go.dev/doc/faq#covariant_types).

Здесь есть существенная разница обещаний. Если бы и дроби, и деньги удовлетворяли Addable, контракт разрешал бы передать деньги в Add дроби: параметр объявлен как Addable. Он не означает «значение того же конкретного типа, что и получатель».

Даже интерфейс с методом Add(Fraction) (Addable, error) не подошёл бы к исходному методу: его результат Fraction не совпадает с объявленным результатом Addable. То, что отдельное значение можно присвоить интерфейсу, не меняет тип всей функции.

## Интерфейс для сложения конкретных дробей возможен

```go
type FractionAdder interface {
    Add(fraction.Fraction) (fraction.Fraction, error)
}

func AddFraction(left FractionAdder, right fraction.Fraction) (fraction.Fraction, error) {
    return left.Add(right)
}

var _ FractionAdder = fraction.Fraction{}
```

Такой код корректен и обходится без адаптера. Но связь с Fraction явно осталась в параметре и результате. Этот контракт допускает разные реализации операции над дробью; он не превращается в общий Sum для дробей, денег и целых.

Термин «обобщение» здесь требует уточнения: можно обобщить реализацию поведения, сохранив фиксированные типы аргументов, а можно захотеть обобщить и сами эти типы. Обычные интерфейсы прекрасно решают первую задачу, но не выражают произвольную связь «аргумент и результат имеют тот же конкретный тип».

## Можно ли переделать Add под interface{}

Технически можно спроектировать метод Add(interface{}) (interface{}, error), извлекать внутри Fraction через assertion и возвращать ошибку для неподходящего типа. Но существующий Add пришлось бы изменить или поместить такую операцию в обёртку: перегрузить два метода с именем Add у одного базового типа нельзя.

Тогда вызов с Money станет допустим на этапе компиляции, а проверку совместимости возьмёт на себя реализация. Результат тоже будет иметь статический тип interface{}; чтобы получить Fraction, вызывающий должен проверять его конкретный тип. Это осознанный обмен статических гарантий на динамическую обработку, а не бесплатное устранение адаптера.

В нашем moneySum сложение остаётся Money.Add(Money). Общий алгоритм вызывает Add(index), а адаптер берёт конкретные деньги из своего среза. Проверка совместимости валют остаётся предметной проверкой даже при таком статически согласованном типе.

## Почему []Fraction нельзя передать как []Stringer

```go
func PrintAll(values []Stringer) {
    for _, value := range values {
        fmt.Println(value.String())
    }
}
```

```go
fractions := []fraction.Fraction{
    {Numerator: 1, Denominator: 2},
}
// PrintAll(fractions) // Не компилируется: []Fraction не является []Stringer.
```

Соответствие интерфейсу у элемента не распространяется автоматически на контейнер. Типы []fraction.Fraction и []Stringer различаются. Go не выполняет скрытый цикл присваиваний элементов; нужен отдельный срез. См. [FAQ о срезах интерфейсов](https://go.dev/doc/faq#convert_slice_of_interface).

```go
var printable []Stringer
if fractions != nil {
    printable = make([]Stringer, len(fractions))
}
for i, value := range fractions {
    printable[i] = value
}
PrintAll(printable)
```

Теперь каждый элемент printable — интерфейсное значение. Оно может хранить и Fraction, и Money. Присваивание printable[0] = money.Money{Currency: "USD"} было бы допустимо и заменило бы элемент нового среза, не элемент исходного fractions.

Это также помогает увидеть, почему нельзя просто обращаться к одному срезу как к другому: []Stringer разрешает записывать значения разных подходящих типов, а []Fraction разрешает хранить только дроби. В нашем примере структуры копируются по значениям. Если упаковать указатели, сами указатели будут скопированы, но объекты за ними могут остаться общими.

Замыкание и коллекционный адаптер позволяют обходить исходный []Fraction без такого поэлементного упаковывания.

## Почему одна Fraction всё равно не подходит нашему Find

Наш Find просит Len и Match(index). Это контракт коллекции вместе с условием, а не контракт отдельной дроби. Наличие у Fraction методов String, Equal и Add не удовлетворяет этим другим требованиям.

Можно было бы придумать объект поиска из одного элемента с Len, возвращающим 1. Но смысл проверки всё равно пришлось бы где-то задать. Такой объект фактически стал бы адаптером одиночного значения; он не решил бы задачу обхода произвольного среза.

У самого []Fraction также нет методов Len и Match. А если они нужны именно выбранному интерфейсному API, их предоставляет fractionQuery. Для API FindIndex достаточно длины и замыкания — отдельные методы вообще не требуются.

## Значение и указатель: ещё одна граница соответствия

Методы нашего Fraction объявлены с получателем по значению. Поэтому и Fraction, и *Fraction удовлетворяют Stringer. У moneySum метод Add(index) объявлен с получателем-указателем, поскольку он изменяет Total. Интерфейсу Summable удовлетворяет *moneySum, а значение moneySum — нет.

Вызов sum.Add(0) для адресуемой переменной sum может выглядеть рабочим: Go допускает неявное взятие адреса при таком вызове метода. Но присваивание sum интерфейсу не добавляет недостающие методы. В algorithms.Sum нужно передать &sum. Правила: [наборы методов в спецификации](https://go.dev/ref/spec#Method_sets).

Отдельно от соответствия типов стоит пригодность значения. Нулевой указатель может удовлетворять интерфейсу, но вызов метода через него может паниковать. Интерфейс, содержащий типизированный nil-указатель, сам не равен nil. Поэтому проверка интерфейса на nil не доказывает, что его конкретное значение пригодно для вызова.

## Как выбрать границу обобщения

| Что нужно потребителю | Подходящий вариант | Какое ограничение остаётся |
|---|---|---|
| Вызвать String у разных значений | Передать само значение как Stringer | Доступны только методы контракта |
| Складывать именно дроби | Конкретный параметр или FractionAdder | Сигнатура связана с Fraction |
| Искать в разных срезах | Длина и замыкание | Длину и захваченные данные согласует вызывающий |
| Передавать набор операций коллекции | Predicate, Ordered, Sortable и адаптер | Нужно реализовать методы протокола |
| Хранить разнородные значения | Срез интерфейсов | Конкретные операции требуют подходящего контракта или проверок |
| Сохранить собственный тип аргумента и результата для разных типов | Параметры типов и ограничения | Предметные законы и ошибки всё равно проверяются отдельно |

В главе о дженериках мы вернёмся к Addable[T] с методом Add(T) (T, error). Для T = Fraction контракт потребует именно Fraction.Add(Fraction), для T = Money — Money.Add(Money). Но этот механизм относится к более позднему этапу: в раннем варианте общий алгоритм работал с индексами, а конкретная операция оставалась в замыкании или адаптере.
