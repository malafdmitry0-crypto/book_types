# 16. История стандартной библиотеки через одну задачу

Код главы: [example_test.go](../../examples/example_test.go).


> Проследим реальные изменения API на сортировке и поиске, а не выдумаем линейную смену механизмов.

Свяжем изученные решения с настоящими API Go. На сортировке особенно хорошо видно, что менялось в интерфейсе вызова и какие старые варианты продолжают иметь смысл.

## Четыре формы сортировки пользователей

Все следующие варианты решают одну задачу: упорядочить `users` по возрасту. Они отличаются местом, где задаются операции и проверяются типы.

```go
// Старый интерфейсный API: три метода у адаптера UsersByAge.
sort.Sort(UsersByAge(users))

// Go 1.8+: срез как interface{}, сравнение через индексы.
sort.Slice(users, func(i, j int) bool {
    return users[i].Age < users[j].Age
})

// Go 1.21+: типизированные элементы в callback.
slices.SortFunc(users, func(a, b User) int {
    return cmp.Compare(a.Age, b.Age)
})

// Для типов со встроенным порядком callback вообще не нужен.
slices.Sort([]int{3, 1, 2})
```

У `sort.Slice` нет требований реализовать методы адаптера. Но первый параметр не гарантирует срез на этапе компиляции, а замыкание способно случайно сравнивать элементы другой коллекции. `slices.SortFunc` связывает тип элемента и параметры сравнения статически.

`sort.Slice` использует runtime-механизмы для доступа к переданному срезу и перестановок. Это не означает, что он вызывает `reflect.Call` для каждого сравнения: callback здесь обычная функция от индексов. Поэтому его нельзя оценивать по скорости учебного `MapReflect` с поэлементными динамическими вызовами. Источники: [sort.Slice](https://pkg.go.dev/sort#Slice), [Go 1.8](https://go.dev/doc/go1.8#sort).

## Реальная временная линия

| Период | Изменение | Какое ограничение стало проще обойти |
|---|---|---|
| Ранний Go / Go 1 | Интерфейсы, функции, замыкания, reflection | Общее поведение и runtime-работа с типами без параметров типов |
| Go 1.4, 2014 | `go generate` | Единый способ запускать внешнюю специализацию исходника |
| Go 1.8, 2017 | `sort.Slice`, `reflect.Swapper` | Сортировка среза без трёх методов отдельного адаптера |
| 2019 | Публичное обсуждение мотивации generics | Сформулирована проблема повторяемых контейнерных алгоритмов |
| Go 1.18, 2022 | Параметры типов и ограничения | Связи типов выражаются в библиотечной сигнатуре |
| Go 1.21, 2023 | `slices`, `maps`, `cmp` | Типизированные обобщённые алгоритмы входят в стандартную библиотеку |
| Go 1.23, 2024 | `iter`, range-over-func, функции обхода в `slices` и `maps` | Общий протокол последовательностей и композиция обхода |

Это выбранные вехи темы, а не утверждение, что обобщённое программирование остановилось в Go 1.23. Для этой линии важнее изменение границы абстракции, чем перечисление каждого последующего релиза.

Источники дат: [Go 1.18](https://go.dev/doc/go1.18), [Go 1.21](https://go.dev/doc/go1.21), [Go 1.23](https://go.dev/doc/go1.23). Интерфейсы и reflection не стали ненужными после этих релизов.

## Где наши алгоритмы встречаются в stdlib

| Учебная задача | Средство Go | Особенность |
|---|---|---|
| Первый элемент по предикату | `slices.IndexFunc` | Индекс или `-1` |
| Есть ли подходящий элемент | `slices.ContainsFunc` | bool |
| Все удовлетворяют условию | Отрицание `ContainsFunc` для отрицательного предиката | Сохраняет раннюю остановку |
| Отсортированный поиск | `slices.BinarySearch` / `BinarySearchFunc` | Требует согласованного порядка |
| Преобразовать каждый E в R | Учебная `Map` / явный цикл | В рассматриваемом API slices отдельной Map нет |
| Все пары индекс–значение | `slices.All` | Итератор, не логический All |
| Собрать итератор в срез | `slices.Collect` | Материализация результата |

```go
// import "slices"
index := slices.IndexFunc(users, adult)
all := !slices.ContainsFunc(users, func(u User) bool {
    return !active(u)
})
```

Названия Find, All и Map в учебнике обозначают общие задачи библиотеки алгоритмов, а не буквальную копию API Go. `map[K]V` — ассоциативный контейнер, а алгоритм Map — поэлементное преобразование; они тоже не тождественны. Справочник API: [slices](https://pkg.go.dev/slices).

## Почему это полезнее истории синтаксиса

Если смотреть только на новые квадратные скобки, непонятно, почему `sort.Sort` было недостаточно и почему `sort.Search` не нуждался в E. Если сравнить операции, всё становится яснее: сортировка могла скрыть перестановки за методами, индексный поиск — исключить элемент из сигнатуры, а Map нуждался в отношении между входным и выходным типами.

## Проверка понимания
