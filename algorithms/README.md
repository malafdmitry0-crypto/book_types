# Алгоритмы в стиле раннего Go

Один пакет `gotypes/algorithms`, обычные интерфейсы и адаптеры коллекций. В реализации нет параметров типов, reflection, `any`, generic-пакетов `slices`/`cmp` или упаковки элементов в `[]interface{}`.

Это учебная реализация исторического подхода, а не копия исходников старой стандартной библиотеки. Ориентир — [sort.Interface](https://pkg.go.dev/sort#Interface): алгоритм знает операции над позициями коллекции, конкретные данные обслуживает адаптер. Интерфейсы как форма обобщённого программирования и ограничения такого подхода обсуждаются в [Why Generics?](https://go.dev/blog/why-generics).

## Отдельная альтернатива без адаптеров

В [closures](closures/README.md) реализован FindIndex через длину и замыкание. В [примерах](closures/example_test.go) один алгоритм ищет дроби и деньги без структур с Len и Match.

## API

| Алгоритм | Интерфейс | Результат |
|---|---|---|
| `Find` | `Predicate`: Len, Match | Первый индекс или -1; error |
| `All` | `Predicate`: Len, Match | Все подходят? bool; error |
| `Any` | `Predicate`: Len, Match | Есть подходящий? bool; error |
| `Map` | `Mapping`: Len, Apply | error; типизированный результат хранит адаптер |
| `Sum` | `Summable`: Len, Add | error; типизированный аккумулятор хранит адаптер |
| `Min`, `Max` | `Ordered`: Len, Compare | Первый индекс экстремума или -1; error |
| `Sort` | `Sortable`: Len, Compare, Swap | error; меняет порядок на месте |

Имена Find/All/Map — имена учебной библиотеки, не утверждение о наличии таких функций в первых релизах стандартного Go. Сортировка реализована простыми стабильными вставками: O(n²) в худшем случае, O(1) дополнительной памяти. Это позволяет читать алгоритм целиком и видеть обращения к интерфейсу.

## Почему нужны адаптеры

`Fraction.Add(Fraction) (Fraction, error)` и `Money.Add(Money) (Money, error)` похожи по форме, но это разные конкретные сигнатуры. Без параметра типа нельзя объявить единый интерфейс с таким отношением «принимает и возвращает собственный тип» для обеих структур.

Поэтому Summable описывает `Add(i int) error`, а не сложение произвольного элемента. Адаптер знает тип своего среза и аккумулятора, берёт элемент по индексу и вызывает его настоящий типизированный метод. Библиотека организует обход и остановку при ошибке.

Аналогично Mapping описывает `Apply(i int) error`. Преобразование Fraction → string и создание `[]string` находятся у вызывающего. Алгоритм Map не может сам вернуть произвольный `[]R` со статической связью с callback — именно это ограничение позже устраняют параметры типов.

В Sortable метод `Compare` возвращает ошибку. Это наше расширение исторической идеи: у стандартного `sort.Interface` метод `Less` возвращает только bool. Изменение нужно, чтобы не скрывать ошибки наших денежных и дробных типов.

## Примеры на типах проекта

В [example_test.go](example_test.go) приведены полные компилируемые адаптеры рядом с их использованием:

- `fractionQuery`: конкретный `[]Fraction` и callback; общий Find ищет `2/4` по математическому равенству с `1/2`.
- Тот же `fractionQuery`: All проверяет положительность, Any ищет нулевую дробь.
- `fractionText`: Map получает строки через Fraction.String, сохраняя конкретный `[]string` у вызывающего.
- `moneySum`: Sum вызывает Money.Add, начиная с нулевой суммы в явно заданной валюте.
- `boxes`: определённый срез BoxInt с Len, Compare и Swap; используется для Min, Max и Sort.

Тесты также суммируют дроби тем же алгоритмом Sum с другим адаптером. Пакет algorithms не импортирует ни один предметный тип: зависимости остаются на стороне потребителя.

## Контракт обхода

Len должен быть неотрицательным и оставаться неизменным во время алгоритма. Адаптер обслуживает все индексы от 0 до Len()-1. Nil-интерфейсы, изменение длины и panic внутри callback не обрабатываются автоматически.

Find и Any прекращают обход на первом совпадении; All — на первом несовпадении. Пустой вход даёт -1, false и true соответственно. Ошибка прекращает обход и возвращается без подмены; bool или индекс при ошибке не используются.

Map и Sum идут слева направо. При ошибке результат может быть частично заполнен, аккумулятор — частично обновлён. Отката нет, последующие элементы не обрабатываются. Приведённые адаптеры сначала вычисляют очередное значение, а затем записывают его, поэтому не записывают результат неуспешного шага. Это свойство адаптера, не гарантия для произвольного Apply/Add.

Начальное значение Sum задаёт вызывающий: для дробей — 0/1, для денег — 0 с валютой. Пустой Sum оставляет аккумулятор как есть; перед независимым повторным суммированием его нужно сбросить. Аналогично nilness и размер результата Map определяет вызывающий.

Min/Max при равенстве сохраняют первый индекс. Пустые коллекции возвращают -1. Для единственного элемента сравнение не нужно, поэтому общий алгоритм не обнаружит невалидный одиночный элемент. Если требуется проверка каждого значения, её выполняют перед вызовом.

Sort стабилен: равные элементы сохраняют относительный порядок. Если сравнение вернуло ошибку, предыдущие перестановки остаются. Для Money с разными валютами нельзя превращать ошибку Compare в произвольный ответ «меньше» — нужно вернуть её вызывающему.

## Проверка

Из корня проекта:

```sh
go test ./algorithms
go test ./...
go vet ./...
```

Примеры проверяют вывод, а тесты — пустые коллекции, короткое замыкание, совпадение первого экстремума, стабильность сортировки, порядок обработки, остановку по ошибке и сохранение частичного результата. Проверки выполняются современным Go 1.25.4; весь проект требует Go 1.23 и не объявляется запускаемым на Go 1.0. Историческим является способ обобщения алгоритмов.
