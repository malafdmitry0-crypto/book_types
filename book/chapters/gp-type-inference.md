# 17. Вывод типов: когда аргументы типов можно не писать

Код главы: [inference.go](../../lessons/generic/inference.go) · [inference_example_test.go](../../lessons/generic/inference_example_test.go).


> Вывод аргументов типов сокращает запись вызова, но не меняет его смысл: компилятор восстанавливает ровно те аргументы, которые можно было бы написать явно.

В предыдущих главах мы писали `Map(users, name)` и ни разу `Map[User, string](users, name)`. Компилятор выводил аргументы типов сам. Это удобно, пока работает, и сбивает с толку, когда не работает. Разберём, откуда берётся информация для вывода, где её нет и что изменилось в Go 1.21. Источник: [спецификация, Type inference](https://go.dev/ref/spec#Type_inference).

## Унификация типов аргументов

```go
users := []user{{"Аня", 30}, {"Борис", 17}}
names := generic.Map(users, userName)              // E = user, R = string выведены
same := generic.Map[user, string](users, userName) // то же самое явно
```

Сигнатура `Map[E, R any](src []E, transform func(E) R)` сопоставляется с типами аргументов: `[]E` против `[]user` даёт `E = user`, затем `func(E) R` против `func(user) string` даёт `R = string`. Этот процесс называется унификацией. В этом примере информация приходит из типов аргументов вызова; тело функции, оператор `return` и место, куда попадёт результат вызова, в выводе не участвуют. Ограничения тоже могут дать дополнительную информацию — это разобрано ниже. Обе строки выше порождают одну и ту же инстанциацию `Map[user, string]`.

## Когда выводить не из чего

```go
func Zero[T any]() T {
	var zero T
	return zero
}
```

У `Zero` нет параметров, и `T` встречается только в результате. Вызов `generic.Zero()` отвергается с сообщением `cannot infer T`; см. [cannot_infer.go](../../lessons/failures/testdata/cannot_infer.go). Не поможет и `var x int = generic.Zero()`: тип переменной не является источником для вывода при вызове. Единственная форма — `Zero[int]()`.

Аргументы типов задаются слева направо, и список можно оборвать: оставшиеся параметры компилятор выведет из аргументов. Это частичная инстанциация.

```go
func Convert[To, From Number](x From) To {
	return To(x)
}
```

```go
n := 42
wide := generic.Convert[int64](n) // To задан явно, From = int выведен
```

Порядок параметров в `Convert` выбран не случайно: `To` стоит первым, потому что его всё равно придётся написать, а `From` вторым, потому что он следует из аргумента. В обратном порядке вызов потребовал бы `Convert[int, int64](n)`. Правило проектирования: параметры, которые вызывающий обязан указывать, идут первыми.

## Нетипизированные константы

```go
func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}
```

```go
fmt.Printf("%T %v\n", generic.Max(1, 2), generic.Max(1, 2))         // int 2
fmt.Printf("%T %v\n", generic.Max(1, 2.5), generic.Max(1, 2.5))     // float64 2.5
```

Литералы `1` и `2.5` не имеют типа, и `T` нужно выбрать. Для `Max(1, 2)` берётся тип по умолчанию, `int`. Для `Max(1, 2.5)` до Go 1.21 вывод завершался ошибкой: первая константа задавала `int`, вторая в него не помещалась. Начиная с Go 1.21 нетипизированные константы одного параметра типа рассматриваются вместе, по тем же правилам, что операнды выражения `1 + 2.5`: побеждает «более широкий» вид константы, и `T = float64`. Смешивать виды, между которыми такого правила нет, по-прежнему нельзя: `Max(1, "go")` даёт `mismatched types untyped int and untyped string`; см. [mixed_constants.go](../../lessons/failures/testdata/mixed_constants.go). Источник: [Go 1.21](https://go.dev/doc/go1.21#language).

## Generic-функция как аргумент и как значение

```go
func Identity[T any](x T) T { return x }
```

```go
var f func(int) int = generic.Identity // Go 1.21+: T = int из типа переменной
doubled := generic.Map([]int{1, 2}, generic.Double[int])
inferred := generic.Map([]int{1, 2}, generic.Double) // Go 1.21+: T выведен из []int
```

До Go 1.21 неинстанцированную generic-функцию нельзя было ни присвоить переменной, ни передать аргументом: сначала требовалось написать `Identity[int]`. С Go 1.21 при присваивании переменной функционального типа аргументы типов выводятся из типа переменной, а при передаче в другую функцию — из типа параметра. В `Map([]int{1, 2}, Double)` сначала `E = int` из первого аргумента, затем `Double` инстанцируется как `func(int) int`, и уже из него следует `R = int`. Go 1.27 распространил то же правило на конверсии вида `(func(int) int)(Identity)`; здесь это только упоминание, код для нового компилятора вынесен в справочник, глава [13](13-modern-generics.md). Источники: [Go 1.21](https://go.dev/doc/go1.21#language), [Go 1.27](https://go.dev/doc/go1.27#language).

## Вывод из ограничения

Ограничения тоже участвуют в выводе, но ограниченным образом. Методы, перечисленные в ограничении, тип не выбирают: компилятор не подбирает `T` по принципу «у какого типа есть метод `Add`». Начиная с Go 1.21 сигнатуры методов известного типа также могут помогать выводить связанные параметры из ограничения. Кроме того, если ограничение задаёт форму `~[]E`, то из уже известного аргумента типа извлекаются его составляющие.

```go
func Clone[S ~[]E, E any](src S) S {
	if src == nil {
		return nil
	}
	out := make(S, len(src))
	copy(out, src)
	return out
}
```

```go
copied := generic.Clone(ages{3, 9, 5}) // S = ages из аргумента, E = int из ограничения ~[]E
fmt.Printf("%T %v %d\n", copied, copied, copied.Oldest()) // generic_test.ages [3 9 5] 9
```

Аргумент даёт только `S = ages`. Никакой аргумент вызова не имеет типа `E`. Но ограничение `S ~[]E` требует, чтобы underlying type у `ages` был срезом, и унификация `[]int` с `[]E` даёт `E = int`. Это называют constraint type inference. Именно оно позволяет сигнатуре `Clone[S ~[]E, E any]` из главы об ограничениях не требовать от вызывающего двух явных аргументов типов. Источник: [Deconstructing Type Parameters](https://go.dev/blog/deconstructing-type-parameters).

## Практическое правило

Если вывод не сработал, компилятор говорит об этом сразу и однозначно; ответ — написать аргументы типов явно, а не искать обходную форму вызова. Явная инстанциация уместна и там, где вывод сработал бы: для параметров, встречающихся только в результате, `Zero[int]()` и `Convert[int64](n)` читаются как часть договора функции. Наоборот, писать `Map[user, string](users, userName)` не нужно: аргументы уже сказали компилятору и читателю всё необходимое. Вывод типов не создаёт новых инстанциаций и не выбирает «лучшую» из нескольких; либо аргументы типов определяются однозначно, либо вызов не компилируется.

## Проверка понимания

Для функции `Keys[Map ~map[K]V, K comparable, V any](m Map) iter.Seq[K]` из пакета `maps` укажите, какие параметры типов выводятся из аргумента, а какие — из ограничения, и почему вызов `maps.Keys(index)` для `index map[string]int` не требует ни одного явного аргумента типа.
