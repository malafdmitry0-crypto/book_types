Библиотека алгоритмов: что именно мы хотим обобщить

Исходник Markdown ↗
Центральный вопрос: как один раз написать Find, All и Map для разных типов, не потеряв проверку связей между данными, операцией и результатом?

Сквозная задача

Мы пишем библиотеку алгоритмов над коллекциями. Её пользователи хранят числа, строки, заказы, пользователей и собственные структуры. Алгоритму поиска не должно быть дела до того, что означает поле Age: он перебирает элементы и останавливается на первом совпадении. Бизнес-условие передаёт вызывающая программа.

Go
type User struct {
    Name   string
    Age    int
    Active bool
}

users := []User{
    {Name: "Аня", Age: 17, Active: true},
    {Name: "Борис", Age: 31, Active: true},
    {Name: "Вера", Age: 25, Active: false},
}

adult := func(u User) bool { return u.Age >= 18 }
active := func(u User) bool { return u.Active }
name := func(u User) string { return u.Name }

Три запроса к этим данным: найти первого совершеннолетнего; проверить, что все активны; получить имена в исходном порядке. Ожидаемые результаты: индекс 1, значение false, срез []string{"Аня", "Борис", "Вера"}.

Позже приходит []Order. Требуется тот же обход, но с другими условиями и результатами. Именно это изменение будет проверять каждую архитектуру в следующих главах.

Контракт раньше синтаксиса

Алгоритм учебной библиотекиРезультатПустой входКогда останавливается
Find(xs, pred)Индекс первого совпадения, иначе -1-1На первом true
All(xs, pred)Все элементы удовлетворяют предикату?trueНа первом false
Map(xs, fn)Новый срез результатов в исходном порядкеnil остаётся nil; ненулевой пустой срез остаётся ненулевымПосле всех элементов

Название Find здесь означает поиск индекса. Это соответствует задаче slices.IndexFunc, а не обещанию стандартного имени Go. Для произвольного итератора мы позже изменим контракт: у последовательности может не быть индекса.

Вызовы callback идут последовательно слева направо. Find и All не проверяют элементы после остановки. При пустом входе callback не вызывается. Предполагаем корректный ненулевой callback; panic внутри него не скрываем. Map не меняет входной срез сам, но пользовательская функция может иметь побочные эффекты. Копирование результата не означает глубокого копирования объектов.

All на пустой последовательности даёт true: нет контрпримера к утверждению «все подходят». Это позволяет последовательно определить All(xs, p) как отсутствие элемента, для которого p ложно.

Четыре независимые оси обобщения

ОсьПример измененияЧто нужно отделить от алгоритма
ПоведениеСовершеннолетний → активныйПредикат

Функция с callback может обобщать поведение, оставаясь жёстко привязанной к User. Интерфейс коллекции может обобщать источник, ничего не сообщая о типе элемента. Дженерики могут обобщать элемент, продолжая принимать только срез. Нельзя оценивать универсальность API одним флагом «generic / не generic».

Связь типов — главный критерий

Желаемая форма Map: вход содержит E, функция принимает именно E и выдаёт R, результат содержит именно R. Буквы должны обозначать согласованные типы во всей сигнатуре.

Схема
[]E  +  func(E) R  →  []R
 User      User string   string
 Order     Order int     int

Если вызывающий передаёт []User и func(Order) string, кто обнаружит ошибку: компилятор, проверка при входе в функцию или assertion при обработке третьего элемента? Это гораздо полезнее, чем вопрос «можно ли вообще написать Map».

Для сравнения фиксируем также цену адаптации, создание промежуточного контейнера, место runtime-проверок и необходимость повторять реализацию. Оценки производительности будем отделять от гарантий языка.

История не является лестницей замен

Интерфейсы и reflection существовали в раннем Go одновременно. Генерация кода тоже не ждала специальной команды. Главы расположены по усложнению требований, а реальные даты разобраны отдельно. Интерфейсы уже были средством обобщённого программирования; Go 1.18 добавил новый способ выражать связи между типами. Эта постановка прямо обсуждалась до принятия дженериков в Why Generics?.

Проверка понимания

Конкретные типы и функции высшего порядка

Исходник Markdown ↗
Отделим переиспользование поведения от переиспользования алгоритма для разных типов.

Три типобезопасных алгоритма для User

Go
func FindUser(src []User, pred func(User) bool) int {
	for i, user := range src {
		if pred(user) {
			return i
		}
	}
	return -1
}
Go
func AllUsers(src []User, pred func(User) bool) bool {
	for _, user := range src {
		if !pred(user) {
			return false
		}
	}
	return true
}
Go
func MapUserNames(src []User, transform func(User) string) []string {
	if src == nil {
		return nil
	}
	out := make([]string, len(src))
	for i, user := range src {
		out[i] = transform(user)
	}
	return out
}

Вызов FindUser(users, adult) типобезопасен: компилятор связывает параметр callback с элементом среза. В MapUserNames(users, name) он также знает тип результата. Никакой динамической проверки типа не требуется.

Но две степени свободы закрыты заранее. FindUser принимает только []User; MapUserNames возвращает только []string. Название с Names — лишь напоминание о выбранном сценарии: переданный callback может возвращать любой текст, а не обязательно имя.

Callback уже является обобщением

Сравните три вызова одной функции:

Go
FindUser(users, func(u User) bool { return u.Age >= 18 })
FindUser(users, func(u User) bool { return !u.Active })
FindUser(users, func(u User) bool { return len(u.Name) > 6 })

Меняется условие, а порядок обхода и ранняя остановка остаются в библиотеке. Функция, принимающая функцию, называется функцией высшего порядка. Это возможность раннего Go, а не нововведение дженериков.

У такого разделения уже есть практическая ценность: ошибку в ранней остановке исправляют один раз для всех условий над User. Поэтому считать весь код до Go 1.18 «необобщённым» неверно.

Где начинается дублирование

Теперь требуется искать Order. Если оставить эту архитектуру, появится FindOrder. Тело совпадёт с FindUser, а типы в сигнатуре изменятся. Для Map ситуация хуже: новые комбинации входа и выхода порождают новые специализации.

ТребованиеНужна новая реализация?
Другое условие над UserНет, другой callback
Поиск по []OrderДа, FindOrder
User → string с другой логикойНет
User → intДа, другой Map
Order → stringДа, другой Map

Не всегда стоит устранять это дублирование: два коротких локальных цикла могут быть проще собственной библиотеки. Но для библиотеки общего назначения повторение становится частью публичного API и тестовой нагрузки.

Встроенные контейнеры уже умели больше

В Go до 1.18 можно было создать []User, []Order, map[string]User; len, append и copy работали с разными типами в рамках своих специальных правил. Разработчик обычной функции не мог объявить аналогичное отношение «срез произвольного E» в своей сигнатуре.

Это объясняет запрос на параметры типов: дать библиотечному коду часть выразительности, уже доступной встроенным операциям. Источник исторической постановки: Why Generics?.

Что потребуем от следующего подхода

Хотим оставить один цикл и для User, и для Order. Возможно, библиотеке вообще не нужно получать элементы? Если алгоритм только спрашивает «совпал ли элемент с индексом i», достаточно передать ему индексы и действие над ними.

Индексы и замыкания: обобщение без типа элемента

Исходник Markdown ↗
Универсальный алгоритм иногда получается, если полностью исключить элемент из его API.

Поиск как работа с индексами

Go
func FindIndex(n int, pred func(int) bool) int {
	for i := 0; i < n; i++ {
		if pred(i) {
			return i
		}
	}
	return -1
}

Тип пользователя нигде не упоминается. При этом callback внутри вызывающего кода остаётся обычной типизированной функцией:

Go
index := FindIndex(len(users), func(i int) bool {
    return users[i].Age >= 18
})

Замыкание захватывает users. Алгоритм получает только длину и ответ на вопрос для индекса. Для []Order изменится замыкание, но библиотечный цикл останется тем же.

Go
func AllIndex(n int, pred func(int) bool) bool {
	return FindIndex(n, func(i int) bool { return !pred(i) }) == -1
}

AllIndex показывает ещё один уровень переиспользования: универсальная проверка выражается через поиск контрпримера. Это сохраняет раннюю остановку и true для пустого входа.

Аналог в стандартной библиотеке: sort.Search

sort.Search(n, f) тоже знает индексы, а не элементы. Но он выполняет бинарный поиск: предикат должен быть сначала ложным, а затем истинным, без обратного перехода. Если подходящего индекса нет, возвращается n, не -1.

Go
// import "sort"
ages := []int{17, 25, 31} // уже отсортированы
index := sort.Search(len(ages), func(i int) bool {
    return ages[i] >= 18
}) // 1

Нельзя заменить наш линейный FindIndex на sort.Search для произвольного users: данные из первой главы не отсортированы по любой возможной проверке. Общая форма callback не означает одинаковый контракт алгоритма. Источник: sort.Search.

Map обнаруживает границу

Можно спрятать и чтение, и запись в замыкание:

Go
func MapInto(n int, assign func(int)) {
	for i := 0; i < n; i++ {
		assign(i)
	}
}
Go
var names []string
if users != nil {
    names = make([]string, len(users))
}
MapInto(len(users), func(i int) {
    names[i] = users[i].Name
})

Этот код типобезопасен. Но библиотека теперь организует только цикл: создание []string, выбор размера и связь результата с функцией находятся у вызывающего. MapInto не способен самостоятельно вернуть срез типа, вычисленного из типа callback, потому что этот тип вообще не входит в его сигнатуру.

Кроме того, компилятор не проверит, что n совпадает с длиной именно захваченного среза. Передать длину одной коллекции и индексировать другую возможно. Это ошибка договора между аргументами, а не ошибка типа переменной.

Что обобщили, что переложили

СвойствоИндексный подход
Один цикл для разных элементовДа
Callback видит конкретный типДа, через замыкание
Дополнительный []interface{}Не нужен
Библиотека возвращает типизированный []RНет, результат создаёт вызывающий
Связь длины и источникаДоговор, а не проверка компилятора
Работа без случайного доступаПотребует другого протокола обхода

Здесь нет утраты типов во всём приложении: информация остаётся внутри замыкания. Мы сознательно убрали её с границы библиотеки. Для поиска это часто отличный компромисс. Для полноценного Map публичный API оказывается беднее желаемого.

Переход к интерфейсам

Длину, источник и проверку можно связать в один объект. Тогда алгоритм получит протокол поведения коллекции вместо нескольких несвязанных аргументов. Так возникает следующий подход.

Проверка понимания

Интерфейсы: алгоритм через минимальный набор операций

Исходник Markdown ↗
Интерфейс позволяет алгоритму не знать представление данных, если все нужные действия выражены методами.

Сначала настоящий пример: sort.Interface

Исторический sort.Sort принимает объект с методами Len, Less, Swap. Он не извлекает «универсальный элемент». Для сортировки достаточно узнавать длину, сравнивать позиции и переставлять их. Именно поэтому алгоритм может работать с разными коллекциями без знания типа элемента.

Go
// import "sort"
type UsersByAge []User

func (s UsersByAge) Len() int           { return len(s) }
func (s UsersByAge) Less(i, j int) bool { return s[i].Age < s[j].Age }
func (s UsersByAge) Swap(i, j int)     { s[i], s[j] = s[j], s[i] }

// sort.Sort(UsersByAge(users))

Конверсия в UsersByAge добавляет доступ к методам определённого типа; данные среза при этом остаются общими. Общая сортировка управляет порядком вызовов, адаптер выполняет конкретные операции. См. sort.Interface.

Такой же ход для Find и All

Go
type MatchSequence interface {
    Len() int
    Match(int) bool
}

type UserQuery struct {
    Values []User
    Pred   func(User) bool
}

func (q UserQuery) Len() int         { return len(q.Values) }
func (q UserQuery) Match(i int) bool { return q.Pred(q.Values[i]) }
Go
func FindInterface(src MatchSequence) int {
	for i := 0; i < src.Len(); i++ {
		if src.Match(i) {
			return i
		}
	}
	return -1
}
Go
func AllInterface(src MatchSequence) bool {
	for i := 0; i < src.Len(); i++ {
		if !src.Match(i) {
			return false
		}
	}
	return true
}

Вызовы: FindInterface(UserQuery{users, adult}) и AllInterface(UserQuery{users, active}). Реализация интерфейса определяется набором методов; отдельного объявления implements нет. Новый адаптер для заказов использует тот же алгоритм.

MatchSequence объединяет источник с условием. Можно выбрать другой дизайн и передавать предикат отдельно, но тогда возникает вопрос: какого типа его аргумент, если элемент коллекции скрыт? Эта деталь является частью проектирования обобщённого API.

Map тоже можно выразить через интерфейс

Go
type MappingJob interface {
    Len() int
    Apply(int)
}
Go
func RunMap(job MappingJob) {
	for i := 0; i < job.Len(); i++ {
		job.Apply(i)
	}
}

Адаптер UserNameJob хранит Source []User, Target []string и Fn func(User) string. Метод Apply(i) выполняет присваивание. Вызывающий создаёт результат, передаёт задание и получает заполненный срез обратно через своё значение Target. Полная реализация находится в algorithms.go.

Это законное обобщение. Однако алгоритм RunMap не выражает отношение []E + func(E) R → []R. Оно скрыто в конкретном адаптере. Ошибки в длине результата также остаются ответственностью адаптера. Мы сохранили типы локально, но не сделали универсальную типизированную сигнатуру Map.

Почему Get() any не исправляет всё

Можно придумать интерфейс Get(i int) interface{}. Тогда алгоритм получает элементы, но тип, известный ему статически, — пустой интерфейс. Для typed callback нужно либо проверять динамический тип, либо вынести обработку назад в адаптер. Это уже другой компромисс, который разберём отдельно.

Также Get() User не реализует метод интерфейса Get() interface{}: сигнатуры методов должны совпадать. Возможность присвоить отдельный User в interface{} не означает ковариантности результатов методов.

Где интерфейсы остаются правильным выбором

У io.Reader все реализации читают в []byte и возвращают (int, error). Здесь нет неизвестного отношения E → R, которое нужно выразить параметрами типов. Различается поведение источников. Интерфейс позволяет хранить разные реализации вместе и выбирать реализацию во время исполнения.

Такое обобщение часто называют поведенческим, а вызовы через интерфейс — динамическим полиморфизмом. Это описание модели языка: конкретный компилятор иногда устраняет косвенный вызов. Не следует превращать «интерфейс» в синоним «медленно». О выборе между интерфейсами и параметрами типов: When To Use Generics.

interface{}: один контейнер, потерянные статические связи

Исходник Markdown ↗
Принять значение любого типа и сохранить связь между произвольными типами — разные требования.

Убираем адаптеры с методами

Если все элементы заранее упаковать в interface{}, получится одна сигнатура для разных данных. В этой главе используем историческое написание; с Go 1.18 any является алиасом того же типа.

Go
func FindAny(src []interface{}, pred func(interface{}) bool) int {
	for i, item := range src {
		if pred(item) {
			return i
		}
	}
	return -1
}
Go
func AllAny(src []interface{}, pred func(interface{}) bool) bool {
	for _, item := range src {
		if !pred(item) {
			return false
		}
	}
	return true
}
Go
func MapAny(src []interface{}, transform func(interface{}) interface{}) []interface{} {
	if src == nil {
		return nil
	}
	out := make([]interface{}, len(src))
	for i, item := range src {
		out[i] = transform(item)
	}
	return out
}

Алгоритмы действительно общие. Но MapAny на этапе компиляции возвращает только []interface{}. То, что внутри оказались исключительно строки, не меняет этот статический тип.

Цена на границе вызова

Go
var boxed []interface{}
if users != nil {
    boxed = make([]interface{}, len(users))
}
for i, user := range users {
    boxed[i] = user
}

index := FindAny(boxed, func(x interface{}) bool {
    return x.(User).Age >= 18
})
all := AllAny(boxed, func(x interface{}) bool {
    return x.(User).Active
})
raw := MapAny(boxed, func(x interface{}) interface{} {
    return x.(User).Name
})

var names []string
if raw != nil {
    names = make([]string, len(raw))
}
for i, item := range raw {
    names[i] = item.(string)
}

Нельзя просто передать []User как []interface{}. И нельзя присвоить func(User) string переменной типа func(interface{}) interface{}. В первом случае нужен новый срез с поэлементным присваиванием, во втором — функция-обёртка.

Отсутствие ковариантности у срезов важно и семантически: если бы общий изменяемый []User можно было использовать как []interface{}, через него можно было бы попытаться записать строку в хранилище пользователей. Для преобразования срезов Go требует явного цикла. Источник: Go FAQ.

Что увидит компилятор

В FindAny нет декларации «callback ожидает тот же конкретный тип, который лежит в исходном срезе». Он получает interface{} и возвращает bool — это весь статический контракт. Поэтому такой вызов компилируется:

Go
FindAny([]interface{}{User{Name: "Аня"}}, func(x interface{}) bool {
    return len(x.(string)) > 0 // panic при обработке User
})

Можно заменить assertion на value, ok := x.(User). Но затем нужно решить, что делать при несовпадении: пропустить элемент, вернуть ошибку, завершить поиск? Мы вынуждены добавлять в контракт ситуации, которых у конкретной типизированной функции не было.

Ещё опаснее проверка через ==: сравнение двух интерфейсных значений может вызвать panic, если их динамические значения несравнимы. interface{} не означает «любой оператор допустим».

Данные не теряют runtime-тип

Упаковка User в интерфейс не стирает сведения о нём из runtime. Иначе assertion был бы невозможен. Потеря происходит в статическом контракте: компилятор вызывающего кода больше не выводит []string из MapAny.

Поэтому выражение «type erasure» здесь следует использовать осторожно: это не буквальное отсутствие информации о типе во время исполнения. Для нашего сравнения точнее говорить о потере статической связи между типами аргументов и результата.

Когда это полезная модель

Если данные по смыслу разнородны — например, набор произвольных значений для форматирования — []interface{} отражает задачу. Проблема возникает, когда однородную []User вынуждают пройти через этот формат только ради общего цикла.

В приведённом адаптере появляются дополнительные контейнеры и обходы для упаковки и извлечения. Это конкретное свойство этой реализации. Утверждать, что каждое интерфейсное значение обязательно создаёт отдельную heap-аллокацию, нельзя: размещение зависит от компилятора и контекста.

Переход к reflection

Следующий вопрос: можно ли принять исходный []User и исходный func(User) string без ручной упаковки, а совместимость выяснить внутри библиотеки? Для этого нужно уметь исследовать типы и вызывать функцию во время исполнения.

Reflection: универсальность с проверкой при исполнении

Исходник Markdown ↗
Reflection переносит часть работы с типами внутрь библиотеки, но выполняет её над runtime-описаниями значений.

Меняем границу API

Вместо []interface{} примем весь исходный срез в одном интерфейсном значении. Отдельно примем исходную функцию:

Go
index, err := FindReflect(users, adult)
all, err := AllReflect(users, active)
raw, err := MapReflect(users, name)
// Каждый err нужно проверить до использования результата.

При упаковке среза целиком мы не создаём срез интерфейсных элементов. Его динамический тип остаётся []User. Но тип src interface{} сам по себе не обещает даже того, что пришёл срез: можно передать число. Обещания должна проверить реализация.

Валидация является частью алгоритма

Наша библиотека допускает только неvariadic-функцию с одним входом и одним выходом. Тип входа должен точно совпадать с типом элемента среза. Для Find и All результат должен быть ровно bool.

Go
func checkTransform(src, fn interface{}) (reflect.Value, reflect.Value, error) {
	s, f := reflect.ValueOf(src), reflect.ValueOf(fn)
	if !s.IsValid() || s.Kind() != reflect.Slice {
		return s, f, fmt.Errorf("source must be a slice")
	}
	if !f.IsValid() || f.Kind() != reflect.Func || f.IsNil() {
		return s, f, fmt.Errorf("callback must be a non-nil function")
	}
	t := f.Type()
	if t.IsVariadic() || t.NumIn() != 1 || t.NumOut() != 1 || t.In(0) != s.Type().Elem() {
		return s, f, fmt.Errorf("callback must have signature func(%v) R", s.Type().Elem())
	}
	return s, f, nil
}

Этот контракт сознательно уже, чем все возможности reflect.Value.Call: мы не используем присваиваемость к интерфейсному параметру и не делаем автоматических конверсий. Например, для []User функция func(interface{}) string будет отвергнута. Так проще увидеть и проверить отношение типов.

Typed nil-срез является корректным пустым входом. Нетипизированный nil, не-срез, nil-функция, неправильное число аргументов и несовпадение типов возвращают ошибку. Проверка выполняется даже для пустого среза: неверную сигнатуру нельзя маскировать отсутствием элементов. Все проверки находятся в reflection.go.

Find и All

Go
func FindReflect(src, pred interface{}) (int, error) {
	s, f, err := checkPredicate(src, pred)
	if err != nil {
		return -1, err
	}
	for i := 0; i < s.Len(); i++ {
		if f.Call([]reflect.Value{s.Index(i)})[0].Bool() {
			return i, nil
		}
	}
	return -1, nil
}
Go
func AllReflect(src, pred interface{}) (bool, error) {
	s, f, err := checkPredicate(src, pred)
	if err != nil {
		return false, err
	}
	for i := 0; i < s.Len(); i++ {
		if !f.Call([]reflect.Value{s.Index(i)})[0].Bool() {
			return false, nil
		}
	}
	return true, nil
}

После проверки каждый элемент передаётся через reflect.Value, результат читается как bool. Ранняя остановка сохранена. Но ошибка func(Order) bool для []User обнаруживается при вызове, а не при компиляции программы.

Map может построить настоящий []R

Go
func MapReflect(src, transform interface{}) (interface{}, error) {
	s, f, err := checkTransform(src, transform)
	if err != nil {
		return nil, err
	}
	target := reflect.SliceOf(f.Type().Out(0))
	if s.IsNil() {
		return reflect.Zero(target).Interface(), nil
	}
	out := reflect.MakeSlice(target, s.Len(), s.Len())
	for i := 0; i < s.Len(); i++ {
		out.Index(i).Set(f.Call([]reflect.Value{s.Index(i)})[0])
	}
	return out.Interface(), nil
}

Из типа возвращаемого значения callback библиотека строит тип []R, создаёт срез и заполняет его. Для func(User) string динамический тип результата действительно будет []string, а не []interface{}.

Go
raw, err := MapReflect(users, name)
if err != nil {
    // Обработать несовместимый вызов.
    return
}
names, ok := raw.([]string)
if !ok {
    // Нарушено ожидание вызывающего кода о типе результата.
    return
}

Статический тип raw по-прежнему interface{}. Связь между callback и результатом существует в реализации, но не выражена сигнатурой Go. На границе вызывающего кода снова нужна проверка.

Если исходный срез nil, возвращается интерфейс, содержащий nil-срез целевого типа. Поэтому raw == nil в успешном таком вызове ложно, а raw.([]string) == nil истинно. Прежняя справочная глава о typed nil объясняет механизм, а здесь видно его влияние на дизайн API.

Граница между ошибкой API и panic пользователя

Валидация гарантирует допустимую форму вызова. Она не гарантирует, что name не паникует, не делит на ноль и не обращается к закрытому ресурсу. В нашей реализации panic callback распространяется наружу, как в остальных вариантах. Автоматически восстанавливать его и выдавать как «ошибку типа» было бы изменением контракта.

Цена реализации включает проверки метаданных, упаковку аргументов вызова и reflect.Call на каждом обработанном элементе. Количественный вывод требует измерения. Нельзя переносить результат такого поэлементного reflection-алгоритма на любой код, который использует reflect один раз при настройке. API и ограничения: reflect, модель интерфейсного значения: The Laws of Reflection.

Где reflection сохраняет свою роль

Когда типы приходят из данных во время исполнения — например, при обходе полей произвольной структуры и чтении тегов — compile-time-параметр E не заменяет исследование структуры. Для однородного Map с известными в исходном коде типами мы платим за динамику, которая не была требованием задачи.

Генерация кода: специализация до компиляции

Исходник Markdown ↗
Можно сохранить конкретные сигнатуры, если повторяющийся код будет писать программа.

Переносим обобщение в инструмент

У конкретного FindUser был удобный типобезопасный API, но повторяющееся тело. Генератор хранит тело один раз в шаблоне, подставляет типы и выпускает обычный Go-код. Компилятор видит уже специализированные функции.

Схема
Шаблон Find / All / Map
        +
(User, string), (int, string)
        ↓ генерация
FindUsersGenerated, MapUsersGenerated, ...
        ↓ обычная компиляция
Программа с конкретными сигнатурами

Существенно, что генерация нужна до проверки типов итоговой программы. Это не runtime reflection и не параметр типа в языке.

В учебнике есть работающий генератор

Файл generate.go объявляет команду:

Go
//go:generate go run ./internal/generate

Генератор использует text/template и go/format. Он выпускает Find, All и Map для двух специализаций: User → string и int → string. Входное описание задаёт имя специализации, тип элемента и тип результата. Реализация: internal/generate/main.go.

Пример реально сгенерированной функции:

Go
func MapUsersGenerated(src []User, fn func(User) string) []string {
	if src == nil {
		return nil
	}
	out := make([]string, len(src))
	for i, item := range src {
		out[i] = fn(item)
	}
	return out
}
Go
names := MapUsersGenerated(users, name) // []string без assertion

Компилятор отвергнет func(Order) string при передаче в эту функцию. Чтобы получить User → int, нужно добавить специализацию, запустить генерацию и собрать программу заново.

ТребованиеГенерация

Конкретный результат []RДа, в каждом выпуске

Типобезопасность выпуска не означает типобезопасности любого возможного развёртывания шаблона. Ошибка может не проявиться на первых двух специализациях и проявиться на третьей.

Историческая роль go generate

Команда go generate появилась в Go 1.4. Она стандартизировала запуск генераторов по директивам, но не изобрела генерацию и не включила её автоматически в go build. Автор пакета запускает её явно; сгенерированные файлы обычно поставляются вместе с библиотекой. Источник: Generating code.

Поэтому неверно рисовать историю как «до Go 1.4 генерации не существовало». Менялась интеграция с инструментами, а сам приём был доступен ранее.

Почему параметры типов всё равно понадобились

Генератор решает повторение исходника, но заставляет поддерживать отдельный язык шаблона, список специализаций и стадию сборки. Потребитель библиотеки не может просто вызвать единственную Map с новым типом и получить проверенный результат без подготовки нового кода.

Следующее требование: сделать типовую параметризацию частью обычной декларации Go. Тогда библиотека сможет публиковать одну проверяемую функцию, а потребитель — выбирать типы при вызове.

Исходник Markdown ↗
Параметры типов позволяют опубликовать один алгоритм с согласованными типами входа, callback и результата.

Find и All: тип известен, но произволен

Go
func Find[E any](src []E, pred func(E) bool) int {
	for i, item := range src {
		if pred(item) {
			return i
		}
	}
	return -1
}
Go
func All[E any](src []E, pred func(E) bool) bool {
	for _, item := range src {
		if !pred(item) {
			return false
		}
	}
	return true
}

E — не интерфейсная коробка вокруг каждого элемента. При конкретном вызове он обозначает выбранный тип. Тело алгоритма проверяется с учётом ограничения: при any оно может передавать E в func(E) bool, но не может произвольно складывать значения или читать у них поле Age.

Go
index := Find(users, adult)
all := All(users, active)
textIndex := Find([]string{"go", "generic"}, func(s string) bool {
    return len(s) > 2
})

Один исходник работает для User, string и новых пользовательских типов. Цикл и условия остановки проверяются в одном месте; предметные предикаты остаются обычными типизированными функциями.

Map: недостающее отношение E → R

Go
func Map[E, R any](src []E, transform func(E) R) []R {
	if src == nil {
		return nil
	}
	out := make([]R, len(src))
	for i, item := range src {
		out[i] = transform(item)
	}
	return out
}
Go
names := Map(users, name) // []string
ages := Map(users, func(u User) int { return u.Age }) // []int

// Map(users, func(s string) int { return len(s) })
// Ошибка компиляции: []User и параметр string не согласованы.

Компилятор связывает E с элементом первого аргумента и входом callback; R — с выходом callback и элементом результата. Теперь то, что reflection проверял при исполнении, выражено на границе функции.

Для []User и func(User) string никакие преобразования User → interface{} и interface{} → string не требуются. Вывод аргументов типов сокращает запись, но не меняет смысл: можно написать Map[User, string](users, name) явно.

any в ограничении и any как тип значения

Сравните:

Схема
MapAny([]interface{}, func(interface{}) interface{}) []interface{}
Map[E, R any]([]E, func(E) R) []R

В первой сигнатуре один и тот же интерфейсный тип принимает значения разных динамических типов. Во второй any ограничивает допустимые аргументы типов, а E и R сохраняют конкретные выбранные типы в сигнатуре.

Вызов Map[any, any] возможен и будет работать с интерфейсными элементами. Дженерики не запрещают динамику; они позволяют не вводить её туда, где нужна типизированная однородная коллекция.

Ограничения: выражаем ровно те операции, которые нужны

Исходник Markdown ↗
Хороший generic-алгоритм требует минимальных возможностей и сохраняет нужные отношения между типами.

Предикат и встроенное равенство — разные API

В Find сравнение целиком принадлежит pred, поэтому E any достаточно. Но поиск конкретного значения через == потребует другого ограничения:

Go
func Contains[E comparable](src []E, target E) bool {
	return Find(src, func(item E) bool { return item == target }) >= 0
}

Это не усиленная версия Find на все случаи. Срез [][]int нельзя передать в Contains, поскольку []int несравним. Его можно передать в Find с функцией сравнения срезов. Ограничение должно следовать из операций тела, а не из названия алгоритма.

С Go 1.20 интерфейсный тип any может удовлетворять comparable. Поэтому Contains[any] разрешён, но сравнение интерфейсных значений с несравнимыми динамическими типами может вызвать panic. comparable не является обещанием безопасно сравнить произвольное runtime-содержимое интерфейса. Источник: Go 1.20.

Сортировка: порядок или функция сравнения

Для < потребуется множество упорядоченных типов, например cmp.Ordered. Для структуры User общего встроенного порядка нет; библиотека принимает func(User, User) int.

Go
// imports: "cmp", "slices"
slices.Sort([]int{3, 1, 2})
slices.SortFunc(users, func(a, b User) int {
    return cmp.Compare(a.Age, b.Age)
})

Предикат «совершеннолетний» не является компаратором: он не сравнивает два значения. Компилятор проверяет форму callback, но не способен доказать согласованность порядка. Даже type-safe API требует семантического договора о сравнении.

Зачем писать S ~[]E, если есть []E

Простой Map[E, R] уже принимает значение определённого срезового типа с подходящим элементом. Но возвращает ровно []R. Отдельный параметр S нужен, когда API должен сохранять сам тип контейнера.

Go
func Clone[S ~[]E, E any](src S) S {
	if src == nil {
		return nil
	}
	out := make(S, len(src))
	copy(out, src)
	return out
}
Go
type Users []User
func (s Users) Count() int { return len(s) }

var users Users
copied := Clone(users)
_ = copied.Count() // возвращён Users, не просто []User

~[]E означает типы, underlying type которых — []E. В Clone тип результата S совпадает с типом входа. Это полезнее, чем механически добавлять S в любую функцию, принимающую срез.

Для Map при переходе User → string сохранить Users нельзя: это другой тип элемента. Можно принимать отдельный параметр целевого контейнера, но Go не всегда сможет вывести его из обычных аргументов. У API появляется дополнительная сложность, которую нужно оправдать реальным требованием. Разбор такой сигнатуры: Deconstructing Type Parameters.

Интерфейс как ограничение

Go
type Named interface {
    Name() string
}

func Names[E Named](src []E) []string {
    return Map(src, func(item E) string { return item.Name() })
}

Это одновременно параметрический алгоритм и требование поведения. []ConcreteNamed не нужно сначала преобразовывать в []Named. Ограничение позволяет вызывать метод внутри generic-тела, сохраняя связь с конкретным E.

В сквозной модели User уже есть поле Name; метод с тем же именем добавить нельзя. Для этого примера нужна другая модель или адаптер. Поле структуры и метод интерфейса — разные вещи.

Есть и ограничение с отношением к самому типу:

Go
type Equaler[E any] interface {
    Equal(E) bool
}

func ContainsEqual[E Equaler[E]](src []E, target E) bool {
    return Find(src, func(item E) bool { return item.Equal(target) })
}

Здесь описано не просто наличие метода с любым параметром, а способность сравниваться с тем же E. Такая запись допустима начиная с Go 1.18: объявление Equaler ссылается на собственный параметр E, а не рекурсивно ограничивает само себя в списке параметров.

Type sets не являются runtime-контейнерами вариантов

Ограничение interface{ ~int | ~string } разрешает инстанциации с подходящими типами. Оно не создаёт обычный интерфейсный контейнер «int или string», который можно положить в поле и переключать во время исполнения. Для динамического набора вариантов нужен другой дизайн данных.

Аналогично два независимых параметра E any и R any не разрешают просто написать R(x): допустимость конверсии должна следовать из ограничений. В Map операция предоставлена функцией func(E) R, поэтому библиотека не придумывает конверсию самостоятельно.

Исходник Markdown ↗

Четыре формы сортировки пользователей

Все следующие варианты решают одну задачу: упорядочить users по возрасту. Они отличаются местом, где задаются операции и проверяются типы.

Go
// Старый интерфейсный API: три метода у адаптера UsersByAge.
sort.Sort(UsersByAge(users))

// Go 1.8+: срез как interface{}, сравнение через индексы.
sort.Slice(users, func(i, j int) bool {
    return users[i].Age < users[j].Age
})

// Go 1.21+: типизированные элементы в callback.
slices.SortFunc(users, func(a, b User) int {
    return cmp.Compare(a.Age, b.Age)
})

// Для типов со встроенным порядком callback вообще не нужен.
slices.Sort([]int{3, 1, 2})

У sort.Slice нет требований реализовать методы адаптера. Но первый параметр не гарантирует срез на этапе компиляции, а замыкание способно случайно сравнивать элементы другой коллекции. slices.SortFunc связывает тип элемента и параметры сравнения статически.

sort.Slice использует runtime-механизмы для доступа к переданному срезу и перестановок. Это не означает, что он вызывает reflect.Call для каждого сравнения: callback здесь обычная функция от индексов. Поэтому его нельзя оценивать по скорости учебного MapReflect с поэлементными динамическими вызовами. Источники: sort.Slice, Go 1.8.

Почему это полезнее истории синтаксиса

Итераторы: обобщаем уже не тип элемента, а источник

Исходник Markdown ↗
После решения проблемы E → R остаётся другая: алгоритм всё ещё привязан к срезу.

Дженерики не сделали []E произвольной коллекцией

Map[E, R] обобщён по типам, но его вход — срез. Для дерева, списка или вычисляемой последовательности придётся сначала собрать []E либо предоставить другой протокол обхода. Сборка может быть дорогой, а бесконечный источник вообще нельзя предварительно материализовать.

С Go 1.23 стандартный тип iter.Seq[E] описывает функцию, которая передаёт значения потребителю через yield. Возврат false сообщает источнику, что обход нужно остановить. iter.Seq2[K, V] передаёт пары. Это push-протокол: источник вызывает потребителя. Источник: iter.

Go
// Концептуальная форма iter.Seq[E]:
// type Seq[E any] func(yield func(E) bool)

// import "slices"
for user := range slices.Values(users) {
    // user имеет тип User
    _ = user
}

Обычный for range скрывает обмен сигналом остановки. Если потребитель делает break, корректный источник должен прекратить выдавать значения. Go 1.23 стандартизировал типы и синтаксис; функции с callback как идея существовали раньше.

Ленивый Map

Go
func MapSeq[E, R any](src iter.Seq[E], transform func(E) R) iter.Seq[R] {
	return func(yield func(R) bool) {
		for item := range src {
			if !yield(transform(item)) {
				return
			}
		}
	}
}

Вызов MapSeq создаёт функцию обхода. Он ещё не вызывает transform и не создаёт срез результатов. Работа начинается, когда кто-то потребляет возвращённую последовательность.

Go
// import "slices"
names := MapSeq(slices.Values(users), name)
for value := range names {
    // Обработать только первое имя.
    _ = value
    break
}

Обработан только первый элемент. Проверка if !yield(...) { return } принципиальна: игнорирование false нарушает протокол и может привести к panic при range-over-func. Это не необязательная оптимизация.

Find и All над последовательностью

Go
func FindSeq[E any](src iter.Seq[E], pred func(E) bool) (E, bool) {
	for item := range src {
		if pred(item) {
			return item, true
		}
	}
	var zero E
	return zero, false
}
Go
func AllSeq[E any](src iter.Seq[E], pred func(E) bool) bool {
	for item := range src {
		if !pred(item) {
			return false
		}
	}
	return true
}

Теперь Find возвращает (E, bool). Прежний индекс int больше не является универсальным результатом: дерево или канал может не иметь понятия индексируемого элемента. Можно вернуть порядковый номер обхода, но это будет другая семантика, которую нужно назвать явно.

Нулевая величина E не служит признаком отсутствия: нулевой пользователь тоже может быть найден. Поэтому bool отделяет результат от отсутствия совпадения.

Композиция без промежуточного среза

Go
// import "slices"
lengths := MapSeq(
    MapSeq(slices.Values(users), name),
    func(s string) int { return len(s) },
)
allLong := AllSeq(lengths, func(n int) bool { return n >= 4 })

Не создаются промежуточные []string и []int. Но функции и замыкания всё ещё имеют стоимость; код не обещает отсутствие любых аллокаций. При первом коротком имени All прекращает потребление, и остановка распространяется через обе стадии.

Это меняет наблюдаемое поведение при побочных эффектах. Eager-выражение All(Map(users, fn), pred) сначала вызывает fn для всех элементов. Ленивое выражение может вызвать fn только для префикса. Такие программы эквивалентны по bool для подходящих чистых функций, но не обязательно по логам, записи в БД или моменту panic.

Материализация — отдельное решение

Go
// import "slices"
names := slices.Collect(MapSeq(slices.Values(users), name))

Collect возвращает nil для пустой последовательности. Итератор сам по себе не различает nil-срез и ненулевой пустой срез: оба не выдают элементов. Поэтому eager-контракт нашей Map о nil нельзя механически перенести на pipeline через Seq. Это пример потери информации при абстрагировании источника, а не ошибка типизации.

Не каждый Seq допускает повторный обход. Одни источники повторяемы, другие одноразовые; это нужно документировать. Для pull-модели есть iter.Pull, возвращающий next и stop; при раннем завершении потребитель должен вызвать stop. Протокол завершения и жизненный цикл — часть интерфейса алгоритмов. Источники: Range Over Function Types, slices.Collect.

Основная линия развития — всё более прямое выражение нужного отношения на границе библиотеки. Это не означает, что последний пункт лучше для любого вызова. Что означает «переиспользовали алгоритм»

Можно переиспользовать только цикл (MapInto), цикл и протокол операций (RunMap), шаблон исходника (генерация), динамическую реализацию (reflection) или типизированное отношение (Map[E, R]). Эти варианты устраняют разные виды повторения.

Считать только строки тела недостаточно. Учитывайте код вызова, адаптеры, проверки ошибок, промежуточные контейнеры и необходимость обновлять специализации. Короткий универсальный цикл может обойтись дорогим и хрупким API вокруг него.

Стоимость: что измерять отдельно

Для конечных срезов Find и All имеют худшее время O(n) и O(1) дополнительной памяти самого обхода. Map выполняет n преобразований и хранит n результатов. Стоимость callback в эти оценки нужно включать отдельно. У всех вариантов может быть одна асимптотика и совершенно разная постоянная стоимость.

Нельзя обосновывать выбор только лозунгом «reflection медленный»: разделяйте настройку и поэлементную работу.

Упражнения на benchmark намеренно не заменены выдуманными цифрами. Достоверный результат должен указывать Go toolchain, архитектуру, размер входа, работу callback, ns/op, B/op, allocs/op и повторяемость измерений.

Минимальная библиотека после разбора

Для срезов достаточно начать с Find[E any], All[E any], Map[E, R any]. Поиск по значению может быть отдельным Contains[E comparable]. Для произвольных источников добавьте Seq-варианты с документированным завершением и семантикой повторного обхода.

Не добавляйте поддержку ошибок, параллелизма, контекста и отмены одним универсальным флагом. Например, MapErr с func(E) (R, error) должен определить: остановку на первой ошибке, возврат частичного результата, порядок и выполнение оставшихся callback. Эти решения не следуют из параметров типов.

Также не стоит дублировать стандартную библиотеку ради собственного названия: реальный поиск по предикату для среза уже есть как slices.IndexFunc. Учебные реализации здесь нужны, чтобы сравнить выразительность подходов.

Практика, которая проверяет понимание

  1. Добавьте Order и повторите Find/All/Map всеми подходами. Запишите, какие файлы и адаптеры понадобились, где выявились несовместимые callback.
  2. Напишите Filter[E any] с сохранением порядка. Зафиксируйте поведение nil, пустого среза и отсутствия совпадений. Сравните срез результата с представлением через Seq.
  3. Напишите Reduce[E, A any] с начальным аккумулятором и func(A, E) A. Объясните, почему тип аккумулятора может отличаться от E и зачем нужен начальный результат для пустого входа.
  4. Создайте два Map: User → string и User → []string. Покажите, что Map сохраняет вложенность, а FlatMap потребовал бы другого алгоритма.
  5. Добавьте ошибку callback на третьем элементе и спроектируйте MapErr. Проверьте, были ли обработаны четвёртый и пятый элементы.
  6. Реализуйте FindSeq над деревом. Объясните, почему возвращается значение с bool, а не индекс среза.

Для Filter важна не только сигнатура: если результат ссылается на исходный backing array, мутации будут наблюдаемы иначе, чем при новой аллокации. Для Reduce важен порядок: без ассоциативности нельзя произвольно распараллелить свёртку. Для ленивой композиции важен момент вычислений. Исходник Markdown ↗
Цель главы: Различать присваивание, константы и идентичность типов.

4.1. Нетипизированная константа

Go
const answer = 42
var a int8 = answer
var b float64 = answer
var c complex128 = answer

inferred := 42 // int: тип по умолчанию
const typed int = 42
// var d int64 = typed // typed уже имеет тип int

// _ = uint8(300) // ошибка компиляции: константа не помещается
// _ = int(3.9)   // ошибка компиляции: константа не представима как int

Разница между константой и переменной объясняет, почему uint8(300) запрещено, а преобразование переменной со значением 300 даёт 44. Это не автоматическое расширение любых чисел. См. Constants.

4.2. Совместимость при присваивании

Go
type Numbers []int
var named Numbers = []int{1, 2}
var plain []int = named // одинаковые underlying types, один тип неименованный

type OtherNumbers []int
// var other OtherNumbers = named // оба типа определённые
other := OtherNumbers(named)       // явная конверсия допустима

Термины: type ID int создаёт определённый тип; его underlying type — int. Именованность, идентичность типов и возможность присваивания — разные понятия. Алиас сам по себе нового типа не создаёт.

Есть отдельные правила для интерфейсов, каналов, nil и параметров типов. Эти правила действуют также при передаче аргументов и возврате результатов. Нормативный список: Assignability.

Строки, байты, руны и числа

Исходник Markdown ↗
Цель главы: Выбирать между байтами, рунами и текстовым представлением числа.
Go
text := "Привет"
bytes := []byte(text) // UTF-8 байты
runes := []rune(text) // кодовые точки Unicode
fromBytes := string(bytes)
fromRunes := string(runes)

letter := string(rune(65)) // "A", не "65"
replacement := string(rune(-1)) // "�": недопустимая кодовая точка

type Label string
label := Label(text)
original := string(label)

byte — алиас uint8, rune — алиас int32. Одна руна не обязательно равна одному видимому символу. []byte сохраняет байты, а []rune декодирует UTF-8; некорректные последовательности при декодировании заменяются на U+FFFD.

Обычные конверсии между строкой и срезом обеспечивают независимость наблюдаемых изменений: изменение полученного []byte не меняет исходную строку. Из этого не следует обязательная heap-аллокация: компилятор может оптимизировать её. См. Effective Go: strings и конверсии строк.

Текстовое представление: strconv

Go
// import "strconv"

if err != nil {
    // Обработать ошибку формата или диапазона.
}

parsed, parseErr := strconv.ParseInt("ff", 16, 64)

int("42") запрещено, string(42) даёт кодовую точку, а strconv.Itoa(42) — десятичную запись. Для форматирования с шаблоном есть fmt.Sprintf, для чтения формата — fmt.Sscanf. Проверка синтаксиса и диапазона относится к разбору данных, а не к конверсии языка. Справочник: strconv.

Определённые типы, структуры, функции и контейнеры

Исходник Markdown ↗
Цель главы: Понимать совместимость составных и определённых типов.

6.1. Новый тип не наследует методы

Go
// import "fmt"
type UserID int64
func (id UserID) String() string { return fmt.Sprintf("user:%d", id) }

type OrderID UserID

func exampleIDs() {
    user := UserID(42)
    order := OrderID(user)
    _ = user.String()
    // _ = order.String() // у OrderID нет этого метода
    _ = order
}

Конверсия позволяет перейти между такими типами, но не проверяет предметный смысл. Для запрета отрицательного ID нужен конструктор с валидацией.

6.2. Структуры; послабление Go 1.8 для тегов

Go
type APIUser struct {
    ID int64 `json:"id"`
}
type DBUser struct {
    ID int64 `db:"user_id"`
}

func convertUser(api APIUser) DBUser {
    return DBUser(api) // Go 1.8+: различия тегов не мешают
}

Это не автоматический маппинг по названиям. Порядок полей и их типы имеют значение. Например, ID int и ID int64 потребуют явного построения результата. Копирование структуры неглубокое: поля-срезы и указатели могут продолжить ссылаться на общие данные. См. Go 1.8.

6.3. Указатели, функции, массивы, срезы и map

Go
type A int
type B int

type F func(int) int
type G func(int) int

type Vector [2]int
type SliceA []int
type SliceB []int
type MapA map[string]int
type MapB map[string]int

func exampleComposite() {
    a := A(1)
    b := (*B)(&a) // допустимая конверсия неименованных указателей
    *b = 7       // изменяет a: это та же память

    f := F(func(n int) int { return n + 1 })
    g := G(f)
    vector := Vector([2]int{1, 2})

    s := SliceA{1, 2}
    t := SliceB(s) // тот же backing array
    t[0] = 9

    m := MapA{"x": 1}
    convertedMap := MapB(m) // та же map
    convertedMap["x"] = 2

    _, _, _ = g, vector, b
}

Одинаковое представление памяти само по себе не разрешает конверсию. Например, *int64 → *float64 требует иных механизмов. Для обычных указателей существенны условия идентичности underlying types базовых типов; для функций — сигнатуры. См. Conversions.

Нет поэлементной конверсии контейнеров:

Go
src := []int{1, 2, 3}
// dst := []int64(src) // запрещено
dst := make([]int64, len(src))
for i, n := range src {
    dst[i] = int64(n)
}

// Не работают также []string → []any и map[string]int → map[string]int64.

6.4. Направление канала

Go
ch := make(chan int)
var recv <-chan int = ch
var send chan<- int = ch
explicit := (<-chan int)(ch)
// both := (chan int)(recv) // восстановить оба направления нельзя

Это ограничивает доступ через значение, а не создаёт новый канал. Для двух определённых типов каналов может потребоваться промежуточный неименованный тип. Правила приведены в Assignability.

Интерфейсы: исходная модель полиморфизма

Исходник Markdown ↗
Цель главы: Работать с динамическим типом интерфейсного значения.

7.1. Упаковка конкретного значения

Go
var x any = int(42) // any доступен с Go 1.18
var old interface{} = int(42) // историческая запись того же типа

Интерфейс хранит динамический тип и значение. Присваивание int в any не превращает его в «универсальное число». Пара тип + значение — семантическая модель, не обещание конкретной раскладки runtime. См. The Laws of Reflection.

7.2. Type assertion: x.(T)

Go
var x any = int(42)
n := x.(int)              // 42
wide, ok := x.(int64)      // 0, false
// panicValue := x.(int64) // panic

if n, ok := x.(int); ok {
    converted := int64(n)  // assertion, затем числовая конверсия
    _ = converted
}

Для конкретного T требуется совпадение динамического типа, а не просто возможность конверсии. Для интерфейсного T проверяется реализация интерфейса. Исходный операнд должен иметь интерфейсный тип; к обычной переменной int assertion применить нельзя. См. Effective Go: interface conversions.

7.3. Интерфейс → интерфейс

Go
// import "io"
func inspect(rw io.ReadWriter) {
    var reader io.Reader = rw // все нужные методы гарантированы статически
    writer, ok := reader.(io.Writer) // проверка динамического значения
    _, _ = writer, ok
}

7.4. Type switch

Go
// import "fmt"
func describe(x any) string {
    switch v := x.(type) {
    case nil:
        return "nil interface"
    case int:
        return fmt.Sprintf("int: %d", v)
    case string:
        return "string: " + v
    case float32, float64:
        return fmt.Sprintf("float: %v", v) // здесь v имеет тип any
    default:
        return fmt.Sprintf("other: %T", v)
    }
}

Это проверка вариантов во время исполнения. Нетипизированного x.(type) вне type switch не существует. См. Type switches.

7.5. Методы, указатели и typed nil

Go
type Worker interface { Work() }
type Job struct{}
func (*Job) Work() {}

var _ Worker = (*Job)(nil) // проверка реализации на этапе компиляции
// var _ Worker = Job{}   // у Job нет метода с pointer receiver

func nilExample() bool {
    var p *Job = nil
    var w Worker = p
    return w == nil // false: динамический тип *Job присутствует
}

Автоматическое взятие адреса при вызове метода у адресуемой переменной не добавляет pointer-методы в method set типа значения. Интерфейс равен nil, когда отсутствуют и динамический тип, и значение. Это также объясняет ошибку возврата typed nil как error. См. Go FAQ: nil error и method sets.

Reflection: когда тип приходит во время исполнения

Исходник Markdown ↗
Цель главы: Проверять возможность динамической конверсии.
Go
// import "reflect"
func convertDynamic(x any, target reflect.Type) (any, bool) {
    value := reflect.ValueOf(x)
    if target == nil || !value.IsValid() || !value.CanConvert(target) {
        return nil, false
    }
    return value.Convert(target).Interface(), true
}

// out, ok := convertDynamic(int32(42), reflect.TypeOf(int64(0)))
// out имеет статический тип any и динамический тип int64.

reflect.Type.ConvertibleTo проверяет совместимость типов. Value.CanConvert учитывает также конкретное значение: например, длину среза перед конверсией в массив. Convert без проверки может вызвать panic.

AssignableTo относится к присваиванию, Implements — к реализации интерфейса. Эти проверки не взаимозаменяемы. reflect.Value.Int() читает целочисленное значение как int64, но не меняет исходный тип. Запись через Set/SetInt дополнительно зависит от доступности значения для изменения.

С Go 1.22 reflect.TypeFor[T]() возвращает тип аргумента, включая интерфейсный тип; reflect.TypeOf(x) возвращает динамический тип значения. Источники: reflect, Go 1.22.

Срез → указатель на массив: Go 1.17

Исходник Markdown ↗
Цель главы: Понимать совместное использование памяти среза и массива.
Go
s := []int{10, 20, 30}

// _ = (*[4]int)(s) // panic: len(s) < 4

Проверяется len, а не cap. Конверсия не копирует элементы. Для nil-среза конверсия в *[0]T даёт nil-указатель; для пустого, но ненулевого среза — ненулевой указатель на массив нулевой длины. Это первый введённый в Go случай конверсии, способной вызвать runtime panic. Источник: Go 1.17.

Дженерики: Go 1.18

Исходник Markdown ↗
Цель главы: Обобщать конверсии с проверяемыми ограничениями.

11.1. Что они добавили

До дженериков обобщённый алгоритм обычно выражали через интерфейсы с методами, interface{} с assertions, reflection, генерацию кода или отдельные реализации для типов. Дженерики позволили проверять операции над параметрами типов при компиляции и сохранять конкретные типы аргументов и результатов. См. An Introduction To Generics.

11.2. Ограниченная конверсия

Go
type Real interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64 |
    ~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr |
    ~float32 | ~float64
}

func Convert[To Real, From Real](x From) To {
    return To(x)
}

// result := Convert[int64](int32(42))
// To задан явно; From выводится из аргумента.

~int64 допускает типы с underlying type int64, например type UserID int64. Без ~ член int64 описывает сам этот тип. | объединяет множества типов. Здесь конверсия разрешена для всех сочетаний исходного и целевого типов, но потери точности и переполнение остаются возможными.

Интерфейс с type terms, например interface{ ~int | ~string }, применяется как ограничение, а не как тип обычной переменной. any означает отсутствие ограничений, а не разрешение любой операции. Источник: Go 1.18.

11.3. Почему универсальный cast не получается

Go
// Не компилируется: any не гарантирует допустимость конверсии.
// func Cast[To, From any](x From) To { return To(x) }

func Assert[T any](x any) (T, bool) {
    value, ok := x.(T)
    return value, ok
}

func IsString[T any](x T) bool {
    _, ok := any(x).(string)
    return ok
}

Assert[int64](int(42)) вернёт 0, false. Assert обобщает проверку типа, не числовую конверсию. Прямой x.(string) для x T запрещён: сначала нужно интерфейсное значение. Так же для type switch используют switch any(x).(type). См. Type assertions.

11.4. Поэлементный маппинг

Go
func Map[S ~[]E, E, R any](src S, convert func(E) R) []R {
    if src == nil {
        return nil
    }
    dst := make([]R, len(src))
    for i, item := range src {
        dst[i] = convert(item)
    }
    return dst
}

// result := Map([]int{1, 2}, func(n int) int64 { return int64(n) })

Алгоритм создаёт новый срез, а смысл конверсии задаёт вызывающий код. При возможных ошибках нужен отдельный контракт с (R, error) и правилом обработки частичного результата. Дженерики сами такой контракт не выбирают.

11.5. comparable: уточнение Go 1.20

С Go 1.20 any может удовлетворять ограничению comparable. Это не обещает, что сравнение любых динамических значений безопасно:

Go
func Equal[T comparable](a, b T) bool { return a == b }

// Equal[any](42, 42)           // true, Go 1.20+
// Equal[any]([]int{1}, []int{1}) // panic: срезы несравнимы

Это изменение правил удовлетворения ограничения, а не новый способ конверсии. Источник: Go 1.20.

13.4. Методы с собственными параметрами типов: Go 1.27

Исходник Markdown ↗

15.1. errors.As: извлечение ошибки из дерева

Go
// imports: "errors", "io/fs"
func pathFromError(err error) (string, bool) {
    var target *fs.PathError
    if errors.As(err, &target) {
        return target.Path, true
    }
    return "", false
}

err.(*fs.PathError) проверяет только непосредственный динамический тип. errors.As проходит по обёрнутым ошибкам и учитывает пользовательский метод As. Это механизм поиска, а не T(x). Он появился в Go 1.13; пример использует пакет io/fs из Go 1.16. Источник: errors.

15.2. JSON и другие форматы

json.Unmarshal декодирует данные по правилам JSON. Для традиционного API encoding/json число при декодировании в any обычно становится float64; Decoder.UseNumber позволяет получить json.Number. Преобразование через JSON может терять сведения о типах и точность чисел, поэтому это отдельный контракт сериализации. Источник: encoding/json.

15.3. Адаптер функции к интерфейсу

Go
// import "net/http"
func serve(w http.ResponseWriter, r *http.Request) {}

var handler http.Handler = http.HandlerFunc(serve)

Здесь сначала функция конвертируется в определённый функциональный тип http.HandlerFunc, у которого есть метод ServeHTTP, затем присваивается интерфейсу. Это сочетание двух обычных механизмов. Источник: Effective Go: interfaces.

15.4. Ручной маппинг, генерация, cgo

Для структур с разными полями пишут ToDomain, ToDTO, конструктор или генерируют такой код. Генерация не вводит новых правил типизации. На границе с C действуют также размеры C-типов, правила владения и передачи указателей; функции вроде C.GoString выполняют специальное преобразование данных. Это отдельная тема межъязыкового взаимодействия, не универсальный cast. См. cgo.

Практика и маршрут изучения

Исходник Markdown ↗

Пройдите главы 1–7 последовательно, затем изучите reflection и исторические расширения. Главу 16 используйте как справочник.

Практические задания

  1. Различать конверсию, проверку типа и преобразование данных. Почему int64(x) и x.(int64) нельзя считать взаимозаменяемыми?
  2. Связать изменения системы типов с версиями Go. Какие возможности появились в Go 1.17, 1.18 и 1.20?
  3. Предсказывать результат числовой конверсии. Почему uint8(300) запрещено, а преобразование переменной со значением 300 возможно?
  4. Различать присваивание, константы и идентичность типов. Почему константу 42 можно присвоить int64, а переменную int — нельзя?
  5. Выбирать между байтами, рунами и текстовым представлением числа. Какие результаты дадут string(rune(65)) и strconv.Itoa(65)?
  6. Понимать совместимость составных и определённых типов. Какие данные остаются общими после конверсии среза, map и структуры?
  7. Работать с динамическим типом интерфейсного значения. Почему интерфейс с nil-указателем не равен nil?
  8. Проверять возможность динамической конверсии. Почему ConvertibleTo недостаточно для проверки конкретного среза перед конверсией в массив?
  9. Отличать новое имя типа от нового типа. Чем type ID = int64 отличается от type ID int64?
  10. Понимать совместное использование памяти среза и массива. Что изменится в исходном срезе после записи через (*[2]int)(s)?
  11. Обобщать конверсии с проверяемыми ограничениями. Почему функция с параметрами To any и From any не может просто вернуть To(x)?
  12. Отличать копию массива от указателя на общие элементы. Чем [2]int(s) отличается от (*[2]int)(s)?
  13. Читать современный generic-код с учётом версии языка. В каких версиях появились generic aliases и собственные параметры типов у методов?
  14. Отличать числовую конверсию от интерпретации памяти. Почему uintptr не удерживает объект от сборки мусора?
  15. Распознавать библиотечные преобразования и адаптеры. Почему errors.As находит ошибку, которую прямой assertion может не найти?
  16. Самостоятельно выбирать подходящий механизм. Как получить int64 из any, содержащего int, и где нужно проверять ошибки?

Как проверять решения

Для каждого решения укажите минимальную версию Go, ожидаемый результат, возможность ошибки компиляции или panic. Объясните, копируются ли данные или остаются общими. Запускайте намеренно падающие примеры отдельно.

Следующий этап: исполняемые пакеты

Материал можно превратить в учебный репозиторий с небольшими программами:

  1. 01-basic — числа, константы, строки, переполнение.
  2. 02-defined-types — структуры, функции, указатели, контейнеры, каналы.
  3. 03-interfaces — assertions, type switch, method sets, typed nil.
  4. 04-reflect — успешные и запрещённые динамические конверсии.
  5. 05-aliases — определённые типы и алиасы.
  6. 06-slice-array — Go 1.17 и Go 1.20, общая память и копирование.
  7. 07-generics — ограничения, конверсии, маппинг, comparable.
  8. 08-modern-generics — возможности Go 1.24–1.27.
  9. 09-unsafe — представление памяти рядом с безопасными аналогами.

Для каждого примера: минимальная версия Go, результат, ожидаемая ошибка компиляции или panic и объяснение. Это план следующего этапа; исполняемые пакеты пока не созданы.

Версии, источники и проверка

Исходник Markdown ↗

Срез исходного материала: 5 сентября 2026 года, Go 1.27. Ссылки на официальную документацию сохранены в каждой главе.

Примеры — учебные фрагменты, а не самостоятельные программы. Объявления типов и функций размещаются на уровне пакета, выражения — внутри функций; нужные импорты указаны комментариями. Неиспользуемые локальные переменные в реальной программе нужно использовать или удалить. До Go 1.18 вместо any пишите interface{}.

История и правила сверены с официальной спецификацией, release notes и документацией стандартной библиотеки по ссылкам в разделах. В локальном окружении команда go version сообщает Go 1.22.8, но go doc недоступен (no such tool "doc"). Фрагменты не заявлены как прошедшие компиляцию; примеры для Go 1.24–1.27 требуют соответствующего toolchain.
