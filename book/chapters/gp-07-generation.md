# 7. Генерация кода: специализация до компиляции

> Можно сохранить конкретные сигнатуры, если повторяющийся код будет писать программа.

## Переносим обобщение в инструмент

У конкретного `FindUser` был удобный типобезопасный API, но повторяющееся тело. Генератор хранит тело один раз в шаблоне, подставляет типы и выпускает обычный Go-код. Компилятор видит уже специализированные функции.

```text
Шаблон Find / All / Map
        +
(User, string), (int, string)
        ↓ генерация
FindUsersGenerated, MapUsersGenerated, ...
        ↓ обычная компиляция
Программа с конкретными сигнатурами
```

Существенно, что генерация нужна до проверки типов итоговой программы. Это не runtime reflection и не параметр типа в языке.

## В учебнике есть работающий генератор

Файл [generate.go](../../examples/generate.go) объявляет команду:

```go
//go:generate go run ./internal/generate
```

Генератор использует `text/template` и `go/format`. Он выпускает Find, All и Map для двух специализаций: `User → string` и `int → string`. Входное описание задаёт имя специализации, тип элемента и тип результата. Реализация: [internal/generate/main.go](../../examples/internal/generate/main.go).

Пример реально сгенерированной функции:

```go
func MapUsersGenerated(src []User, fn func(User) string) []string {
	if src == nil {
		return nil
	}
	out := make([]string, len(src))
	for i, item := range src {
		out[i] = fn(item)
	}
	return out
}
```

```go
names := MapUsersGenerated(users, name) // []string без assertion
```

Компилятор отвергнет `func(Order) string` при передаче в эту функцию. Чтобы получить `User → int`, нужно добавить специализацию, запустить генерацию и собрать программу заново.

## Что решено, что осталось

| Требование | Генерация |
|---|---|
| Одно тело алгоритма у автора | Да, в шаблоне |
| Конкретный результат `[]R` | Да, в каждом выпуске |
| Проверка callback компилятором | Да, для сгенерированной функции |
| Произвольная новая комбинация типов у потребителя | Требует новой генерации или готовой специализации |
| Проверка корректности шаблона обычным Go-компилятором | Только после развёртывания для выбранных типов |
| Обновление алгоритма | Изменить шаблон, регенерировать результаты, проверить diff |

Типобезопасность выпуска не означает типобезопасности любого возможного развёртывания шаблона. Ошибка может не проявиться на первых двух специализациях и проявиться на третьей.

## Историческая роль go generate

Команда `go generate` появилась в Go 1.4. Она стандартизировала запуск генераторов по директивам, но не изобрела генерацию и не включила её автоматически в `go build`. Автор пакета запускает её явно; сгенерированные файлы обычно поставляются вместе с библиотекой. Источник: [Generating code](https://go.dev/blog/generate).

Поэтому неверно рисовать историю как «до Go 1.4 генерации не существовало». Менялась интеграция с инструментами, а сам приём был доступен ранее.

## Почему параметры типов всё равно понадобились

Генератор решает повторение исходника, но заставляет поддерживать отдельный язык шаблона, список специализаций и стадию сборки. Потребитель библиотеки не может просто вызвать единственную `Map` с новым типом и получить проверенный результат без подготовки нового кода.

Следующее требование: сделать типовую параметризацию частью обычной декларации Go. Тогда библиотека сможет публиковать одну проверяемую функцию, а потребитель — выбирать типы при вызове.
