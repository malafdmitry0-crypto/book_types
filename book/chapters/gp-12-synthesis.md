# 18. Сравнение подходов и проектирование собственной библиотеки

Код главы: [algorithms_test.go](../../examples/algorithms_test.go) · [example_test.go](../../lessons/generic/example_test.go).


> Выбор определяется тем, какую информацию и какие операции должен сохранять контракт.

Мы прошли путь от конкретного цикла до типизированной ленивой последовательности. Сравним решения по требованиям задачи и договору об ошибках, а не по количеству строк или возрасту синтаксиса.

Следующая часть реализует этот план: [одна задача на дробях во всех подходах](gp-shared-task.md), затем законы, Filter/Reduce, замеры и практикум.

## Один сценарий, разные границы API

Историческая отправная точка теперь находится в первых десяти главах и работающем пакете algorithms. Там Fraction, Money и BoxInt уже обслуживаются общими циклами без параметров типов. Поэтому вывод курса — не «дженерики впервые сделали алгоритмы общими», а «дженерики позволили прямо записать часть отношений типов, прежде скрытых в адаптерах».

При сравнении с примерами над User из examples учитывайте разные договоры: algorithms передаёт ошибки операций, хранит Map-результат и Sum-аккумулятор в адаптере и не откатывает выполненные шаги. Упрощённый callback без error нельзя считать эквивалентной заменой проверяемому сложению денег.

| Подход | Где известен E | Где известен R | Кто проверяет согласованность |
|---|---|---|---|
| Конкретные функции | В исходной сигнатуре | В исходной сигнатуре | Компилятор, но нужны специализации |
| Индексы и замыкания | В замыкании вызывающего | В созданном им результате | Компилятор локально; длина и источник — договор |
| Поведенческий интерфейс | В адаптере | В адаптере | Компилятор проверяет методы, адаптер связывает данные |
| `[]interface{}` | Динамический тип каждого элемента | Динамические типы отдельных результатов | Assertions и договор о содержимом |
| Reflection | В runtime-описании среза | В runtime-описании callback | Валидатор библиотеки во время вызова |
| Генерация | В выпущенной функции | В выпущенной функции | Компилятор после генерации |
| Параметры типов | Параметр E в общей сигнатуре | Параметр R в общей сигнатуре | Компилятор на generic-границе |
| Дженерики + Seq | Параметр E в протоколе обхода | Параметр R в протоколе обхода | Компилятор; остановка и жизненный цикл — договор |

Основная линия развития — всё более прямое выражение нужного отношения на границе библиотеки. Это не означает, что последний пункт лучше для любого вызова. Для `io.Reader` нужен общий набор методов; для обхода полей неизвестной структуры нужны runtime-метаданные; для обычного `[]User → []string` естественен generic Map.

## Что означает «переиспользовали алгоритм»

Можно переиспользовать только цикл (`MapInto`), цикл и протокол операций (`RunMap`), шаблон исходника (генерация), динамическую реализацию (reflection) или типизированное отношение (`Map[E, R]`). Эти варианты устраняют разные виды повторения.

Считать только строки тела недостаточно. Учитывайте код вызова, адаптеры, проверки ошибок, промежуточные контейнеры и необходимость обновлять специализации. Короткий универсальный цикл может обойтись дорогим и хрупким API вокруг него.

## Стоимость: что измерять отдельно

Для конечных срезов Find и All имеют худшее время O(n) и O(1) дополнительной памяти самого обхода. Map выполняет n преобразований и хранит n результатов. Стоимость callback в эти оценки нужно включать отдельно. У всех вариантов может быть одна асимптотика и совершенно разная постоянная стоимость.

| Измерение | Что включаем | Какой вопрос задаём |
|---|---|---|
| Ядро алгоритма | Готовый адаптер / готовый boxed-срез | Сколько стоит сам обход? |
| Полный вызов | Упаковка, аллокации, распаковка, валидация | Сколько платит потребитель API? |
| Раннее совпадение | Предикат прекращает обход в начале | Сохранили ли короткое замыкание? |
| Отсутствие совпадения | Полный проход | Сколько стоит обработка каждого элемента? |
| Дешёвый и дорогой callback | Разные полезные вычисления | Доминирует ли механизм вызова? |
| Eager и lazy | Материализация или частичное потребление | Выполнен ли вообще одинаковый объём работы? |

Нельзя вынести упаковку `[]interface{}` из benchmark и затем объявить полученное время стоимостью полного API. Нельзя сравнить ленивый Map, который никто не потребил, с eager Map, который реально обработал все элементы. Нельзя обосновывать выбор только лозунгом «reflection медленный»: разделяйте настройку и поэлементную работу.

Результаты реальных запусков вынесены в [главу об измерениях](gp-measurements.md). Достоверный результат должен указывать Go toolchain, архитектуру, размер входа, работу callback, `ns/op`, `B/op`, `allocs/op` и повторяемость измерений.

## Минимальная библиотека после разбора

Для срезов достаточно начать с `Find[E any]`, `All[E any]`, `Map[E, R any]`. Поиск по значению может быть отдельным `Contains[E comparable]`. Для произвольных источников добавьте Seq-варианты с документированным завершением и семантикой повторного обхода.

Не добавляйте поддержку ошибок, параллелизма, контекста и отмены одним универсальным флагом. Например, `MapErr` с `func(E) (R, error)` должен определить: остановку на первой ошибке, возврат частичного результата, порядок и выполнение оставшихся callback. Эти решения не следуют из параметров типов.

Также не стоит дублировать стандартную библиотеку ради собственного названия: реальный поиск по предикату для среза уже есть как `slices.IndexFunc`. Учебные реализации здесь нужны, чтобы сравнить выразительность подходов.

## Практика, которая проверяет понимание

1. Добавьте `Order` и повторите Find/All/Map всеми подходами. Запишите, какие файлы и адаптеры понадобились, где выявились несовместимые callback.
2. Напишите `Filter[E any]` с сохранением порядка. Зафиксируйте поведение nil, пустого среза и отсутствия совпадений. Сравните срез результата с представлением через Seq.
3. Напишите `Reduce[E, A any]` с начальным аккумулятором и `func(A, E) A`. Объясните, почему тип аккумулятора может отличаться от E и зачем нужен начальный результат для пустого входа.
4. Создайте два Map: `User → string` и `User → []string`. Покажите, что Map сохраняет вложенность, а FlatMap потребовал бы другого алгоритма.
5. Добавьте ошибку callback на третьем элементе и спроектируйте `MapErr`. Проверьте, были ли обработаны четвёртый и пятый элементы.
6. Реализуйте FindSeq над деревом. Объясните, почему возвращается значение с bool, а не индекс среза.
7. Проверьте закон композиции Map с чистыми функциями. Затем найдите контрпример при побочных эффектах или изменяемых объектах.
8. Сравните benchmark ядра и полного вызова для Any, reflection и generics. Не делайте вывода по одному короткому запуску.

Для Filter важна не только сигнатура: если результат ссылается на исходный backing array, мутации будут наблюдаемы иначе, чем при новой аллокации. Для Reduce важен порядок: без ассоциативности нельзя произвольно распараллелить свёртку. Для ленивой композиции важен момент вычислений. Именно на таких вопросах проектирование алгоритмов становится содержательным.

## Исполняемые примеры и границы проверки

Основная историческая линия проверяется в [algorithms](../../algorithms/README.md): там находятся общие интерфейсные алгоритмы, примеры на наших типах и тесты ранней остановки, ошибок, стабильности и частичных результатов. Это первый пакет, который следует открыть после чтения начала курса.

В [examples](../../examples/README.md) находятся реальные реализации всех разобранных семейств, генератор специализаций и тесты общего контракта. Модуль требует Go 1.23 из-за итераторов; сами generic-алгоритмы используют возможности Go 1.18, а исторические варианты — более ранние механизмы.

Примеры в главах иногда опускают импорты и контекст вызова ради читаемости. Полные Go-файлы являются исполняемой версией. Исходные главы о конверсиях сохранены в том же учебнике как справочник: они объясняют локальные детали, а основная часть — место этих деталей в проектировании обобщённых алгоритмов.
