# 19. Зачем вводили новшества: проблемы и решения

Эта глава отдельно объясняет причины изменений, относящихся к учебнику. Даты и совместимость собраны в [истории возможностей](02-history.md). Ниже историческая мотивация подкреплена источниками; примеры с Fraction, Money и Stack — применение этих идей к нашему курсу.

## Интерфейсы и замыкания: общий алгоритм через операции

Алгоритму сортировки нужны сравнение и перестановка, а не знание полей каждого элемента. Поведенческий интерфейс позволяет передать эти операции; замыкание дополнительно связывает функцию с данными вызывающего. Так один обход работает с разными коллекциями. Но связь «получить значение T и вернуть тот же T» приходится сохранять в адаптере. Этот предел раннего подхода помогает понять дальнейшую мотивацию параметров типов. Источник: [Why Generics?](https://go.dev/blog/why-generics).

## Генерация: повторяющийся исходник создаёт инструмент

Когда программа зависит от схемы, описания протокола или таблицы констант, часть Go-кода можно получить автоматически. Команда `go generate`, добавленная в Go 1.4, дала стандартный способ записать и запустить такой шаг рядом с исходником. Раньше для этого использовали отдельные команды и сценарии сборки. Генерация не запускается автоматически при `go build`: автор явно обновляет производные файлы. В нашем курсе тот же механизм выпускает специализации алгоритмов. Источник: [Generating code](https://go.dev/blog/generate).

## Алиасы: перенос типа без одновременного обновления всех клиентов

При переносе типа между пакетами повторное объявление создаёт другой тип. Старые и новые пользователи API перестают свободно обмениваться значениями. Алиасы Go 1.9 дают старому и новому имени обозначать один тип, позволяя обновлять клиентов постепенно. В Go 1.24 этот способ распространили на типы с параметрами: выросшим generic-библиотекам понадобился такой же рефакторинг. Алиас сохраняет идентичность; определённый тип нужен, когда её как раз требуется изменить. Источник: [What's in an (Alias) Name?](https://go.dev/blog/alias-names).

## Параметры типов: общий код с проверяемыми связями типов

Для общего стека или Map приходилось дублировать код, генерировать специализации либо хранить значения через интерфейс с проверками при извлечении. Go 1.18 позволил выразить связь входа и результата в сигнатуре: Stack[T] принимает и возвращает T, а Map связывает E и R через callback. Проверка остаётся статической. Это не обещание ускорения: выигрыш прежде всего в выразительности API и сопровождении. Источники: [Why Generics?](https://go.dev/blog/why-generics), [An Introduction To Generics](https://go.dev/blog/intro-generics).

## Ограничения: тело общей функции тоже должно проверяться

Параметр T сам по себе не объясняет, разрешены ли сложение, сравнение или вызов метода. Ограничение задаёт допустимые типы и операции. Запись `~int` включает определённые типы с базовым int; ограничение методом описывает поведение. Так компилятор проверяет тело функции для всех разрешённых аргументов типов. Для Money наличие Add всё равно не доказывает совпадение валют: предметные условия остаются проверками самой операции. Источник: [An Introduction To Generics](https://go.dev/blog/intro-generics).

## comparable: согласовать generic API с обычными сравнимыми типами

Первоначальные правила не позволяли использовать некоторые сравнимые типы, включая any, как аргументы для comparable. Получалась неожиданная граница: обычная карта с интерфейсными ключами допустима, а соответствующая generic-функция их не принимает. Go 1.20 расширил удовлетворение ограничения. При этом сравнение интерфейсных значений с несравнимым содержимым по-прежнему может вызвать panic. Исправление доступности API не превращает динамическое сравнение в безусловно безопасную операцию. Источник: [All your comparable types](https://go.dev/blog/comparable).

## Вывод типов: убрать повторение уже известной информации

Если из среза и callback видны E и R, требовать их ещё и в квадратных скобках избыточно. Вывод позволяет писать Map(values, transform). Go 1.21 расширил его для generic-функций как аргументов и значений, методов при сопоставлении интерфейсов и смешанных нетипизированных констант. Практический результат — меньше явных инстанциаций при композиции функций. Для Zero[T]() информация о T по-прежнему отсутствует: тип результата вызова не выводится из переменной слева. Источник: [Go 1.21](https://go.dev/doc/go1.21#language).

## slices, maps и cmp: общие операции в стандартной библиотеке

После появления параметров типов стандартная библиотека смогла предложить типизированные операции над срезами и картами без отдельной реализации для каждого элемента. Пакеты Go 1.21 сокращают повторение поисков, сравнений и копирования в проектах. Для курса это переход от собственного учебного алгоритма к библиотечному договору: например, порядок NaN следует проверять по правилам cmp, а не предполагать обычное поведение операторов. Источник: [Go 1.21](https://go.dev/doc/go1.21#library).

## Итераторы: общий обход пользовательских источников

Параметр типа обобщил элемент, но функция с аргументом []E всё ещё требует срез. Деревья и другие контейнеры использовали собственные договоры обхода или заранее собирали результат. В Go 1.23 range по функциям и пакет iter дали общий протокол, совместимый с обычным циклом и ранним break. Преобразования можно соединять без обязательных промежуточных срезов. iter.Pull помогает потребителю запрашивать следующий элемент, например при чередовании двух источников. Завершение и освобождение ресурсов остаются частью договора. Источник: [Range Over Function Types](https://go.dev/blog/range-functions).

## Последующие уточнения: выразить привычные действия напрямую

Go 1.26 разрешил самоссылки в ограничениях generic-типов: связь типа с операциями над самим собой теперь можно описать в ранее запрещённых объявлениях. В том же выпуске `new(expr)` упростил получение указателя на начальное значение, для которого прежде заводили временную переменную или вспомогательную функцию. Практический смысл этих изменений — меньше обходных конструкций для явно заданного отношения или значения. Источник: [Go 1.26](https://go.dev/doc/go1.26#language).

Go 1.27 разрешил методам собственные параметры типов: обобщённую операцию можно поместить рядом с остальным API типа, вместо обязательной функции пакета. Методы интерфейсов собственных параметров типов по-прежнему не имеют, и generic-метод их не реализует. Вывод типов также распространился на дополнительные контексты присваивания и конверсии функциональных значений. В этом репозитории такие примеры защищены условиями сборки и требуют отдельной проверки новым компилятором. Источник: [Go 1.27](https://go.dev/doc/go1.27#language).

## Как читать причины изменений

Для каждого механизма задайте три вопроса: что приходилось повторять или обходить; какая связь стала выражаться непосредственно; какие проверки остались на вызывающем? Например, generics сохраняют тип Money, но не выбирают валюту; итератор задаёт протокол доставки, но не обещает повторяемость источника. Новые средства расширяют набор решений, а выбор определяется договором конкретной задачи.
