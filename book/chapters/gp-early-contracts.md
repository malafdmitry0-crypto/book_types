# 10. Min, Max, Sort и границы обещаний ранней библиотеки

Код главы: [algorithms.go](../../algorithms/algorithms.go) · [algorithms_test.go](../../algorithms/algorithms_test.go).


> Закончим первую библиотеку и проверим её договор: интерфейс делает алгоритм общим, но не делает ошибки и предметные ограничения невозможными.

Для поиска хватало проверки одной позиции. Минимум и сортировка требуют сравнения двух позиций, а сортировка — ещё и перестановки. Расширим договор ровно этими операциями и проверим его границы.

## Экстремум без возвращения неизвестного значения

```go
func Min(data Ordered) (int, error) {
	n := data.Len()
	if n == 0 {
		return -1, nil
	}
	best := 0
	for i := 1; i < n; i++ {
		comparison, err := data.Compare(i, best)
		if err != nil {
			return -1, err
		}
		if comparison < 0 {
			best = i
		}
	}
	return best, nil
}
```

У Min тот же удачный выход, что у Find: индекс. Тип значения остаётся у вызывающего, который обращается к исходному срезу. При равенстве лучший индекс не меняется — возвращается первое минимальное значение.

Max устроен симметрично: кандидат заменяет лучший индекс, если Compare дал положительный результат. Обе функции возвращают -1 для пустой коллекции и при ошибке сравнения; наличие ошибки отличает эти случаи.

```go
func ExampleMin() {
	values := []boxint.BoxInt{{Value: 3}, {Value: 1}, {Value: 2}, {Value: 1}}
	collection := boxes(values)

	index, err := algorithms.Min(collection)
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	if index == -1 {
		fmt.Println("Коллекция пуста")
		return
	}
	fmt.Println("Индекс:", index)
	fmt.Println("Минимум", values[index])
	// Output:
	// Индекс: 1
	// Минимум 1
}
```

Это учебный пример с известным непустым входом. В общем коде нужно проверить `err` и `index >= 0` до доступа `values[index]`. Индекс -1 нельзя безусловно использовать для обращения к срезу.

## От Ordered к Sortable

Для поиска экстремума достаточно сравнений. Для сортировки добавляется Swap. Реальная реализация нашего пакета намеренно короткая: стабильные вставки.

```go
func Sort(data Sortable) error {
	n := data.Len()
	for i := 1; i < n; i++ {
		for j := i; j > 0; j-- {
			comparison, err := data.Compare(j, j-1)
			if err != nil {
				return err
			}
			if comparison >= 0 {
				break
			}
			data.Swap(j, j-1)
		}
	}
	return nil
}
```

Для входа `3, 1, 2` последовательность действий такова:

```text
i = 1: Compare(1, 0) < 0 → Swap(1, 0) → 1, 3, 2
i = 2: Compare(2, 1) < 0 → Swap(2, 1) → 1, 2, 3
       Compare(1, 0) > 0 → остановить внутренний цикл
```

Равные элементы не переставляются, поскольку при Compare >= 0 внутренний цикл прекращается. Так сохраняется их относительный порядок. Худшая сложность — O(n²), дополнительная память — O(1).

Это не утверждение, что стандартная сортировка раннего Go целиком была таким циклом. Из раннего Go мы взяли способ связать алгоритм с коллекцией через интерфейс. Собственный алгоритм вставок выбран для чтения и объяснения. Стандартный API также отличался: Less не возвращал error, а наш Compare возвращает.

## Ошибка не означает откат

| Сценарий | Что уже произошло | Что остаётся вызывающему |
|---|---|---|
| Map ошибся на втором элементе | Первый Apply успешно выполнился | Частично заполненный результат |
| Sum начал с 50 USD, добавил 100 USD и встретил EUR | Аккумулятор стал 150 USD | Ошибка валюты и текущий Total |
| Sort переставил первую пару и получил ошибку при следующем сравнении | Часть элементов перемещена | Частично изменённый порядок |
| Find нашёл совпадение до невалидного элемента | Поздний элемент не посещался | Успешный индекс, без проверки всей коллекции |

Алгоритм может знать, что ошибка произошла, но не знать, как отменить действия произвольного адаптера. Если нужен атомарный результат, потребуется иной контракт: работа с копией, предварительная валидация, отдельное хранилище результата или поддержка отката. Такие требования не возникают автоматически из интерфейса.

## Пустые коллекции и нулевые значения

All пустой коллекции возвращает true, Any — false. Map пустой коллекции ничего не записывает. Sum не создаёт и не проверяет новое начальное значение — оставляет существующий аккумулятор. Sort не сравнивает пустую и одноэлементную коллекции. Min для единственного элемента возвращает индекс 0, не вызывая Compare.

Поэтому невалидная единственная Fraction может пройти через Min без ошибки, если адаптер не выполнил предварительную проверку. Общий контракт Ordered обещает сравнение, а не валидацию каждого элемента. Это ограничение нужно понимать, а не прятать за словом «типобезопасный».

Запуск производится современным toolchain проекта. Проверенные исходники алгоритмов используют модель обычных интерфейсов, а не параметры типов. Само наличие `go.mod` и современных реализаций числовых методов не относится к исторической эпохе Go 1.

## Итог первой эпохи: обобщение уже работает

Один algorithms обслуживает разные предметные типы. Ни один цикл не знает поля дроби или валюты. Конкретные значения и результаты сохраняют типы внутри адаптеров. Автоматического наследования методов или операторов не понадобилось.

Но добавление нового типа требует новых адаптеров. Сложные отношения вроде `[]E + func(E) R → []R` описываются косвенно, через конкретные структуры с полями. Именно это оставшееся повторение и отсутствие общей связанной сигнатуры создают мотивацию изучать interface{}, reflection, генерацию и позже параметры типов.

## Как читать продолжение

Следующие главы сравнивают альтернативы и развитие языка. `interface{}`, reflection и генерация — в том числе варианты, доступные до generics, а не последовательные замены друг друга. Для некоторых сравнений сохранён небольшой набор примеров над User из отдельного модуля examples; он показывает тот же вопрос типов на более простом API без ошибок callback.

Не смешивайте его `MapAny` или `Map[E, R]` с нашим `algorithms.Map(Mapping) error`: это разные учебные API. При сравнении с нынешними денежными и дробными типами нужно сохранять возврат ошибок. В главе о generics отдельно покажем такое продолжение контракта, не переписывая уже работающий ранний пакет.
